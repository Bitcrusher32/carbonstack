# v0.5.21 candidate review/update priority decision

Status: implementation-priority decision record
Phase: v0.5.x candidate/mismatch implementation staging
Scope: candidate review/update mechanics first, candidate/mismatch trust-history append integration second
Date: 2026-06-07 local session

## 1. Purpose

v0.5.21 decides the next implementation order after:

    v0.5.19 candidate identity storage;
    v0.5.20 pure mapped identity mismatch classifier.

This is a decision record only.

v0.5.21 does not implement candidate review/update mechanics.

Decision:

    A first:
      candidate review/update mechanics.

    B second:
      candidate/mismatch trust-history append integration.

Rationale:

    candidate state should become locally updateable before history append integration is added;
    append integration will be cleaner once candidate review/reject/unverified/conflict transitions exist;
    both steps must remain separate from trust.json mutation, verification ceremony, live provider import, CLI, registry, and local-backbone.

## 4. Decision A: candidate review/update mechanics first

v0.5.22 should implement candidate review/update mechanics.

Expected surfaces:

    carbonstack-comms/internal/trust/identity_candidate_review.go
    carbonstack-comms/internal/trust/identity_candidate_review_test.go

Expected first behavior:

    update candidate state by candidate_id;
    update candidate state by deterministic dedupe key if useful;
    allow observed -> pending_review;
    allow observed -> rejected;
    allow pending_review -> rejected;
    allow observed -> unverified if explicitly chosen;
    allow pending_review -> unverified if explicitly chosen;
    allow conflicts_known_device state when classifier output requires it;
    preserve observed_at;
    optionally set reviewed_at or updated_at if added;
    preserve raw public identity material;
    preserve fingerprint;
    preserve source/provenance;
    write only identity-candidates.json.

Required exclusions:

    no verified candidate state;
    no trust.json mutation;
    no trust-events.jsonl append;
    no device_verified;
    no device_key_changed;
    no provider identity import;
    no key replacement;
    no send/open/ack behavior change;
    no CLI;
    no registry;
    no local-backbone.

## 5. Candidate state-transition policy

Initial allowed transitions should be conservative.

Suggested first transition set:

    observed -> pending_review
    observed -> rejected
    observed -> unverified
    observed -> conflicts_known_device

    pending_review -> rejected
    pending_review -> unverified
    pending_review -> conflicts_known_device

    conflicts_known_device -> pending_review
    conflicts_known_device -> rejected

    unverified -> rejected

Do not allow:

    any state -> verified;
    rejected -> unverified without a deliberate future recovery/reopen policy;
    rejected -> pending_review unless a future explicit reopen helper is added;
    unverified -> verified;
    conflicts_known_device -> verified.

Rationale:

    rejected should be sticky for the first implementation;
    verified promotion requires ceremony and must not exist yet;
    conflict state should not auto-resolve into verified trust.

## 6. Decision B: trust-history append integration second

Candidate/mismatch trust-history append integration should come after candidate review/update mechanics.

Expected later scope:

    convert selected candidate/mismatch outcomes into provider/candidate trust-history events;
    append trust-events.jsonl only;
    no trust.json mutation;
    no verification;
    no key replacement;
    no send/open/ack behavior change.

Candidate future event names:

    provider_identity_candidate_observed
    provider_identity_candidate_review_started
    provider_identity_candidate_rejected
    provider_identity_candidate_marked_unverified
    provider_identity_candidate_conflict
    provider_identity_reverify_required
    provider_identity_promotion_blocked_revoked
    provider_identity_promotion_blocked_compromised

Do not emit:

    device_verified;
    device_key_changed;
    device_revoked;

unless the corresponding explicit mature ceremony/mutation/revocation flow exists.

## 8. CLI / registry decision

Do not add CLI or registry entries yet.

Reason:

    internal trust mechanics are still forming;
    exposing commands too early makes candidate review/verification look more mature than it is;
    registry should describe actual supported command/profile/script/API surfaces;
    CLI/registry should wait until the full local-backbone path is ready enough to be described honestly.

Preferred timing:

    late v0.5.x end-rung;
    after full local-backbone feasibility is stronger;
    before cleanup and v0.6.0 minor-epoch readiness.
