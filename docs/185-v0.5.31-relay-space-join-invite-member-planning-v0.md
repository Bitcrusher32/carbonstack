# v0.5.31 Relay Space join/invite/member planning

Status: architecture planning / join-invite-member decision record
Phase: v0.5.x Relay Space practical mechanics before implementation
Scope: Relay Space addressing, invite, join, member semantics, Cypher/Comms/OpenMLS trust boundaries
Date: 2026-06-08 local session

## 1. Purpose

v0.5.31 defines practical Relay Space join/invite/member mechanics after the v0.5.30 local-backbone blocker reassessment.

This is a planning record only.

v0.5.31 does not implement:

    Relay Space schema;
    Relay Space API routes;
    Relay Space join flow;
    Relay Space invite flow;
    Relay Space member tables;
    provider live-flow wiring;
    validation profile changes;
    CLI/registry entries;
    local-backbone;
    destructive reset/recovery;
    backup/restore;
    re-enrollment mutation;
    vault;
    PQ/hybrid crypto.

Decision:

    Relay Space is a routable server/conversation container and vector to OpenMLS join.
    OpenMLS/provider join is cryptographic group participation.
    Local Comms verification is actual trust/auth/presence.
    Cypher may store routing membership.
    Cypher must not become identity authority.
    Comms remains local trust/candidate/recovery authority.
    Relay Space implementation must wait for a later separate rung.
    Roadmap PDF should be refreshed after this v0.5.31 breakpoint is marked.

## 2. Current doctrine carried forward

v0.5.16 established:

    Relay Space is routing/conversation infrastructure.
    Relay Space is not identity authority.
    Relay admin is not a trust root.
    Cypher delivery is not trust.
    Server membership claims are not enough for client trust.
    Client trust history and verification remain local/client-owned.

v0.5.30 established:

    local-backbone is closer, but still not implementation-ready.
    Relay Space join/invite/member semantics need a dedicated planning rung.
    Cypher is downstream relay/storage context, not trust authority.

v0.5.31 refines the practical mechanics needed before implementation.

## 3. Core model

The core model is:

    Relay Space = addressable routing/conversation container.
    Invite = authorization to attempt routing access / join flow.
    Join = staged process that may include server routing, provider/OpenMLS membership, and local candidate observation.
    Member = context-specific word; must be qualified.
    OpenMLS/provider membership = cryptographic group state.
    Local verified trust = Comms-local trust/auth/presence decision.

Never collapse:

    joined Relay Space
    OpenMLS group member
    locally verified/trusted participant

into one concept.

## 4. Relay Space definition

A Relay Space is a persistent addressable routing/conversation container served by Cypher and consumed by Comms.

A Relay Space may contain:

    canonical relay_space_id;
    optional human label;
    routing member/device records;
    invite records;
    encrypted envelope queues;
    ack state;
    server-side routing/access metadata;
    future server-side moderation/access controls that do not become trust.

A Relay Space must not contain or decide:

    plaintext;
    verified identity;
    verified device trust;
    local trust state;
    local candidate promotion;
    key replacement;
    OpenMLS safety truth;
    user verification ceremony result;
    client trust-store mutation.

## 5. Addressing model

### 5.1 Canonical Relay Space identifier

Canonical Relay Space ID should be full-strength random identity, such as:

    UUIDv4;
    128-bit random token;
    or equivalent high-entropy opaque ID.

It should not be a 12-hex-character value.

Reason:

    12 hex characters are 48 bits.
    That may be acceptable as a short human display code, but not as the canonical globally exposed Relay Space identifier.

### 5.2 Human display code

A Relay Space may expose a short human display code for usability:

    12 to 16 hex characters;
    split into groups, for example 8F3A-C91B-2D44;
    or represented through a word-code phrase.

This code is for:

    human comparison;
    local UX;
    quick reference;
    verbal confirmation;
    non-authoritative display.

It is not the security authority.

### 5.3 Word-code phrase

A word-code phrase may be derived from the canonical invite token or short display code.

Example shape:

    banana-wall-red-applesauce

The phrase may map to grouped digest/code material, such as 3+3+3+3 digit/word chunks.

It should be treated as:

    display aid;
    confirmation aid;
    maybe anti-typo aid;
    not proof of trust by itself.

### 5.4 QR code

QR should encode the full invite package, not only the short display code.

A future QR package may include:

    server URL;
    relay_space_id;
    invite token;
    invite display code;
    optional relay_space label;
    protocol version;
    expiry/constraints if implemented;
    maybe provider bootstrap hint later;
    checksum/digest.

QR scan still must not imply verified trust.

## 6. Invite model

A Relay Space invite authorizes an attempt to access a routing space.

Invite claim can mean:

    server accepted an invite token;
    server associated an account/device/routing member with a Relay Space;
    server granted routing access;
    server may allow envelope queue operations for that member.

Invite claim must not mean:

    device is verified;
    user is authenticated by local trust standards;
    OpenMLS membership is complete;
    local trust is complete;
    existing members silently accepted identity;
    server may replace keys;
    Comms should mutate trust.json.

Future invite records may have:

    invite_id;
    relay_space_id;
    invite_token_hash;
    display_code;
    optional word_code;
    created_at;
    expires_at;
    max_claims;
    claim_count;
    created_by_member_id;
    state;
    constraints.

Plain invite tokens should not need to be stored server-side after hashing, if avoidable.

## 7. Join lifecycle

Join should be modeled as staged, not atomic.

Suggested stages:

    invite_created
    invite_claimed
    routing_member_registered
    provider_keypackage_submitted_or_observed
    provider_welcome_created
    provider_welcome_consumed
    provider_joined
    candidate_identity_observed
    candidate_review_required
    locally_verified

Meaning:

    invite_claimed:
      Cypher accepted invite/routing credential.

    routing_member_registered:
      Cypher can route envelopes for the member/device.

    provider_keypackage_submitted_or_observed:
      Comms/OpenMLS material needed for group join became available.

    provider_welcome_created:
      existing participant created provider/OpenMLS Welcome.

    provider_welcome_consumed:
      joining participant consumed Welcome.

    provider_joined:
      provider/OpenMLS state says the device is cryptographically in the group.

    candidate_identity_observed:
      Comms observed identity material and stores candidate/unverified state.

    candidate_review_required:
      Comms detected unverified/conflicting/reverify-required state.

    locally_verified:
      local verification ceremony or explicit trust decision completed later.

Only locally_verified should mean trusted.

## 8. Member terminology

The word member is overloaded and must be qualified.

Required terms:

    routing_member
    provider_member
    local_known_device
    local_verified_device
    candidate_identity
    blocked_or_revoked_device

Do not use unqualified member in implementation docs where trust semantics matter.

### 8.1 routing_member

A routing_member is server-side access/routing state in Cypher.

It can route envelopes.

It is not trusted identity.

### 8.2 provider_member

A provider_member is cryptographic group membership according to OpenMLS/provider state.

It is not automatically locally verified.

### 8.3 local_verified_device

A local_verified_device is a Comms-local trust-state result.

It must not be assigned by Cypher or by provider observation alone.

## 9. Cypher responsibility model

Cypher may store:

    relay_space_id;
    routing_member_id;
    account_id or routing account label;
    device_id;
    invite claim metadata;
    envelope queues scoped to relay_space_id;
    ack state;
    timing;
    payload size/hash metadata;
    access/rate-limit state;
    operational retention metadata.

Cypher may expose:

    create Relay Space later;
    create invite later;
    claim invite later;
    register routing member/device later;
    submit envelope scoped to relay_space_id;
    list/retrieve envelopes for a routing member/device;
    ack envelope after Comms permits ack;
    list routing metadata as allowed by local dev API.

Cypher must not store/claim:

    verified trust;
    local trust state;
    plaintext;
    trust.json authority;
    verification ceremony result;
    key replacement authority;
    provider safety truth;
    locally authenticated presence.

## 10. Comms responsibility model

Comms owns:

    local identity state;
    local trust state;
    local trust history;
    candidate identity storage/review;
    mapped mismatch classification;
    recovery classification/orchestration;
    provider event classification;
    provider trust reports/history;
    send/open/ack policy;
    future verification ceremony;
    local warnings/UX.

Comms must treat Relay Space artifacts as inputs to local policy, not as authoritative trust.

Relay Space join should feed:

    candidate observation;
    provider/OpenMLS join;
    local recovery checks;
    local review/reverify/verification path.

It must not directly verify identity.

## 11. OpenMLS/provider responsibility model

OpenMLS/provider owns cryptographic group operations:

    identity creation/loading;
    public bundle / KeyPackage generation;
    conversation/group creation;
    member add;
    Welcome generation;
    Welcome consume/join;
    message protect/open;
    storage/checkpoint state.

Provider/OpenMLS state can indicate cryptographic membership.

It cannot by itself decide local verified trust.

Provider observations that affect trust must pass through candidate/mismatch/recovery/report/history policy.

## 12. Recovery and unsafe state behavior

Relay Space actions must account for recovery safety.

Unsafe recovery states should block or warn before sensitive trust-sensitive actions.

Examples:

    recovery_missing_trust_store:
      do not claim trust continuity; allow only carefully bounded dev/routing diagnostics if needed.

    recovery_corrupt_trust_store:
      block trust-sensitive join/send/open/promotion flows.

    recovery_requires_reverify:
      allow candidate observation and routing diagnostics, but block trusted promotion.

    recovery_blocked_revoked:
      block promotion and trusted send.

    recovery_blocked_compromised:
      block promotion and trusted send.

Recovery history append is not recovery execution.

## 13. Ack policy

Relay Space must preserve the current ack boundary:

    server delivery is not enough;
    envelope retrieval is not enough;
    artifact write is not enough;
    provider report generation is not enough;
    trust-history append is not enough;
    event draft generation is not enough;
    routing membership is not enough;
    invite claim is not enough;
    only successful sidecar message-open/consume may permit ack unless a future negative-ack/quarantine design is explicitly created.

v0.5.31 does not create negative ack.

## 14. Metadata boundary

Relay Space does not provide metadata privacy.

Likely visible to Cypher:

    Relay Space identifier;
    timing;
    envelope size;
    sender/recipient routing metadata;
    invite claim metadata;
    routing member/device records;
    ack timing;
    IP/network metadata unless hidden externally.

Future work may reduce metadata, but v0.5.31 must not claim metadata-private messaging.

## 15. Minimal future implementation shape

Future implementation should likely be split.

First Cypher schema/API spike may add:

    relay_spaces table;
    relay_space_invites table;
    relay_space_members table;
    relay_space_id on envelopes or envelope routing table;
    create/claim/list APIs;
    tests proving routing-only semantics.

First Comms integration spike may add:

    client methods for Relay Space create/invite/claim/list;
    no trust mutation;
    no verification;
    no provider trust import;
    candidate observation handoff only when identity material is actually present;
    tests proving server membership does not mutate trust.json.

Do not combine all of this into one implementation rung.
