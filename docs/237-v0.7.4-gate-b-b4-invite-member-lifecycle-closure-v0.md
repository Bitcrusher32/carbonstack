## 4. Capability domains

### Relay-admin/dev authority

The current unauthenticated dev/operator surfaces may:

- create Relay Spaces;
- register routing members;
- create Relay Space invites;
- inspect members;
- transition active/disabled/left state.

These are development and validation capabilities. They are not authenticated production administration.

### Participant claim authority

A participant may present:

- a full Relay Space invite token;
- an existing account ID;
- an existing device ID owned by that account.

The claim path does not create an account and does not prove real-world identity.

### Routing authority

Only an active routing-member row for the exact Relay Space and device authorizes scoped Relay delivery.

Routing authority is not:

- identity verification;
- trust promotion;
- sender authenticity;
- OpenMLS group membership;
- application authorization beyond Relay delivery.

## 5. Invite lifecycle contract

- `max_claims = NULL` means unlimited claims.
- `claim_count` increments only for a committed newly created member.
- An idempotent same-member retry does not increment `claim_count`.
- The final finite claim transitions the invite to claimed.
- Expiry is evaluated at claim time.
- Malformed stored expiry is an internal data/compatibility error.
- Refused claims do not silently mutate invite state.
- Conditional update and transaction retry protect finite claim slots.
- Existing disabled or left membership is not silently reactivated through invite claim.

## 6. Member lifecycle contract

- `active` has routing authority.
- `disabled` has no routing authority and records `disabled_at`.
- `active -> disabled` is explicit.
- `disabled -> active` is explicit and clears `disabled_at`.
- `active -> left` is explicit.
- `disabled -> left` is explicit.
- `left` has no routing authority.
- same-state transition is idempotent.
- `left -> active` requires a future explicit rejoin workflow.
- no B4 path deletes member history.

## 7. Inspection and restart contract

The member-list route is the current inspection surface:

`GET /v0/relay-spaces/{relay_space_id}/members`

Inspection after restart must report the persisted routing-member state and `disabled_at` semantics.

Restart persistence means reopening the same Cypher database preserves committed lifecycle state. It does not claim:

- backup correctness;
- restore correctness;
- rollback safety;
- replication;
- multi-node consistency;
- crash-consistency beyond the exercised SQLite transaction path.
