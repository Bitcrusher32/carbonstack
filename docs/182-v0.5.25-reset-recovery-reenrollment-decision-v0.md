# v0.5.25 reset/recovery/re-enrollment decision

Status: reset/recovery/re-enrollment decision record
Phase: v0.5.x local-backbone blocker reduction
Scope: Comms-first reset/recovery/re-enrollment semantics; Cypher downstream context only
Date: 2026-06-07 local session

## 1. Purpose

v0.5.25 defines the reset/recovery/re-enrollment boundary after the v0.5.19-v0.5.24 candidate identity implementation arc.

This is a decision record only.

v0.5.25 does not implement reset code, recovery code, re-enrollment code, CLI, registry entries, local-backbone, Relay Space join, vault, or PQ/hybrid behavior.

Decision:

    reset/recovery/re-enrollment semantics must be defined before local-backbone work.
    Comms local state comes first.
    Cypher reset/recovery remains downstream operational context.

## 2. Current implementation context

Current implemented Comms trust/candidate surfaces include:

    trust.json load/save;
    trust-events.jsonl append/load;
    device verification/dev revocation/dev changed-state helpers;
    identity-candidates.json load/save/add/dedupe;
    candidate review/update transitions;
    pure mapped identity mismatch classifier;
    candidate/mismatch trust-history draft/event helpers;
    candidate observation orchestration.

Current candidate observation orchestration can:

    add or dedupe a candidate;
    optionally look up a known device by claimed_device_id;
    classify the candidate against the known device when available;
    append a selected trust-history event only when a candidate is newly added;
    return a structured result.

It still does not:

    mutate trust.json;
    verify identity;
    replace key material;
    emit device_verified, device_key_changed, or device_revoked;
    affect send/open/ack behavior;
    expose CLI/registry;
    implement local-backbone.

## 3. Why this rung is needed

v0.5.17 identified reset/recovery/re-enrollment immaturity as a local-backbone blocker.

v0.5.19-v0.5.24 reduced the candidate identity and mapped mismatch blockers, but did not define what happens when local identity/trust/provider state is missing, corrupt, stale, intentionally reset, recovered from backup, or deliberately re-enrolled.

Without this boundary, local-backbone would overclaim because it would not know how to handle:

    lost local app state;
    missing trust.json;
    missing trust-events.jsonl;
    missing identity-candidates.json;
    corrupt trust-bearing state;
    stale candidate identity records;
    missing or corrupt OpenMLS provider state;
    deliberate local identity reset;
    deliberate new-device re-enrollment;
    recovery from copied or restored state;
    replayed or stale provider artifacts after reset;
    known device mismatch after recovery.

## 4. Definitions

### 4.1 Reset

Reset means deliberately discarding or reinitializing local state.

Reset does not mean:

    verification;
    safe recovery;
    trust continuity;
    automatic key replacement;
    automatic re-enrollment;
    account recovery.

Reset can be narrow or broad.

Narrow reset examples:

    remove generated sidecar runtime artifacts;
    clear relay staging artifacts;
    clear local dev scratch state.

Broad reset examples:

    remove local app state;
    remove local provider state;
    remove candidate identity state;
    remove trust state.

Broad reset is dangerous and should require explicit scope.

### 4.2 Recovery

Recovery means restoring or reusing prior state after loss, corruption, migration, or reinstall.

Recovery does not automatically prove trust continuity.

Recovery must fail loudly when restored state conflicts with current provider observations, candidate observations, or known trust records.

Recovery should prefer:

    explicit state classification;
    explicit trust-history append;
    explicit user/operator warning;
    no silent verification;
    no silent key replacement.

### 4.3 Re-enrollment

Re-enrollment means deliberately introducing a new local identity/device path after loss, rotation, compromise, reinstall, or planned migration.

Re-enrollment is not the same as verification.

Re-enrollment should produce candidate/unverified state first unless a mature verification ceremony exists.

Re-enrollment must not silently replace a verified device identity.

## 5. State-domain decisions

### 5.1 Comms local app state

Current app state is dev/local state and may be reset in development flows.

Reset behavior should eventually distinguish:

    safe generated/dev state;
    user-relevant local app state;
    trust-bearing state;
    provider identity/group state.

### 5.2 trust.json

trust.json is trust-bearing state.

Resetting trust.json is destructive.

Missing trust.json may load as an empty store for current helpers, but mature flows must not treat that as trust continuity.

Recovery behavior:

    missing trust.json should mean no known verified devices;
    recovered trust.json should be checked against provider/candidate observations;
    mismatch should require review/reverify, not silent acceptance.

Re-enrollment behavior:

    re-enrolled device material must not auto-update trust.json;
    candidate/unverified state should come first;
    verified promotion requires a future explicit ceremony.

### 5.3 trust-events.jsonl

trust-events.jsonl is trust-history state.

Missing trust-events.jsonl currently loads as empty history.

Mature behavior should distinguish:

    empty because new install;
    empty because history intentionally reset;
    empty because history lost/corrupt.

Resetting trust-events.jsonl should be explicitly destructive.

Candidate/mismatch history append must not become trust mutation.

### 5.4 identity-candidates.json

identity-candidates.json is trust-adjacent candidate state.

It may contain raw candidate public identity material in dev/pre-alpha.

Resetting it removes review context and candidate provenance.

Recovery should preserve:

    candidate_id;
    fingerprint;
    source;
    source_detail;
    provider_event_name;
    candidate_state;
    observed_at;
    note/provenance.

Recovered candidates must not become verified automatically.

### 5.5 OpenMLS provider state

OpenMLS provider state is group/conversation/identity-bearing state.

Missing or corrupt provider state can affect identity continuity, group membership, epoch state, and message-open safety.

Reset behavior should be explicit and loud.

Recovery behavior should not silently regenerate or replace identity/group state.

Re-enrollment may eventually require a new provider identity path, but that should be candidate/unverified until verified externally.

### 5.6 Relay staging artifacts

Relay staging artifacts include KeyPackages, Welcomes, envelopes, and local generated transfer artifacts.

Resetting relay staging can be safe in dev flows, but message-open/ack boundaries must remain strict:

    do not ack unless message-open succeeds;
    do not treat retrieved artifacts as trusted identity;
    do not treat replayed/stale artifacts as fresh trust.

### 5.7 Cypher server state

Cypher state is downstream for v0.5.25.

Cypher may later need operational backup/restore/retention/reset policy, but Comms identity/trust recovery must be defined first.

Cypher must not become identity authority, verified-device authority, or silent key-replacement authority.

## 6. Recovery classifications

Future recovery helpers should classify state rather than immediately mutate it.

Suggested classifications:

    recovery_clean_local_state
    recovery_missing_trust_store
    recovery_missing_trust_history
    recovery_missing_candidate_store
    recovery_missing_provider_state
    recovery_corrupt_trust_store
    recovery_corrupt_trust_history
    recovery_corrupt_candidate_store
    recovery_corrupt_provider_state
    recovery_provider_identity_mismatch
    recovery_candidate_conflict
    recovery_requires_reverify
    recovery_requires_reenrollment
    recovery_blocked_revoked
    recovery_blocked_compromised

These classifications should initially be pure/non-mutating.

## 7. Reset scope model

Future reset helpers should require explicit scope.

Suggested scopes:

    generated_dev_artifacts
    relay_staging
    candidate_state
    trust_history
    trust_store
    provider_state
    local_app_state
    all_comms_local_state

Dangerous scopes:

    trust_store
    trust_history
    provider_state
    all_comms_local_state

Dangerous scopes should never be hidden behind a generic reset command.

## 8. Re-enrollment model

Re-enrollment should be a deliberate flow.

First implementation should likely be planning/pure helper only.

Re-enrollment should:

    create or observe candidate identity material;
    preserve old known trust state;
    append history;
    require review/reverify;
    avoid silent replacement;
    avoid verified import.

Re-enrollment must not:

    call VerifyDevice automatically;
    call MarkDeviceChanged automatically from provider observation alone;
    replace PublicIdentityKey automatically;
    mark verified automatically;
    bypass candidate review;
    ack messages;
    weaken send/open policy.

## 9. Trust-history append policy

Reset/recovery/re-enrollment may append history later.

Candidate event names may include:

    recovery_missing_trust_store
    recovery_missing_trust_history
    recovery_missing_candidate_store
    recovery_missing_provider_state
    recovery_corrupt_trust_store
    recovery_corrupt_provider_state
    recovery_candidate_conflict
    recovery_requires_reverify
    recovery_requires_reenrollment
    reset_candidate_state
    reset_relay_staging
    reset_generated_dev_artifacts
    reenrollment_candidate_observed
    reenrollment_requires_verification

Do not emit:

    device_verified;
    device_key_changed;
    device_revoked;

unless an explicit mature ceremony/mutation/revocation flow is being executed.

## 10. Send/open/ack policy

Reset/recovery/re-enrollment must not weaken send/open/ack behavior.

Rules:

    missing or reset trust does not imply safe send;
    recovered provider state does not imply verified trust;
    re-enrolled device material does not imply verified trust;
    message retrieval does not imply message-open success;
    artifact write does not imply ack;
    history append does not imply ack.
