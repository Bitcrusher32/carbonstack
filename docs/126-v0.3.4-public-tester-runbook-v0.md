# v0.3.4 Public Tester Runbook v0

Status: public testing runbook
Phase: v0.3.6 tester runbook / self-test UX cleanup
Applies to: CarbonStack v0.3.4 testing bug hotfix

## 1. What this is

This runbook explains how to test the CarbonStack v0.3.4 experimental backbone release from the attached release source snapshots.

The goal is to let a tester verify the current known-good local backbone path:

    CarbonStackComms OpenMLS sidecar
    CarbonStackCypher real local relay server
    opaque OpenMLS artifact envelope relay
    payload metadata validation
    consume-then-ack semantics

This is a local development/testing path.

It is not a production deployment guide.

It is not a secure messenger user guide.

## 2. What this release proves

A successful run proves that the v0.3.4 source snapshots can run the current local experimental backbone self-test on the tested machine.

It validates:

    local Cypher server test lifecycle;
    Comms OpenMLS sidecar artifact generation and consume path;
    opaque OpenMLS artifact relay through Cypher;
    payload metadata validation;
    consume-then-ack behavior in the tested harness;
    current local validation scripts.

## 3. What this release does not prove

This release does not prove:

    production readiness;
    production E2EE;
    hostile-server safety;
    metadata privacy;
    Android readiness;
    secure vault/storage;
    Linux portability;
    Debian deployability;
    external audit;
    certification.

Do not use this release as a production secure messenger.

## 7. Verify checksums

From the directory containing the downloaded release assets, compare SHA256 hashes against:

    carbonstack-v0.3.4-checksums.txt

On PowerShell, a basic hash command is:

    Get-FileHash .\carbonstack-v0.3.4-source-snapshot.zip -Algorithm SHA256
    Get-FileHash .\carbonstack-comms-v0.3.4-source-snapshot.zip -Algorithm SHA256
    Get-FileHash .\carbonstack-cypher-v0.3.4-source-snapshot.zip -Algorithm SHA256

Compare those values to the checksum file.

## 8. Run the targeted public self-test

From the extracted `carbonstack-comms` snapshot:

    cd .\carbonstack-comms
    powershell -ExecutionPolicy Bypass -File .\scripts\self-test-openmls-backbone.ps1

Expected result:

    OpenMLS backbone self-test completed successfully.

This runs the targeted known-good OpenMLS real-Cypher relay lifecycle proof.

## 9. Run full public validation

From the extracted `carbonstack-comms` snapshot:

    powershell -ExecutionPolicy Bypass -File .\scripts\self-test-openmls-backbone.ps1 -Full

## 11. Expected generated files after tests

Tests generate local build and development artifacts.

After testing, it is normal to see paths such as:

    target/
    .carbonstack-openmls-sidecar-state/
    provider-storage.json
    signer.json
    .phase1-validation-temp/
    *.db
    *.exe

These are generated after validation starts.

They must not be included in release source snapshots.

Their presence after tests does not mean the release shipped them.

## 12. Artifact guard behavior

v0.3.4 fixes the source-snapshot self-test path.

In a Git working tree, the artifact guard checks tracked files.

In a release source snapshot without `.git/`, the artifact guard uses filesystem fallback mode.

In non-strict source snapshot fallback mode, generated artifacts found after tests are reported as informational.

## 13. Common local issues

### Localhost / port issues

If real-Cypher tests fail with bind errors, refused connections, or odd localhost behavior, check for network tools interfering with local loopback tests.

Known local interference candidates:

    Tailscale
    Cloudflare WARP

Disable them temporarily and rerun before assuming the test failed because of CarbonStack logic.

### Antivirus / Go test executable issues

Some antivirus tools may interfere with Go-generated test executables.

If this happens, use a narrow Go temp/cache path for CarbonStack testing rather than excluding all of `%TEMP%`.

Do not create broad antivirus exclusions unless you understand the risk.

## 14. Reporting results

Useful test reports include:

    operating system;
    Go version;
    Rust version;
    command run;
    pass/fail result;
    full terminal log if failed;
    whether Tailscale/WARP/VPN-like tools were active;
    whether antivirus blocked generated test executables.
