# v0.7.2 Gate B B3 Relay Space-Scoped Normal-Message Path

**Status:** Implemented and registry/documentation aligned. Formal B3b closure remains intentionally pending a separate continuity-anchor re-examination.

## 1. Purpose

This document is the current authority for the ordinary CarbonStack dev/pre-alpha normal-message path after Gate B B1-B3 implementation.

It supersedes older wrapper descriptions wherever they imply an unscoped Cypher application-message submission or inbox route. Historical implementation and planning documents remain useful for chronology, but they do not override this boundary.

## 2. Implemented path

The current ordinary-message path is:

1. a Relay Space already exists;
2. sender and recipient devices each have active routing membership in that exact Relay Space;
3. Alice runs `message-send-dev --relay-space <relay-space-id> ...`;
4. Comms protects the message through the OpenMLS sidecar;
5. Comms submits the opaque application-message envelope through the Relay Space-scoped Cypher route;
6. Bob runs `message-inbox-dev --relay-space <relay-space-id> ...`;
7. Comms fetches Bob's whole device inbox within that exact Relay Space;
8. unsupported content-type or protocol-version pairs remain visible for explicit unsupported/no-ack classification;
9. supported messages are opened through the OpenMLS sidecar;
10. `--ack` performs a scoped acknowledgement only after successful message-open.

The lower-level `openmls-send-dev` and `openmls-inbox-dev` proof surfaces remain callable and are not silently redefined as the preferred operational wrapper path.

## 3. Required routing context

`message-send-dev` requires:

- `--relay-space`;
- `--to-device`;
- `--message`;
- `--sidecar-device-label`;
- `--conversation`.

`message-inbox-dev` requires:

- `--relay-space`;
- `--sidecar-device-label`;
- `--conversation`.

The wrappers do not create Relay Spaces, claim invites, or enroll members. Onboarding and membership lifecycle remain separate workflow leaves.

## 4. Active membership boundary

For scoped submission, both sender and recipient device membership must match:

- the exact Relay Space;
- the exact device;
- `state = active`;
- `disabled_at IS NULL`.

An account-only row is not device authorization.

Relay membership is a routing prerequisite only. It is not:

- verified identity;
- trust acceptance;
- MLS membership authorization;
- conversation authorization;
- secure enrollment;
- proof of account ownership;
- production access control.

## 5. Inbox and acknowledgement boundary

`message-inbox-dev` fetches the whole scoped device inbox rather than an application-message-only filtered helper result. This is required so unsupported content or protocol pairs reach the wrapper classifier instead of becoming invisible.

Acknowledgement rules are strict:

- no ack on fetch;
- no ack on empty inbox;
- no ack on unsupported content type;
- no ack on unsupported protocol version;
- no ack on sidecar message-open failure;
- scoped ack only after successful OpenMLS message-open and only when `--ack` was explicitly requested.

A wrong-recipient scoped fetch may correctly return an empty inbox. That is routing isolation, not an OpenMLS failure.

## 6. Validation surfaces

The aligned evidence includes:

- `dev-runtime-openmls-wrappers`;
- `integrated-runtime-dev`;
- `same-state-integrated-dev`;
- wrong-conversation failure;
- malformed-payload failure;
- wrong recipient/device/sidecar isolation;
- replay classification;
- unsupported content-type classification;
- Comms package tests;
- Cypher membership and scoped-route tests.

The wrapper smoke creates its Relay Space, registers active Alice/Bob routing members, sends through the scoped route, receives through the scoped route, and verifies the scoped inbox is empty after successful ack.

## 8. Explicit nonclaims

This path is not:

- production secure messaging;
- hostile-server safety;
- metadata privacy;
- verified identity;
- mature messenger UX;
- deployment;
- local-backbone;
- an adversarial campaign result;
- full operational-spine implementation;
- release-package validation.

## 9. B3b closure posture

The implementation, live smoke, same-state compatibility, unsupported-envelope visibility, registry, boundary table, generated command reference, and current operator documentation are aligned by this patch.

B3b is not declared formally closed in this document. The next action is a deliberate re-examination of continuity-anchor documents and active authority ordering. Only after that re-examination should B3b be formally closed and the later v0.7.3 breakpoint be generated.
