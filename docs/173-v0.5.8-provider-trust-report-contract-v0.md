# v0.5.8 provider-trust report contract

Status: implementation-contract record
Phase: v0.5.x state correctness and provider-linkage implementation staging
Scope: CarbonStackComms internal provider-trust report helper
Date: 2026-06-07 local session

## 1. Purpose

v0.5.8 records the contract for the provider-trust decision report helper added after the v0.5.6 provider-state linkage plan and v0.5.7 implementation spike.

v0.5.7 added a small non-mutating helper around:

    protocol.DecideProviderTrust

v0.5.8 clarifies:

    JSON fields are the diagnostic source of truth;
    human summaries are interpretive helper text;
    the helper remains internal-only for now;
    no CLI command exists yet;
    no registry update is required until a command/profile/script/API surface is added.

## 2. Current implementation boundary

Current CarbonStackComms implementation surfaces:

    carbonstack-comms/internal/protocol/provider_trust.go
    carbonstack-comms/internal/protocol/provider_trust_report.go
    carbonstack-comms/internal/protocol/provider_trust_report_test.go

Current component-local documentation:

    carbonstack-comms/docs/08-provider-trust-report-contract-v0.md

The provider-trust report helper is intentionally non-mutating.

It does not:

    mutate trust.json;
    append trust-events.jsonl;
    import provider identity;
    verify provider identity;
    mark devices changed in persistent trust storage;
    revoke devices;
    ack messages;
    replace send/inbox;
    create local-backbone.

## 3. JSON vs human summary

The structured report fields are the source of truth for diagnostics and future automation.

The human summary is interpretive documentation for humans.

Policy:

    JSON fields may become future CLI/test/stability surface;
    summary text should not be consumed as policy;
    summary text is not final UX copy;
    summary text may evolve more freely than the structured report shape.

## 4. Why no CLI command yet

No CLI command is added in v0.5.8 because the internal helper is still enough.

A CLI command becomes useful when:

    humans need to inspect arbitrary provider events from the terminal;
    runner tests need command-level coverage;
    docs need a user-visible diagnostic workflow;
    the registry is ready to track the surface.

Until then, keeping the helper internal avoids premature command-surface and registry expansion.

## 5. Registry boundary

No registry update is required in v0.5.8 because:

    no CLI command was added;
    no runner profile was added;
    no script was added;
    no API surface was added;
    no sidecar command was added.

If a future `provider-trust-report-dev` command is added, then:

    registry/commands.v0.yaml should be updated;
    registry tests should be updated if needed;
    component README/docs should describe it;
    nonclaims must remain explicit.
