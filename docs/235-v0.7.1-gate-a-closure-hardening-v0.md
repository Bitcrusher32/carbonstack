## 3. Capability domains

The preferred workflow uses three explicit capability domains:

    client
    relay-admin
    dev

Capability domain selection must be:

- explicit;
- inspectable;
- continuously visible during interactive use;
- recorded in resolved workflow context;
- checked before mutation;
- incapable of silently expanding authority.

Capability domains are not identity proof and do not replace server authentication.

### 3.1 Client domain

Intended role:

    ordinary participant lifecycle and local message operation

May inspect:

- active workspace context;
- local device and state summaries;
- Relay Space identity and non-authoritative labels;
- local Cypher/MLS membership classification;
- queued artifacts addressed to the active device;
- compatibility and refusal state.

May request:

- participant onboarding actions;
- Relay-scoped normal-message send;
- inbox retrieval;
- message open;
- acknowledgement after successful open;
- explicit participant-side reconciliation workflows when defined.

Must not silently perform:

- Relay administration;
- invite creation;
- membership creation or removal;
- trust promotion;
- MLS group mutation not required by the named client workflow;
- state repair;
- migration;
- reset;
- development-only fault injection.

### 3.2 Relay-admin domain

Intended role:

    explicit Relay Space coordination and routing administration

May inspect:

- Relay Space identity;
- Relay membership records;
- invite state;
- server-side delivery and acknowledgement summaries;
- routing mismatch classifications.

May request:

- Relay Space creation;
- invite creation or revocation when implemented;
- explicit membership coordination;
- explicit routing-member state changes;
- bounded server-side diagnostics.

Must not infer or mutate:

- MLS group membership;
- verified identity;
- local trust state;
- OpenMLS signer identity;
- cryptographic group state;
- plaintext;
- local recovery authority.

Relay-admin capability is coordination authority only.

### 3.3 Dev domain

Intended role:

    explicit development, test, fault-injection, inspection, and compatibility work

May expose:

- low-level proof commands;
- legacy-compatible development surfaces;
- fault injection;
- same-state evidence profiles;
- scoped reset operations;
- direct artifact inspection;
- diagnostic-only internal detail.

Dev domain must not:

- become the default;
- silently activate from current directory;
- silently activate from hidden files;
- silently weaken client or relay-admin refusal behavior;
- turn future aggregate execution into everything-dev;
- grant production or deployment claims.

### 3.4 Domain switching

Domain switching must be explicit.

A domain switch must:

- identify the previous domain;
- identify the requested domain;
- re-evaluate the active context;
- refuse if required context is missing or ambiguous;
- avoid carrying hidden mutation permission between domains;
- emit structured evidence.

Persistent domain selection, if later implemented, must remain visible and must not override per-command refusal checks.

## 4. Preferred lifecycle stage matrix

The following matrix defines the minimum Gate A contract for the preferred lifecycle.

### 4.1 Inspect environment

Owner:

    CarbonStack validation and Comms inspection surfaces

Capability:

    client, relay-admin, or dev

Reads:

- toolchain and dependency availability;
- configured paths;
- server reachability;
- active context metadata;
- state inventory.

Mutation class:

    READ_ONLY

Expected result:

    completed
    refused_precondition
    compatibility_blocked

Minimum refusals:

- missing required executable;
- unsupported platform or toolchain;
- unreadable context;
- ambiguous state roots;
- unsupported schema.

### 4.2 Initialize or select workspace

Owner:

    CarbonStackComms workflow and state adapters

Capability:

    client or dev

Reads:

- requested workspace path;
- existing workspace metadata;
- context schema.

Mutation classes:

    LOCAL_METADATA_MUTATION

Expected artifacts:

- explicit workspace/context metadata;
- non-secret path declarations.

Minimum refusals:

- workspace already exists with incompatible schema;
- path resolves inside a forbidden source-tree authority location;
- requested root overlaps another active authoritative root;
- unsafe permissions;
- ambiguity between multiple candidate workspaces.

Partial completion:

    failed_partial_local
    operator_action_required

### 4.3 Load and inspect operator context

Owner:

    CarbonStackComms workflow and state adapters

Capability:

    client, relay-admin, or dev

Reads:

- schema version;
- server URL;
- account and device IDs;
- Comms and OpenMLS roots;
- Relay Space and conversation IDs;
- selected capability domain.

Mutation class:

    READ_ONLY

Minimum refusals:

- missing required field for the requested operation;
- unsupported context schema;
- hidden or ambient authority conflict;
- selected domain incompatible with the requested operation;
- path ownership ambiguity.

### 4.4 Inspect local and server state

Owner:

    Comms inspection workflow with Cypher and sidecar adapters

Capability:

    client, relay-admin, or dev

Reads:

- local state summaries;
- trust and candidate metadata;
- OpenMLS state metadata;
- Relay membership records;
- delivery and acknowledgement summaries.

Mutation class:

    READ_ONLY

Minimum classifications:

    aligned
    cypher_member_mls_unknown
    mls_member_cypher_absent
    cypher_removed_mls_present
    pending_onboarding
    pending_removal
    stale_or_ambiguous
    unsupported_state

No inspection result may silently repair or reconcile state.

### 4.5 Create or select Relay Space

Owner:

    Comms workflow using Cypher coordination APIs

Capability:

    relay-admin or explicit dev

Reads:

- active server/account/device context;
- existing Relay Space IDs;
- requested non-authoritative label.

Mutation classes:

    SERVER_COORDINATION_MUTATION
    MULTI_DOMAIN_MUTATION when local context is also updated

Expected artifacts:

- immutable opaque Relay Space ID;
- optional non-authoritative label;
- structured stage result.

Minimum refusals:

- missing relay-admin capability;
- ambiguous server/account/device context;
- duplicate or conflicting requested identity;
- server incompatibility;
- partial server creation without local context update.

### 4.6 Register or select device

Owner:

    Comms workflow using Cypher device APIs

Capability:

    client, relay-admin, or dev according to operation

Reads:

- account context;
- device candidates;
- existing local state;
- registration metadata.

Mutation classes:

    SERVER_COORDINATION_MUTATION
    LOCAL_METADATA_MUTATION
    MULTI_DOMAIN_MUTATION

Minimum refusals:

- missing account;
- ambiguous existing device;
- incompatible existing local device state;
- attempted silent identity replacement;
- partial registration without durable result evidence.

Registration does not establish verified identity or OpenMLS binding.

### 4.7 KeyPackage preparation and submission

Owner:

    Comms workflow with OpenMLS sidecar and Relay adapters

Capability:

    client or explicit dev

Reads:

- signer/provider state;
- active device context;
- target Relay Space;
- recipient/onboarding context.

Mutation classes:

    CRYPTOGRAPHIC_STATE_MUTATION
    SERVER_DELIVERY_MUTATION
    MULTI_DOMAIN_MUTATION

Expected artifacts:

- KeyPackage identity;
- digest and size metadata;
- Relay-scoped envelope identity;
- stage result.

Minimum refusals:

- missing or incompatible signer/provider state;
- stale or ambiguous KeyPackage identity;
- unsupported protocol/ciphersuite;
- sender not an active Relay member when required;
- scoped submission failure;
- duplicate classification requiring operator action.

A KeyPackage is not acknowledged merely because it was fetched.

### 4.8 Add member

Owner:

    Comms workflow with OpenMLS sidecar

Capability:

    client acting as authorized group participant, or explicit dev

Reads:

- current MLS group state;
- selected KeyPackage;
- Cypher/MLS mismatch classification;
- artifact freshness metadata.

Mutation classes:

    CRYPTOGRAPHIC_STATE_MUTATION
    SERVER_DELIVERY_MUTATION when acknowledgement follows
    MULTI_DOMAIN_MUTATION

Expected artifacts:

- updated group state;
- Welcome artifact;
- completed-stage evidence;
- KeyPackage acknowledgement only after safe completion.

Minimum refusals:

- KeyPackage stale, duplicate, malformed, or unsupported;
- group state unavailable or incompatible;
- Cypher/MLS membership ambiguity;
- concurrent writer;
- partial cryptographic mutation;
- unsafe acknowledgement state.

### 4.9 Welcome submission, retrieval, and join

Owner:

    Comms workflow with Relay and OpenMLS sidecar adapters

Capability:

    client or explicit dev

Reads:

- Welcome identity and metadata;
- recipient device context;
- local signer/provider state;
- Relay and MLS membership classifications.

Mutation classes:

    SERVER_DELIVERY_MUTATION
    CRYPTOGRAPHIC_STATE_MUTATION
    MULTI_DOMAIN_MUTATION

Required behavior:

- staged join;
- final promotion only after successful completion;
- no acknowledgement after failed join;
- no silent overwrite of final conversation state.

Minimum refusals:

- stale or duplicate Welcome;
- wrong recipient/device;
- unsupported state or protocol;
- existing incompatible conversation state;
- concurrent writer;
- partial join requiring recovery;
- ambiguous membership.

### 4.10 Compatibility and membership inspection

Owner:

    Comms workflow with Cypher and sidecar inspection adapters

Capability:

    client, relay-admin, or dev

Mutation class:

    READ_ONLY

Required result:

- explicit Cypher membership state;
- explicit local MLS membership state;
- explicit mismatch classification;
- operation-specific safety decision.

Minimum refusal:

    safety-sensitive workflows refuse stale_or_ambiguous
    and unsupported_state classifications

No automatic reconciliation is permitted.

### 4.11 Relay-scoped normal-message send

Owner:

    Comms workflow with OpenMLS and Relay adapters

Capability:

    client or explicit dev

Reads:

- resolved workspace context;
- recipient trust policy;
- Relay membership state;
- MLS conversation state;
- protocol compatibility.

Mutation classes:

    CRYPTOGRAPHIC_STATE_MUTATION
    SERVER_DELIVERY_MUTATION
    MULTI_DOMAIN_MUTATION

Expected artifacts:

- protected MLS application artifact;
- Relay-scoped envelope;
- structured partial-completion evidence.

Minimum refusals:

- missing or ambiguous Relay Space;
- sender or recipient not an active Relay member;
- Cypher/MLS mismatch;
- trust policy block;
- unsupported protocol/ciphersuite;
- concurrent writer;
- protection succeeded but submission failed;
- silent fallback to unscoped delivery.

Silent scoped-to-unscoped fallback is forbidden.

### 4.12 Relay-scoped inbox retrieval

Owner:

    Comms workflow with Cypher client

Capability:

    client or explicit dev

Reads:

- active device;
- active Relay Space;
- queued scoped envelopes.

Mutation class:

    READ_ONLY before acknowledgement

Minimum refusals:

- missing active device;
- missing or ambiguous Relay Space;
- envelope outside selected scope;
- recipient mismatch;
- malformed metadata;
- unsupported content type.

Unscoped retrieval must not silently include Relay-scoped envelopes.

### 4.13 Message open

Owner:

    Comms workflow with OpenMLS sidecar

Capability:

    client or explicit dev

Reads:

- selected scoped envelope;
- local MLS conversation state;
- artifact metadata.

Mutation classes:

    CRYPTOGRAPHIC_STATE_MUTATION

Expected result:

- plaintext only after successful open;
- updated cryptographic state where required;
- explicit sender-metadata nonclaim;
- structured failure classification.

Minimum refusals:

- wrong conversation;
- wrong recipient/device;
- unsupported content type;
- malformed payload;
- replay or duplicate ambiguity;
- unsupported state;
- concurrent writer.

### 4.14 Acknowledgement

Owner:

    Comms workflow using Cypher delivery API

Capability:

    client or explicit dev

Reads:

- successful prior-stage evidence;
- envelope identity;
- recipient identity;
- current acknowledgement state.

Mutation classes:

    SERVER_DELIVERY_MUTATION

Preconditions:

- successful message open;
- successful staged Welcome join;
- successful add-member or explicit safe KeyPackage terminal classification.

Minimum refusals:

- no successful prerequisite evidence;
- envelope mismatch;
- recipient mismatch;
- unsupported or malformed artifact;
- ambiguous duplicate state;
- server conflict.

### 4.15 Stop, restart, and resume

Owner:

    validation/workflow orchestration

Capability:

    dev initially; later client and relay-admin where appropriate

Reads:

- resolved context;
- persisted local and server state;
- process/dependency state.

Mutation classes:

    READ_ONLY
    LOCAL_METADATA_MUTATION when explicit resume metadata is written

Required behavior:

- restart real dependencies;
- reload the same intended state;
- re-run compatibility and membership inspection;
- refuse silent state regeneration.

Minimum refusals:

- state path changed unexpectedly;
- state schema incompatible;
- missing authoritative state;
- regenerated empty state would replace existing authority;
- dependency resumed against a different database or state root.

### 4.16 Explicit scoped reset

Owner:

    development workflow only

Capability:

    dev

Mutation classes:

    LOCAL_METADATA_MUTATION
    LOCAL_POLICY_MUTATION
    CRYPTOGRAPHIC_STATE_MUTATION
    SERVER_COORDINATION_MUTATION
    SERVER_DELIVERY_MUTATION
    MULTI_DOMAIN_MUTATION according to selected scope

Required behavior:

- explicit scope;
- preview or inspection before mutation;
- no generic global force;
- no deletion outside the selected development scope;
- structured record of completed and failed stages.

Reset is not recovery, migration, rollback safety, or secure deletion.

## 7. Evidence requirements

Every implemented preferred-lifecycle leaf must eventually provide:

- deterministic positive evidence;
- relevant deterministic refusal evidence;
- explicit mutation classification;
- explicit context resolution;
- explicit acknowledgement behavior;
- no-silent assertions where applicable;
- restart or resumed-state evidence when stateful;
- current registry and documentation;
- nonclaims proportional to the actual proof.

Raw evidence may remain outside the repository.

Sanitized summaries may enter source only when they grant a specific bounded claim.

Development logs are not production audit logs.
