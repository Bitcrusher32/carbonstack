# CarbonStack v0.6.27 Vault/Security No-Silent State Model v0

Status: docs/model checkpoint after v0.6.27A broad recon.

Scope: state/security model, no-silent rules, backup/recovery implications, bounded substrate eligibility, and dependency notes for later PQ/hybrid and adversarial harness work.

This document is not an implementation.

This document does not add a vault.

This document does not add encryption.

This document does not claim secure key storage.

This document does not claim production backup/restore.

This document does not claim PQ or hybrid security.

This document does not claim hostile-server safety.

This document does not claim production secure messaging.

---

## 1. Purpose

v0.6.27A performed a broad recon across CarbonStack, CarbonStackComms, CarbonStackCypher, and CarbonStackOS to identify state surfaces relevant to the next v0.6.x modeling lane:

* vault/security state model;
* no-silent regeneration, replacement, import, delete, migration, and restore rules;
* backup/recovery implications;
* bounded substrate/stub eligibility;
* later PQ/hybrid dependencies;
* later adversarial harness dependencies.

The recon confirmed that CarbonStack now has enough OpenMLS message-flow and same-state validation evidence to stop expanding normal-message failure profiles by default and begin modeling state/security boundaries.

The goal of this document is to define the state model that future implementation must obey.

The correct model is not simply:

```text
secret vs not secret
```

The correct model is:

```text
authority class
+ sensitivity class
+ allowed mutation behavior
+ no-silent rule
+ recovery posture
```

A state surface may be non-secret but still safety-critical.

A state surface may be metadata but still operator-trust-sensitive.

A state surface may be generated/disposable in dev profiles but non-disposable in a future real deployment.

A state surface may be server-side coordination authority without being cryptographic plaintext authority.

---

## 2. Current context

v0.6.26 clarified two major output/trust boundaries before this model:

1. Normal message inbox sender metadata is unverified relay envelope metadata.

   * `from_device` remains as a compatibility field.
   * `from_device_unverified` is the clearer contract.
   * `sender_identity_verified: false` is explicit.
   * This is not identity verification.

2. `openmls-conversation-load-check-dev` distinguishes provider reloadability from summary metadata presence.

   * Provider storage remains runtime authority for existing message-open.
   * `conversation-summary.json` remains metadata/evidence for existing message-open.
   * Load-check may be stricter than message-open, but it must say so clearly.

This document builds on those decisions.

## 4. Model vocabulary

### 4.1 Runtime authority

State directly required to perform, refuse, open, ack, join, route, recover, or migrate.

If runtime authority is missing, corrupt, stale, or mismatched, the correct behavior is usually refusal, degraded mode, or explicit recovery.

Runtime authority must not be silently regenerated or replaced for an existing security-relevant context.

### 4.2 Server-side coordination authority

Server-side state that determines delivery, routing, membership, queue visibility, ack state, or Relay Space behavior.

This state affects system behavior but does not prove message plaintext authenticity or verified sender identity.

Cypher DB state currently falls mainly into this category.

### 4.3 Metadata / evidence

State that describes, summarizes, indexes, or records runtime state but is not itself runtime authority for existing message-open unless a future design deliberately changes that.

Metadata can be important for operators and validation, but it must not silently become runtime authority.

### 4.4 Secret-bearing state

State whose disclosure could compromise cryptographic identity, message secrecy, enrollment, recovery, or future protocol safety.

Secret-bearing state is not automatically production-vaulted today.

It is simply identified as requiring protection in future models.

### 4.5 Privacy-sensitive state

State whose disclosure can reveal social graph, device history, routing, timing, membership, identifiers, validation behavior, or operator actions.

Privacy-sensitive state may not be cryptographic secret material, but it still needs careful handling.

### 4.6 Safety-sensitive but not secret

State whose tampering can change trust, routing, membership, ack/drain, recovery, migration, or operator decisions even if the state is mostly public-key material or metadata.

Trust stores and identity-candidate stores belong here now.

They become runtime authority once wired into send/receive/enrollment policy.

### 4.7 Generated / disposable state

State that can be deleted and rebuilt only within clearly scoped dev, build, or validation contexts.

Generated/disposable state must never be confused with user state, trust state, runtime authority, or persistent deployment state.

### 4.8 Public / documentation state

Docs, generated references, runbooks, and public-facing explanatory material.

These do not directly operate the protocol, but they shape operator understanding and public claims.

They must not silently convert nonclaims into claims.

## 6. Authority model

### 6.1 Runtime authority surfaces

Current runtime authority surfaces include:

* Comms local account/device/server state;
* OpenMLS sidecar signer and provider state;
* OpenMLS conversation-level provider storage;
* final OpenMLS conversation directories;
* normal application-message payload integrity metadata used by wrappers;
* local state needed to bind a CLI operation to the expected account/device/server;
* trust/candidate stores only once they are wired into send/receive/enrollment policy.

Runtime authority must fail loudly when damaged, missing, stale, or mismatched.

Runtime authority must not be silently regenerated for an existing security context.

### 6.2 Server-side coordination authority surfaces

Cypher DB is server-side coordination authority.

It controls:

* account records;
* device records;
* invite records;
* Relay Space records;
* member/routing records;
* envelope rows;
* ack/delivery state;
* payload metadata used by Comms wrappers.

Cypher DB does not prove:

* message plaintext authenticity;
* verified sender identity;
* endpoint trust;
* local cryptographic continuity;
* hostile-server safety.

Therefore Cypher DB should be described as:

```text
server-side coordination authority
delivery/routing authority
not plaintext authority
not verified identity authority
```

### 6.3 Metadata/evidence surfaces

Metadata/evidence surfaces include:

* `conversation-summary.json`;
* `join-summary.json`;
* identity summary files;
* artifact manifests;
* command reference output;
* validation logs;
* generated docs;
* release notes.

Metadata/evidence can support operator understanding and validation.

Metadata/evidence must not silently become runtime authority.

### 6.4 Generated/disposable surfaces

Generated/disposable surfaces include:

* Rust `target/`;
* test/profile temp directories;
* runner-owned Comms state files;
* runner-owned Cypher DBs;
* sidecar dev state created by test profiles;
* reproducible build outputs.

Generated/disposable state is safe to delete only when scoped to dev/build/profile state.

Generated/disposable state is not a model for user/deployment state.

## 8. No-silent rules

These rules are stronger than implementation details. Future code must not bypass them without a dedicated design update.

### Rule 1: No silent runtime-authority regeneration

Runtime authority for an existing account, device, conversation, trust state, or delivery state must not be silently regenerated.

Allowed:

* create new state for a clearly new dev/test context;
* create new state under a new explicit label;
* create new state during explicit re-enrollment/recovery flow.

Forbidden:

* silently creating replacement provider storage for an existing conversation;
* silently creating a new signer for an existing device identity;
* silently creating a new trust store while pretending continuity remains intact;
* silently restoring “success” when runtime authority is missing.

### Rule 2: No silent runtime-authority replacement

Runtime authority must not be overwritten by new, stale, backup, imported, or generated state without explicit operator/user intent and clear warnings.

Forbidden:

* overwrite existing provider storage with backup state;
* overwrite local account/device state with imported state;
* overwrite trust state with provider-observed identity material;
* replace Cypher DB membership/routing state without explicit migration/recovery path.

### Rule 3: No silent verified trust promotion

Provider observation, Relay metadata, public bundles, KeyPackages, Welcome artifacts, and sender envelope metadata must not directly create verified trust.

Allowed:

* store as candidate;
* store as unverified evidence;
* emit provider-observed event;
* ask for review/confirmation in future UX.

Forbidden:

* mutate `trust.json` to verified from provider observation alone;
* treat `sender_device_id` or `from_device` as verified identity;
* treat Relay Space membership as cryptographic trust.

### Rule 4: No silent identity continuity after loss/reinstall/restore

If local identity material is lost, replaced, restored, or re-enrolled, continuity must not be implied silently.

Correct behavior must distinguish:

* same device continuing;
* restored prior device;
* new device;
* re-enrolled device;
* suspicious duplicate;
* stale backup;
* unknown state.

### Rule 5: No silent backup restore over newer state

A backup must not overwrite newer local or server coordination state without explicit confirmation and compatibility checks.

Future restore flow must consider:

* backup age;
* local current state age;
* algorithm version;
* migration epoch;
* account/device identity;
* Relay Space membership;
* trust/candidate state;
* conversation state;
* Cypher delivery/ack state.

### Rule 6: No silent migration

State migration must not silently change security semantics.

Forbidden:

* silent protocol epoch upgrade;
* silent algorithm upgrade;
* silent PQ/hybrid transition;
* silent downgrade after newer state exists;
* silent conversion of metadata into runtime authority;
* silent merge of incompatible state roots.

### Rule 7: No silent algorithm upgrade or downgrade

Algorithm or protocol-version state must be explicit and durable once introduced.

Future PQ/hybrid work must not silently upgrade existing conversations or silently downgrade upgraded conversations.

### Rule 8: No silent deletion of trust/security-relevant state

Deleting trust/security-relevant state must be explicit, scoped, and recoverability-aware.

Examples requiring care:

* `trust.json`;
* `trust-events.jsonl`;
* `identity-candidates.json`;
* OpenMLS provider storage;
* signer state;
* Cypher DB;
* Relay Space membership;
* delivery/ack state;
* migration markers.

### Rule 9: No ack/drain after failed open or failed join

If message-open fails, no ack/drain must occur.

If Welcome join fails, no Welcome ack/drain must occur.

If artifact write fails before sidecar processing, no relay-side ack must occur.

Existing v0.6.x profiles already enforce this for several normal-message and Welcome failure cases.

Future vault/recovery code must preserve this rule.

### Rule 10: No silent Relay Space membership or routing mutation

Relay Space membership and routing identifiers are server-side coordination authority.

They must not silently mutate in ways that change routing, membership, or operator expectations.

Allowed future behavior:

* explicit add/remove member;
* explicit role/state update;
* explicit migration with evidence;
* explicit recovery with warning.

Forbidden:

* silently rerouting envelopes;
* silently reassigning device IDs;
* silently accepting stale member records as current truth;
* silently treating Relay Space membership as verified identity.

## 10. Backup model v0

This document does not implement backup.

It defines what a future backup model must preserve.

### 10.1 Backup must bind identity and epoch

A backup should eventually be bound to:

* account ID;
* device ID;
* sidecar device label or future stable device identity;
* Relay Space membership context;
* conversation IDs/labels;
* algorithm/protocol version;
* migration epoch;
* created timestamp;
* source instance/fingerprint where available.

### 10.2 Backup must classify contents

A future backup manifest should classify each item as one or more of:

* secret-bearing;
* runtime authority;
* server-side coordination authority;
* metadata/evidence;
* safety-sensitive;
* privacy-sensitive;
* generated/disposable.

### 10.3 Backup restore must be explicit

Restore must not silently overwrite current state.

Restore must say whether it is:

* fresh install restore;
* same-device restore;
* new-device restore;
* post-loss re-enrollment;
* partial restore;
* server coordination restore;
* dev/test restore.

### 10.4 Backup cannot prove server truth

A local backup cannot prove that server-side coordination state is current.

Server-side state such as Relay Space membership, envelope delivery state, and ack state must be reconciled separately.

### 10.5 Backup cannot prove identity continuity alone

Restoring local state does not automatically prove identity continuity to peers.

Future identity/trust UX must distinguish restored local continuity from peer-verified continuity.

## 11. Migration model v0

This document does not implement migration.

It defines required migration posture.

### 11.1 Migration must be versioned

Future migration must record:

* source schema/version;
* target schema/version;
* protocol/algorithm version;
* migration ID;
* migration timestamp;
* pre-migration backup requirement;
* success/failure result;
* rollback availability.

### 11.2 Migration must be loud

Migration must never silently change:

* identity semantics;
* trust semantics;
* provider storage semantics;
* conversation state semantics;
* backup/restore semantics;
* algorithm/PQ semantics;
* Relay Space membership semantics.

### 11.3 Migration failure must not half-upgrade trust

A failed migration must not leave the system in a state where:

* trust is partially promoted;
* identity continuity is implied;
* algorithm state is ambiguous;
* old and new state are both silently accepted;
* ack/drain behavior changes without validation.

## 12. Bounded substrate eligibility

A future bounded substrate/stub may be useful after this model is accepted.

It must be named and framed carefully.

Preferred wording:

```text
bounded state substrate
vault-substrate-dev
state-boundary-dev
```

Avoid user-facing wording that implies:

```text
production vault
secure vault
secure key storage
encrypted vault
```

### 12.1 Allowed future substrate responsibilities

A future bounded substrate may:

* classify state paths;
* label state categories;
* centralize path policy;
* centralize refusal behavior;
* emit warnings;
* produce state inventory output;
* record non-security-claiming integrity metadata;
* enforce no-silent mutation gates;
* wrap import/export boundaries;
* support dev-only substrate tests.

### 12.2 Forbidden default substrate responsibilities

A future bounded substrate must not, by default:

* claim encryption;
* claim secure storage;
* claim production key protection;
* silently regenerate secrets;
* silently restore backups;
* silently migrate state;
* silently promote trust;
* silently import identity;
* silently upgrade algorithm/PQ state;
* hide provider storage failure;
* hide Cypher DB mismatch;
* hide Relay Space membership mismatch.

### 12.3 Substrate must refuse by default

For security-sensitive uncertainty, the default should be:

```text
refuse
warn
require explicit recovery path
```

not:

```text
repair silently
regenerate silently
guess
continue as if normal
```

## 15. Welcome / KeyPackage placement note

Welcome and KeyPackage artifacts are onboarding artifacts, not normal application messages.

They should be modeled well enough now that v0.7.x integration is easy, but full malformed/replay implementation should wait until onboarding lifecycle and Addressable Relay Space mechanics are better formalized.

Current posture:

* corrupt Welcome join failure is covered by v0.6.x profile work;
* Welcome replay is not fully covered;
* KeyPackage replay is not fully covered;
* server equivocation around onboarding is not covered;
* Relay Space membership does not prove verified identity;
* KeyPackage/Welcome metadata must not silently promote trust.

Future v0.7.x work should revisit these after Relay Space mechanics are formalized.

## 16. Concrete current decisions

### Decision 1: `trust.json` and `identity-candidates.json`

Current model:

```text
safety-sensitive now;
future runtime authority once wired into send/receive/enrollment policy.
```

Reason:

* these stores affect future trust and identity decisions;
* they are not yet a complete verified identity gate for current message-open;
* treating them as full runtime authority now would overclaim;
* treating them as harmless metadata would understate tamper risk.

### Decision 2: Cypher DB

Current model:

```text
server-side coordination authority;
delivery/routing authority;
not message plaintext authority;
not verified identity authority.
```

Reason:

* Cypher controls envelope visibility, delivery state, ack state, Relay Space routing, accounts, devices, and membership;
* Cypher does not decrypt message plaintext;
* Cypher does not prove verified sender identity;
* hostile-server safety remains a nonclaim.

### Decision 3: `conversation-summary.json`

Current model:

```text
metadata/evidence;
not runtime authority for existing message-open.
```

Reason:

* provider storage remains runtime authority for existing message-open;
* load-check may be stricter than message-open;
* metadata loss should be loud but should not automatically redefine runtime authority.

### Decision 4: Welcome/KeyPackage replay placement

Current model:

```text
document and model now;
implement later after onboarding lifecycle and Addressable Relay Space mechanics mature.
```

Reason:

* these are onboarding-artifact cases;
* they touch join state, Welcome ack, KeyPackage freshness, membership, and possible state poisoning;
* they should not be wedged into the normal-message profile lane.

### Decision 5: PQ/hybrid

Current model:

```text
dependency notes only in this document;
full PQ/hybrid placement model comes later.
```

Reason:

* PQ requires state tags, algorithm versioning, migration, recovery, compatibility, and downgrade rules;
* doing PQ implementation before state model would create fake security claims.

## 20. Summary

The v0.6.27 model position is:

```text
State is not just secret material.

State is authority, evidence, coordination, safety signal, privacy surface, and recovery context.

CarbonStack must refuse loudly when authority is missing, stale, corrupt, mismatched, or replaced.

CarbonStack must never silently promote trust, restore backups, regenerate runtime authority, migrate algorithm state, or ack/drain after failed cryptographic/state operations.

A future bounded substrate can help enforce these boundaries, but it is not a production vault.
```
