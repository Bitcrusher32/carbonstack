# CarbonStack v0.6.16 Same-State Integrated Dev Profile v0

Status: implementation checkpoint for a dev/pre-alpha validation profile.

## Scope

This document records the committed same-state integrated proof profile:

    go run . --profile same-state-integrated-dev --root <umbrella root> --clean-generated

The profile proves a positive-path same-state flow:

    Relay KeyPackage -> add-member -> Welcome -> join -> message-send-dev -> message-inbox-dev --ack

The proof uses one coherent live-dev temp universe:

    one runner-owned temp root;
    one Cypher server;
    one Cypher DB;
    same Alice/Bob Comms state files;
    same Alice/Bob Cypher device IDs;
    same Alice/Bob sidecar labels;
    same conversation label;
    same Relay Space;
    normal message send/open after Bob joins the conversation.

## Non-scope

    full;

## Why this is a new profile

The existing `integrated-runtime-dev` profile remains:

    relay-openmls-join-dev -> dev-runtime-openmls-wrappers

That is honest sequential composition.

The new `same-state-integrated-dev` profile is stronger because it proves Relay onboarding and normal message flow inside one coherent state story.

Keeping the profiles separate avoids changing the meaning of `integrated-runtime-dev` by surprise.

## Proof level

This profile targets Level 4 from the v0.6.15 planning doc:

    same conversation normal-message proof

Required evidence:

    Alice and Bob are initialized against the same Cypher server;
    Alice and Bob register devices in the same Cypher DB;
    Alice and Bob are members of the same Relay Space;
    Alice and Bob sidecar identities use unique labels;
    Alice creates the conversation;
    Bob submits KeyPackage through Relay Space;
    Alice add-member produces Welcome;
    Bob joins the same conversation;
    Bob conversation load-check reports group_reloadable true;
    Alice sends normal message using message-send-dev;
    Bob opens and acks using message-inbox-dev --ack;
    Bob inbox is empty after ack;
    DB counters show expected envelope and ack state;
    trust/candidate files remain absent.

## Relationship to v0.6.16A probe

v0.6.16A was a temporary shell-level probe.

It proved the same state story before committing a named profile.

v0.6.16 turns that evidence into a runner-owned profile while preserving strict nonclaims.

## Expected DB shape

Positive-path same-state proof expects:

    accounts: 2
    devices: 2
    relay_spaces: 1
    relay_space_members: 2
    envelopes: 3
    envelope_acks: 2
    KeyPackage envelope queued: 1
    Welcome envelope acknowledged: 1
    Welcome ack rows: 1
    Bob inbox after normal message ack: 0

Envelope meaning:

    KeyPackage remains queued because it is onboarding artifact transport and not acked by add-member.
    Welcome is acknowledged after successful join because ACK_AFTER_JOIN is intentionally enabled in this profile.
    Normal application message is acknowledged after successful message-open and explicit --ack.

## Ack doctrine retained

Application-message ack rule:

    no ack on fetch;
    no ack for unsupported envelope;
    no ack on artifact-write failure;
    no ack on sidecar message-open failure;
    ack only after successful sidecar message-open;
    ack only when --ack is explicit.

Relay onboarding ack rule:

    KeyPackage fetch/write alone is not ack eligibility;
    add-member success alone does not ack KeyPackage;
    Welcome fetch/write alone is not ack eligibility;
    Welcome join success/reloadable state may ack only under explicit flag;
    failed join must not ack.

## Future work

After this profile, future work should add failure-path coverage before promotion:

    missing KeyPackage;
    missing Welcome;
    add-member failure;
    join failure;
    message-open failure;
    wrong Relay Space;
    wrong recipient;
    wrong conversation/group;
    stale generated state;
    malformed relay payload;
    duplicate/replay behavior.

This profile should not be added to `full` or `release-snapshot` until a separate preflight explicitly changes that boundary.
