# v0.5.30 local-backbone blocker reassessment

Status: blocker reassessment / next-rung decision
Phase: v0.5.x post-recovery-orchestration local-backbone readiness
Scope: CarbonStack, CarbonStackComms, CarbonStackCypher downstream context
Date: 2026-06-08 local session

## 1. Purpose

v0.5.30 reassesses local-backbone readiness after the candidate/mismatch/recovery implementation arc.

This is a docs-only reassessment.

v0.5.30 does not implement:

    local-backbone;
    Relay Space schema;
    Relay Space join/invite/member behavior;
    provider live-flow wiring;
    validation profile changes;
    CLI/registry entries;
    destructive reset/recovery;
    backup/restore;
    re-enrollment mutation;
    vault;
    PQ/hybrid crypto.

Decision:

    local-backbone is closer, but still not implementation-ready.
    v0.5.31 should be a dedicated Relay Space recon/planning rung.
    Relay Space implementation must be a later separate rung.
    Roadmap PDF refresh should wait until around v0.5.35 unless the plan changes materially.

## 2. Current state after v0.5.29

The post-v0.5.0 v0.5.x arc has now implemented a real internal trust/recovery ladder:

    provider trust report;
    provider trust history draft;
    provider trust event draft bridge;
    trust-owned provider append helper;
    candidate identity storage;
    mapped identity mismatch classifier;
    candidate review/update mechanics;
    candidate/mismatch history events;
    candidate observation orchestration;
    reset/recovery/re-enrollment boundary decision;
    pure recovery classifier;
    recovery-history append helpers;
    recovery orchestration / classification composition.

The v0.5.29 recovery orchestration path can:

    classify local recovery state;
    optionally build recovery-history draft;
    optionally append recovery-history event;
    skip recovery_clean_local_state by default;
    return structured orchestration result.

It still does not:

    execute reset;
    delete files;
    restore files;
    recover files;
    re-enroll identities;
    mutate trust.json;
    mutate identity-candidates.json;
    verify identity;
    mark devices verified;
    mark devices changed;
    revoke devices;
    replace known key material;
    affect send/open/ack behavior;
    expose CLI;
    update registry;
    implement Relay Space join;
    create local-backbone.

## 3. Why local-backbone is closer

Local-backbone is materially closer than it was at v0.5.17 because several earlier blockers are now implemented as internal helpers.

Candidate identity is no longer only a plan:

    identity-candidates.json storage exists;
    candidate dedupe exists;
    candidate states exist;
    candidate review/update mechanics exist;
    candidate/mismatch history append helpers exist;
    candidate observation orchestration exists.

Mapped identity mismatch is no longer only a plan:

    pure candidate-vs-known-device classifier exists;
    continuity, conflict, reverify, changed-candidate, revoked, and compromised cases are modeled.

Recovery is no longer only doctrine:

    reset/recovery/re-enrollment boundary exists;
    pure recovery classifier exists;
    recovery-history append helpers exist;
    recovery orchestration exists;
    clean-state append is intentionally skipped by default.

These reduce the local-backbone blocker set from broad unknowns to a smaller named set.

## 4. Why local-backbone is still not ready

Local-backbone is still not implementation-ready because the system still lacks several claim-critical pieces.

Remaining blockers:

    Relay Space join/invite/member semantics are not planned deeply enough;
    Relay Space schema/API implementation does not exist;
    provider live-flow wiring boundary is not decided;
    broad provider event import is not wired into app flows;
    Comms send/inbox remain split between dev/runtime and older surfaces;
    validation profile claim wording is not ready;
    local-backbone cleanup/reset boundaries are not ready;
    CLI/registry surfaces would overstate maturity;
    mature verification ceremony does not exist;
    verified provider identity import remains forbidden;
    destructive reset/recovery/re-enrollment mutation helpers do not exist and should not be rushed;
    vault remains later;
    PQ/hybrid remains later.

Critical boundary:

    helper orchestration is not user-facing recovery.
    local recovery-history append is not trust verification.
    provider observation is not identity verification.
    Relay Space membership will not equal trusted membership.

## 5. Cypher downstream assessment

CarbonStackCypher remains relay/storage infrastructure.

Cypher currently provides useful downstream primitives:

    dev invite creation/claim surface;
    device registration/lookup;
    encrypted envelope submit/retrieve/ack;
    SQLite-backed local development persistence;
    local operator runbook;
    Relay Space boundary documentation.

Cypher must not become:

    identity authority;
    verified-device authority;
    trust root;
    plaintext authority;
    silent key-replacement authority;
    local trust-store mutation authority.

For v0.5.31, Cypher should be included as Relay Space downstream context, but not as the place where trust semantics are decided.

## 6. Relay Space decision

v0.5.31 should be a dedicated Relay Space recon/planning rung.

It should answer:

    what is a Relay Space?
    what is a join?
    what is an invite?
    what is a member?
    what is server-side membership?
    what is provider/MLS membership?
    what is local verified trust?
    what can Cypher store?
    what can Cypher claim?
    what must remain client-owned?
    what must fail loudly when identity/recovery state is unsafe?

v0.5.31 should not implement Relay Space.

Relay Space implementation should be a later separate rung only after the planning record stabilizes.

## 7. Provider live-flow decision

Do not broadly wire provider live-flow next.

Reason:

    provider live-flow wiring depends on Relay Space membership semantics;
    provider observations still must not verify identity;
    provider event append must not mutate trust.json;
    ack must remain open-success gated;
    candidate/recovery helpers are still internal.

Provider live-flow boundary should likely be revisited after Relay Space planning.

## 8. Validation profile decision

Do not add a local-backbone validation profile yet.

A future local-backbone profile must distinguish:

    what it proves;
    what it does not prove;
    whether it is live-git-umbrella-only;
    whether it is release-package-validatable;
    what generated state it creates;
    what cleanup behavior is safe;
    whether it touches trust/candidate/provider state;
    whether it can be run from public package roots.

Current validation should remain:

    Comms package tests;
    Cypher package tests;
    runner tests;
    runner doctor;
    existing release/package profiles.

## 9. CLI / registry decision

Do not add CLI or registry entries yet.

Reason:

    recovery/reset/re-enrollment commands are dangerous;
    Relay Space is not planned deeply enough;
    local-backbone is not claim-safe;
    helper APIs are internal and not mature UX;
    CLI/registry entries would imply a supported dev surface.

CLI/registry should remain an end-rung candidate around v0.5.35+ only if local-backbone or Relay Space dev surfaces become honest enough to expose.

## 10. Roadmap refresh decision

Do not refresh the roadmap PDF at v0.5.30.

Preferred roadmap refresh timing:

    around v0.5.35;
    after Relay Space planning;
    after provider live-flow boundary planning;
    after validation-profile boundary planning;
    after local-backbone go/no-go reassessment;
    before CLI/registry prep if that prep becomes plausible.

The v0.5.27 roadmap remains structurally useful, but v0.5.28 and v0.5.29 should be understood as now-complete rather than future.
