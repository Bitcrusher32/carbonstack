## 2. Message-ish surface inventory

Current message-ish surfaces fall into four buckets.

### 2.1 Legacy stub message path

    comms.send
    comms.inbox
    comms.ack

Current behavior:

- `send` uses the mock/stub crypto provider.
- `send` submits text-stub content.
- `inbox` decrypts and prints stub plaintext.
- `ack` acknowledges legacy envelope IDs.
- all three print legacy-stub warnings.

Classification:

    legacy continuity surface
    useful for older lifecycle and Cypher envelope tests
    not normalized OpenMLS message flow
    not production messaging
    not mature UX

### 2.2 OpenMLS application-message dev path

    comms.openmls-send-dev
    comms.openmls-inbox-dev
    sidecar.message-protect
    sidecar.message-open
    cypher.api.envelope-ack

Current behavior:

- `openmls-send-dev` calls the OpenMLS sidecar `message-protect` path.
- it submits an OpenMLS application-message envelope through Cypher.
- it emits payload hash/size metadata and sidecar labels.
- `openmls-inbox-dev` filters OpenMLS application-message envelopes.
- it writes the envelope payload to a temporary local artifact.
- it calls sidecar `message-open`.
- it can ack only after successful open when `--ack` is explicitly passed.

Classification:

    best current implementation seed for normalized OpenMLS message flow
    dev/pre-alpha
    not final user UX
    not vault-backed durable message storage
    not hostile-server proof

### 2.3 Relay Space artifact/onboarding path

    comms.openmls-relay-keypackage-submit-dev
    comms.openmls-relay-keypackage-inbox-dev
    comms.openmls-relay-add-member-dev
    comms.openmls-relay-welcome-submit-dev
    comms.openmls-relay-welcome-inbox-dev
    comms.openmls-relay-join-dev
    runner.relay-openmls-join-dev

Current behavior:

- KeyPackage and Welcome artifacts can be transported through Relay Space scoped envelopes.
- add-member can consume a KeyPackage and produce/send a Welcome.
- join can consume a Welcome and optionally ack it after successful join.
- these commands remain dev/pre-alpha and explicitly do not prove identity verification, mature trust mutation, production onboarding, or mature UX.

Classification:

    onboarding/artifact lifecycle primitives
    separately callable by design
    valid future lifecycle-test chain material
    not normal message inbox
    not the only known way to operate the lifecycle

### 2.4 Runner and script surfaces

    runner.dev-runtime-openmls

## 3. Normalized OpenMLS message-flow target decision

v0.6.x normalized encrypted message flow should be modeled from:

    openmls-send-dev
    openmls-inbox-dev --ack

Target content/protocol shape:

    content_type: application/vnd.carbonstack.openmls.application-message
    protocol_version: openmls-sidecar

Required preconditions:

- sender and recipient Comms state exist;
- Cypher server is reachable;
- OpenMLS sidecar identity state exists;
- a conversation exists or has been joined;
- Relay Space onboarding/artifact flow has already produced the needed conversation state;
- trust policy has allowed the send path;
- message-open succeeds before ack.

This target does not mean `openmls-send-dev` and `openmls-inbox-dev` are final command names. They are the current implementation seed.

Future normalized commands may be introduced as wrappers/aliases only after the current seed path is test-protected and documented.

## 4. Legacy stub demotion decision

Legacy `send`, `inbox`, and `ack` should remain callable for now.

Rationale:

- they preserve older lifecycle coverage;
- they keep Cypher envelope behavior easy to test;
- they provide known-good regression contrast;
- deleting them early would create avoidable churn.

However, they should not remain ambiguous long term.

v0.6.x demotion plan:

    Stage 1 / v0.6.1:
      document them as legacy stub continuity surfaces only.

    Stage 2 / v0.6.2 target:
      compare all unit/lifecycle tests that use legacy commands against the OpenMLS path.
      replace stub-path tests where OpenMLS coverage is equivalent or stronger.
      keep stub tests only where they intentionally validate low-level Cypher envelope mechanics.

    Stage 3 / v0.6.2 target if coverage is sufficient:
      gate, rename, or otherwise demote legacy stub commands.
      do not silently leave them as equal public message commands.

Preferred strategy:

    checks and replacements over full retirement

Do not hide or rename legacy commands until replacement coverage is explicit.

## 5. Relay Space lifecycle-wrapper decision

Relay Space onboarding should be part of lifecycle testing, but primitives must remain separately callable.

Decision:

- keep KeyPackage, Welcome, add-member, and join commands as direct primitives;
- allow a future full-spectrum wrapper for happy-path lifecycle testing;
- do not make the wrapper the only known path;
- require wrapper output to expose underlying steps and failure boundaries;
- keep artifact inboxes separate from message inboxes.

Reasoning:

- operators/tests may need only KeyPackage submit, only add-member, only Welcome inbox, or only join;
- trust and recovery states may need partial lifecycle operations;
- wrappers are useful for smoke tests, but dangerous as the only interface.

## 6. Ack semantics decision

Current posture:

    openmls-inbox-dev supports explicit --ack
    ack happens only after sidecar message-open succeeds

v0.6.x target:

- do not ack on fetch;
- keep manual/explicit ack for now;
- treat ack-after-successful-open as the near-term tested behavior;
- later, once vault/durable local storage exists, prefer ack after decrypt plus durable local store/vault commit.

Forbidden behavior:

    acknowledging an envelope merely because it was fetched

Rationale:

- fetch does not prove decrypt/open succeeded;
- successful open does not yet prove durable local storage;
- vault/storage maturity is not present yet;
- hostile-server/replay behavior is not fully characterized.
