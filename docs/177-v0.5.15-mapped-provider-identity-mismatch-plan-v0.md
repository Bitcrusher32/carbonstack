## 3. Core rule

A provider identity mismatch is not automatically a verified fact.

It is a security-relevant observation that may require:

    history append;
    warning;
    review;
    strict-send block;
    re-verification;
    later changed-state mutation if and only if a known mapping exists and policy allows it.

Provider observation alone must not:

    verify a device;
    silently replace a known key;
    silently mark a known device changed without mapped mismatch policy;
    trust Cypher as identity authority;
    trust sidecar labels as identity authority.

## 4. Definitions

### 4.1 Mapped provider identity

A mapped provider identity is provider-observed identity material that can be associated with a local Comms device record.

Mapping evidence may include:

    explicit local mapping created by prior user action;
    candidate import tied to a claimed device_id;
    local sidecar/device label cross-reference;
    future hardware-key enrollment record;
    future QR/in-person ceremony preflight;
    future recovery/re-enrollment metadata.

Mapping evidence does not equal verification.

### 4.2 Unmapped provider identity

An unmapped provider identity has no safe association with a local Comms device record.

Unmapped identity material may become a candidate.

It must not mutate existing trusted device records.

### 4.3 Identity mismatch

Identity mismatch means observed provider identity material does not match the currently expected material for a mapped local device.

Examples:

    fingerprint differs;
    public identity material differs;
    KeyPackage/bundle material implies a different identity;
    provider event explicitly reports identity changed;
    reverify-required event is associated with a mapped device.

## 5. Case matrix

### 5.1 No known mapping

Input:

    provider identity observed;
    no local device mapping exists.

Behavior:

    record candidate later;
    optionally append provider_identity_candidate_observed later;
    do not mutate trust.json;
    do not mark any known device changed;
    do not verify identity;
    strict mature send remains blocked until verification.

Classification:

    candidate-only / history-only.

### 5.2 Known unverified device, same material

Input:

    mapped unverified device;
    provider material matches existing unverified material.

Behavior:

    optionally append continuity observation later;
    keep unverified;
    do not verify automatically.

Classification:

    continuity observation.

### 5.3 Known unverified device, different material

Input:

    mapped unverified device;
    provider material differs.

Behavior:

    record conflict;
    require review;
    strict send blocks;
    do not silently replace material;
    do not verify.

Classification:

    review-required conflict.

### 5.4 Known verified device, same material

Input:

    mapped verified device;
    provider material matches expected identity.

Behavior:

    do not mutate trust.json;
    optionally append continuity history only if useful;
    allow send under existing verified policy.

Classification:

    continuity observation.

### 5.5 Known verified device, different material

Input:

    mapped verified device;
    provider material differs.

Behavior:

    append provider_identity_candidate_conflict or provider_identity_changed later;
    warn loudly;
    require re-verification;
    strict send blocks;
    later implementation may mark device changed if policy and mapping are explicit;
    do not replace verified material silently.

Classification:

    changed/reverify candidate.

### 5.6 Known changed device

Input:

    mapped device is already changed;
    additional provider mismatch arrives.

Behavior:

    append additional history if useful;
    preserve changed state;
    require reverify;
    strict send blocks.

Classification:

    changed continuity / repeated mismatch.

### 5.7 Known revoked device

Input:

    provider material maps to revoked device.

Behavior:

    block promotion;
    warn;
    append suspicious/revoked-device observation later if useful;
    do not un-revoke from provider observation.

Classification:

    blocked.

### 5.8 Known compromised-reserved device

Input:

    provider material maps to compromised-reserved state later.

Behavior:

    block promotion;
    warn;
    keep compromised behavior reserved until designed;
    no automatic recovery.

Classification:

    blocked / reserved.

## 6. Future event names

Candidate future trust-history event names:

    provider_identity_candidate_observed
    provider_identity_candidate_conflict
    provider_identity_continuity_observed
    provider_identity_mismatch_detected
    provider_identity_reverify_required
    provider_identity_changed_mapped
    provider_identity_promotion_blocked_revoked
    provider_identity_promotion_blocked_compromised

Important:

    device_key_changed should remain reserved for actual trust-state mutation to changed.
    device_verified should remain reserved for explicit verification ceremony.
    device_revoked should remain reserved for explicit revocation flow.

## 7. Future mutation rules

A future implementation may mutate trust.json only when all of these are true:

    provider identity material is mapped to a known local device;
    mismatch policy classifies the case as changed/reverify-required;
    the event is not merely an unmapped candidate;
    tests prove no verified identity is created from provider observation;
    tests prove send policy blocks changed/reverify states in strict mode;
    history is appended before or alongside mutation;
    user-visible warning/recovery path is defined.

v0.5.15 does not authorize implementation yet.

## 8. Send policy

Strict mature send should block when:

    device is unknown;
    device is unverified;
    device is changed;
    device is revoked;
    device is compromised-reserved;
    mapped provider mismatch is unresolved;
    provider reverify-required is unresolved;
    candidate identity conflict is unresolved.

Dev mode may allow override only with loud warning.

## 9. Candidate storage interaction

Candidate storage, if implemented later, should track mismatch state separately from verified trust state.

It should preserve:

    observed material;
    expected material fingerprint if known;
    conflict status;
    mapping evidence;
    source;
    observed_at;
    review status;
    reverify-required flag;
    note.

Candidate storage must not silently overwrite trust.json.

## 10. Trust-history interaction

Provider mismatch handling should append history before dangerous mutation.

Safe sequence for later implementation:

    observe provider material;
    produce provider report/draft;
    classify mapping/mismatch;
    append trust-history event;
    block or warn as policy requires;
    only later mutate trust.json if explicit mapped-mutation policy allows it.

## 11. Verification boundary

Re-verification may later return a changed device to verified state.

Re-verification must be explicit.

Possible ceremony types:

    manual fingerprint comparison;
    QR ceremony;
    hardware-key signed enrollment;
    in-person ceremony;
    recovery/re-enrollment.

Provider observation cannot complete re-verification by itself.

## 12. Cypher/server boundary

Cypher may deliver identity material or routing metadata.

Cypher cannot prove identity truth.

Cypher cannot authorize a key replacement.

Cypher cannot silently repair mismatch.

Server-delivered identity material must be treated as candidate/provenance, not trust.

## 13. Provider/sidecar boundary

Provider identity-changed and reverify-required events are security-relevant.

They are not automatically verified facts.

The sidecar can expose observations.

CarbonStackComms must decide local trust behavior using explicit mapping, history, and verification policy.
