# v0.5.10 provider-originated trust-history append plan

Status: planning record
Phase: v0.5.x provider-linkage implementation staging
Scope: ProviderTrustReport, ProviderTrustDecision, future trust-events.jsonl append semantics
Date: 2026-06-07 local session

## 1. Purpose

v0.5.10 defines how provider-originated trust/security observations may eventually become Comms trust-history events.

This is planning only.

v0.5.7 added an internal non-mutating ProviderTrustReport helper.
v0.5.8 clarified that structured JSON fields are the diagnostic source of truth and summaries are interpretive.
v0.5.9 kept the report helper internal-only and deferred CLI exposure.

v0.5.10 answers:

    which provider observations should eventually append trust history?
    which should block without appending?
    which should remain provider-only?
    what event names are needed?
    what source fields are needed?
    what should not mutate trust.json?
    what should be safe for a later append spike?

## 2. Non-implementation boundary

    trust-events.jsonl append from provider events;

    provider identity verification;
    provider-trust CLI exposure;
    mature UX;

## 4. Append principle

Provider-originated trust history should be append-only from the user/model perspective.

Future provider-originated append should happen only when an event affects trust, safety, recovery, identity continuity, group safety, or user-visible security history.

Do not append normal provider noise into trust-events.jsonl.

## 5. Provider event classes

### 5.1 Lifecycle

Examples:

    provider.fixture.started
    provider.fixture.completed
    provider.command.invalid
    provider.command.unsupported
    provider.command.not_implemented

Default append policy:

    no trust-events.jsonl append.

Reason:

    These are diagnostics or command lifecycle events, not user trust history.

Possible exception:

    repeated command invalid/unsupported may belong in a dev log, not trust history.

### 5.2 Public setup

Examples:

    provider.public_bundle.created
    provider.public_bundle.exported

Default append policy:

    no trust-events.jsonl append.

Possible future append:

    setup history may belong in a provider/setup history file, not trust-events.jsonl, unless a known device identity binding is involved.

Reason:

    KeyPackage/public bundle existence is not verification.

### 5.3 Membership

Examples:

    provider.conversation.created
    conversation.member_added
    conversation.joined
    conversation.loaded
    conversation.welcome.created

Default append policy:

    no device trust-events.jsonl append by default.

Possible future append:

    group membership history may need a separate group/conversation history domain.

Reason:

    group membership changes are important, but they are not necessarily device trust state transitions.

### 5.4 Message

Examples:

    message.protected
    message.opened

Default append policy:

    no trust-events.jsonl append for normal success.

Possible future append:

    message lifecycle belongs in a future message database or diagnostics log.

Important:

    successful message-open may justify ack.
    failed or blocked message-open must not ack.

### 5.5 Storage checkpoint

Examples:

    storage.missing
    storage.corrupt
    checkpoint.failed
    provider.identity.missing
    provider.identity.created
    provider.identity.loaded

Default append policy:

    normal loaded/saved/created: no trust-events.jsonl append.
    missing/corrupt/failed: append provider state safety event later.

Reason:

    missing/corrupt provider state can affect identity continuity and recovery safety.

### 5.6 Trust-security

Examples:

    provider.signature.invalid
    provider.identity.changed
    provider.identity.reverify.required
    provider.message.tamper.detected
    provider.replay.detected
    provider.epoch.stale

Default append policy:

    append trust/security history later.

Reason:

    These events affect security posture, warning/block behavior, or re-verification expectations.

### 5.7 Terminal-fatal

Examples:

    provider.fatal
    provider.state.inconsistent
    provider.group.unrecoverable
    provider.secret.material.unavailable
    provider.invariant.violation

Default append policy:

    append trust/security/recovery history later.

Reason:

    These events affect local state safety, recovery path, and user trust posture.

## 8. Append categories

### 8.1 No append

Do not append for:

    normal lifecycle events;
    normal public bundle creation/export;
    normal conversation loaded;
    normal identity loaded when expected;
    normal message protected;
    normal message opened;
    normal storage saved/loaded.

### 8.2 Append history only

Append history later, without trust.json mutation, for:

    provider_signature_invalid;
    provider_tamper_detected;
    provider_replay_detected;
    provider_epoch_stale;
    provider_state_missing;
    provider_state_corrupt;
    provider_checkpoint_failed;
    provider_secret_unavailable;
    provider_group_unrecoverable;
    provider_invariant_violation.

### 8.3 Append and require reverify

Append and require reverify later for:

    provider_identity_changed;
    provider_reverify_required.

If a Comms device mapping is known, these may later mark device trust as changed.

If no mapping is known, they should remain warning/history/recovery events and must not invent a verified mapping.

### 8.4 Append and possibly mutate trust later

Only after a separate implementation plan:

    mapped provider_identity_changed -> mark known device changed;
    mapped provider_reverify_required -> require reverify / changed state;
    explicit recovery flow -> recovery/re-enrollment event;
    explicit verification ceremony -> verified event.

v0.5.10 does not authorize implementation of this yet.

## 9. trust.json mutation boundary

Provider-originated append is not the same as trust-state mutation.

Future provider-originated trust-events.jsonl append may happen before trust.json mutation exists.

Do not mutate trust.json from:

    provider event observation alone;
    KeyPackage receipt alone;
    Welcome receipt alone;
    Cypher delivery alone;
    sidecar label alone;
    identity loaded alone;
    message opened alone.

Possible future trust.json mutation requires:

    explicit verification;
    explicit revocation;
    explicit recovery/re-enrollment;
    mapped identity mismatch policy;
    mapped reverify-required policy.

## 10. Ack boundary

No provider-originated trust-history work should weaken ack policy.

Rules:

    retrieval is not enough;
    artifact write is not enough;
    report generation is not enough;
    trust-history append is not enough;
    sidecar message-open success is required before ack.

If provider report indicates:

    blocks_open;
    quarantine_message;
    replay_detected;
    tamper_detected;
    stale_epoch;
    signature_invalid;
    group_unrecoverable;
    secret_unavailable;

then ack must not happen unless a later explicit policy defines a safe negative-ack/quarantine acknowledgement mechanism.

## 11. First append spike eligibility

Recommended later implementation:

    v0.5.11 provider-originated trust-history append spike

Scope should be narrow:

    add conversion helper from ProviderTrustReport to proposed trust event draft;
    add tests;
    maybe append only for a tiny allowlist of provider security events;
    no trust.json mutation;
    no provider identity import;
    no CLI exposure unless still needed;
    no ack behavior changes.

Candidate first allowlist:

    provider.identity.changed
    provider.signature.invalid
    provider.message.tamper.detected
    provider.replay.detected
    provider.secret.material.unavailable

Reason:

    These are clearly security-relevant and user-visible.
