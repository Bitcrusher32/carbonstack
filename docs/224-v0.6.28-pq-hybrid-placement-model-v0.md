# CarbonStack v0.6.28 PQ/Hybrid Placement Model v0

Status: docs/model checkpoint after v0.6.28A state-model review and PQ/hybrid placement recon.

Scope: PQ/hybrid placement model, state tags, migration posture, compatibility posture, recovery implications, experiment boundaries, and future implementation gates.

This document is not an implementation.

This document does not add PQ.

This document does not add hybrid encryption.

This document does not mutate OpenMLS ciphersuites.

This document does not change HPKE, KEM, credential, or signature behavior.

This document does not claim quantum-safe messaging.

This document does not claim production secure messaging.

This document does not claim hostile-server safety.

---

## 1. Purpose

v0.6.28A performed a broad PQ/hybrid placement recon after the v0.6.27 state/security/no-silent model.

The recon confirmed that PQ/hybrid work cannot safely start as implementation.

It must first define:

- attachment layer;
- state tags;
- migration epoch;
- backup/restore implications;
- compatibility/refusal rules;
- no-silent upgrade/downgrade behavior;
- claim boundaries;
- experiment boundaries.

This document defines that model.

The main result is:

    PQ/hybrid is not added to mainline in v0.6.x.

    The default future posture is new-conversation-only or new-protocol-epoch.

    Existing conversations must not silently become PQ/hybrid.

    PQ-tagged or upgraded state must not silently downgrade.

    Outer-envelope experiments may be useful but do not make the OpenMLS group itself PQ-secure.

    Credential/signature PQ belongs behind a future identity/trust model.

    First PQ experiments must happen in isolated branch/workdir contexts and must not mutate mainline claims.

PQ/hybrid work adds algorithm and migration pressure to these rules.

It does not weaken them.

## 4. Threat claims and nonclaims

PQ/hybrid work is often discussed as one thing, but CarbonStack must keep threat claims separate.

| Threat / goal | Meaning | Current v0.6.28 posture |
|---|---|---|
| Harvest-now-decrypt-later resistance | Reduce future decryption risk if traffic is stored now and cryptographic primitives break later | Model only; no claim |
| OpenMLS group secret PQ protection | PQ/hybrid protection inside MLS group secret establishment or related protocol layer | Model only; no implementation |
| Credential/signature PQ protection | PQ/hybrid identity credential or signature posture | Deferred behind identity/trust model |
| Outer transport protection | Additional wrapper around payloads/envelopes outside OpenMLS | Possible future experiment; not OpenMLS-level PQ |
| Malicious relay resistance | Server/relay cannot force unsafe acceptance, downgrade, replay, or identity claims | Requires adversarial harness later |
| Server compromise resistance | Server-side compromise does not expose plaintext or silently mutate trust | Not claimed |
| Local disk compromise resistance | Local state is protected from disk attacker | Not claimed; needs vault/security implementation |
| Endpoint compromise resistance | Device compromise is resisted | Not claimed |
| Migration/downgrade safety | Old/new algorithm states do not silently mix or downgrade | Model requirement only |

Do not collapse these claims.

Passing one future experiment must not create broad PQ/security language.

## 5. Placement options

v0.6.28A identified five useful placement options.

### Option A: OpenMLS-native / ciphersuite layer

Attach PQ/hybrid inside the MLS/OpenMLS layer, such as:

- MLS ciphersuite;
- HPKE/KEM layer;
- OpenMLS provider behavior;
- credential layer;
- signature layer.

Benefits:

- closest to real protocol-level PQ/hybrid semantics;
- best aligned with actual group-secret protection;
- avoids pretending that an outer wrapper changes MLS internals.

Risks:

- depends on upstream OpenMLS support;
- likely affects provider state format;
- likely affects ciphersuite negotiation;
- affects credentials and signatures;
- affects recovery and backup;
- may require migration epoch design;
- not a casual local patch.

Current posture:

    long-term honest direction;
    not first mainline implementation path;
    model only until upstream and migration realities are clearer.

### Option B: Outer envelope / transport layer

Attach PQ/hybrid-like metadata or protection outside OpenMLS, such as:

- new content type;
- new protocol version;
- hybrid envelope wrapper;
- outer payload protection;
- algorithm metadata around a ciphertext artifact.

Benefits:

- lower integration blast radius;
- easier to experiment with existing envelope metadata;
- easier to tag/refuse/route in current Comms/Cypher surfaces;
- useful for learning migration and compatibility behavior.

Risks:

- does not make MLS group secrets PQ-secure;
- can create misleading quantum-safe claims;
- may protect only an outer layer;
- may not address group membership, credentials, or signatures;
- can become theatre if wording is sloppy.

Current posture:

    acceptable future experiment only with hard nonclaims;
    must not be described as OpenMLS-level PQ security.

### Option C: New-conversation-only / new protocol epoch

Treat PQ/hybrid as a property of a new conversation or new protocol epoch.

Existing conversations remain old-mode.

PQ/hybrid-tagged conversations are created explicitly.

Benefits:

- strongest no-silent posture;
- avoids mixed old/new state ambiguity;
- avoids fake in-place migration;
- makes backup/restore easier to reason about;
- allows compatibility refusal to be explicit.

Risks:

- requires user/operator migration UX later;
- requires state tags;
- requires compatibility matrix;
- may create parallel conversations during transition;
- does not solve old conversation protection retroactively.

Current posture:

    recommended default future model.

### Option D: Identity credential / signature layer

Attach PQ/hybrid work to identity credentials, trust proofs, or signatures.

Benefits:

- important for long-term identity authenticity;
- may eventually support stronger trust continuity;
- aligns with future verified identity direction.

Risks:

- current verified identity is a nonclaim;
- trust/candidate state is not fully wired into send/receive policy;
- implementing this early would overclaim;
- credential/signature PQ without enrollment/trust UX is misleading.

Current posture:

    future dependency;
    not near-term mainline implementation;
    possible late-v0.7.x experiment after identity/trust boundaries are clearer.

### Option E: isolated branch/workdir experiment

Use a separate branch or workdir for learning-focused experiments.

Benefits:

- allows experimentation without mutating mainline claims;
- allows testing tags/refusals/compatibility behavior;
- allows research into outer wrapper or identity-layer options;
- keeps unstable code out of release surfaces.

Risks:

- experiment drift;
- false confidence;
- accidental merge before model gates;
- unreviewed claim expansion.

Current posture:

    acceptable in late v0.7.x after this placement model;
    not a v0.6.x mainline implementation;
    not a security claim.

## 6. Rejected shortcuts

The following shortcuts are rejected by default.

### Shortcut 1: “Just add PQ”

Rejected.

PQ/hybrid requires:

- layer clarity;
- state tagging;
- migration epoch;
- compatibility rules;
- backup/restore rules;
- refusal behavior;
- claim boundaries.

### Shortcut 2: outer wrapper equals quantum-safe messaging

Rejected.

An outer wrapper may be useful, but it does not automatically protect MLS group secrets, credentials, membership, or signatures.

### Shortcut 3: silent in-place upgrade

Rejected.

Existing conversations must not silently become PQ/hybrid.

### Shortcut 4: silent downgrade

Rejected.

Once a conversation or state root is tagged as PQ/hybrid or newer-epoch, older-only clients must not silently proceed as if no downgrade occurred.

### Shortcut 5: credential/signature PQ before identity model

Rejected.

Current identity verification remains a nonclaim.

Credential/signature PQ must wait for stronger identity/trust/enrollment semantics.

### Shortcut 6: schema-first PQ

Rejected.

Cypher schema should not be changed for PQ before the model defines which metadata is required and which layer owns the claim.

## 7. Recommended default posture

The v0.6.28 default posture is:

    PQ/hybrid is model-only in v0.6.x.

    PQ/hybrid should default to new-conversation-only or new-protocol-epoch in future implementation.

    Existing conversations stay old-mode unless an explicit future migration design exists.

    No state silently upgrades.

    No state silently downgrades.

    No backup silently overwrites newer or different algorithm state.

    Outer-envelope experiments are allowed only as nonclaiming experiments.

    OpenMLS-native / ciphersuite-layer support is the honest long-term direction for protocol-level PQ/hybrid.

    Credential/signature PQ waits for future identity/trust modeling.

    First PQ experiments belong in isolated branch/workdir contexts during late v0.7.x.

    A more mature implementation attempt belongs near early v0.8.x after experiments and model review.

## 8. Required state tags and algorithm metadata

Future PQ/hybrid work requires durable algorithm context.

At minimum, future designs should consider tags for:

- conversation algorithm mode;
- protocol epoch;
- PQ/hybrid mode;
- OpenMLS ciphersuite identifier;
- outer envelope algorithm identifier, if any;
- credential/signature algorithm family;
- migration state;
- migration ID;
- migration timestamp;
- backup compatibility version;
- downgrade refusal marker;
- client capability marker;
- creation mode:
  - legacy;
  - classical-only;
  - outer-wrapper-experimental;
  - hybrid-experimental;
  - OpenMLS-native-PQ-if-ever-supported.

These tags must not be cosmetic.

They must affect refusal behavior, compatibility checks, backup/restore, and operator warnings.

## 9. Migration epoch and no-silent rules

PQ/hybrid creates migration risk even before implementation.

Future migration must obey the v0.6.27 no-silent rules.

### 9.1 No silent upgrade

Existing conversations must not silently become PQ/hybrid.

Allowed future paths:

- create a new PQ/hybrid-tagged conversation;
- explicitly migrate with visible operator/user action;
- explicitly mark legacy conversations as legacy;
- explicitly refuse if client capabilities are incompatible.

Forbidden:

- silently changing algorithm mode on existing conversation state;
- silently wrapping old ciphertext and claiming PQ;
- silently changing trust/credential behavior;
- silently changing backup compatibility.

### 9.2 No silent downgrade

Once a state root, conversation, or backup is tagged with a newer PQ/hybrid epoch, old-mode clients must not silently proceed.

Correct behavior should be one of:

- refuse;
- warn and refuse;
- require explicit compatibility mode;
- require explicit recovery/migration path.

Forbidden:

- silently treating PQ-tagged state as classical-only;
- silently stripping algorithm tags;
- silently accepting a stale pre-PQ backup over PQ-tagged state;
- silently accepting mixed old/new state.

### 9.3 No silent mixed mode

Mixed conversations must be either explicitly modeled or refused.

If mixed mode is allowed later, it must define:

- who is classical-only;
- who is hybrid-capable;
- what each member can read;
- what each member can send;
- what guarantees are not granted;
- how migration/rollback works.

Until then:

    mixed mode is refused by default.

## 10. Backup, restore, and recovery implications

PQ/hybrid changes backup and recovery semantics.

Future backup metadata must include enough algorithm context to prevent silent rollback or downgrade.

### 10.1 Backup manifest requirements

Future backup manifests should include:

- backup format version;
- state model version;
- algorithm mode;
- protocol epoch;
- conversation IDs/labels;
- device identity binding;
- credential/signature algorithm family;
- OpenMLS ciphersuite identifier, if relevant;
- outer wrapper algorithm identifier, if relevant;
- migration epoch;
- created timestamp;
- source instance/fingerprint where available.

### 10.2 Restore rules

Future restore must not:

- overwrite newer PQ-tagged state silently;
- restore old-mode state over PQ/hybrid state silently;
- restore PQ/hybrid state into old-only client mode silently;
- imply identity continuity silently;
- imply algorithm continuity silently.

Correct restore behavior should classify:

- fresh install restore;
- same-device restore;
- new-device restore;
- partial restore;
- stale backup;
- pre-migration backup;
- post-migration backup;
- wrong backup.

### 10.3 Recovery rules

Recovery must preserve:

- explicit algorithm mode;
- explicit migration state;
- explicit trust state;
- explicit refusal behavior;
- no ack/drain after failed cryptographic/state operations.

## 11. Compatibility and refusal matrix

Future implementations should define compatibility explicitly.

| State / client condition | Default behavior | Reason |
|---|---|---|
| Classical conversation opened by classical-capable client | Allow under existing nonclaims | Existing mode |
| Classical conversation opened by future PQ-capable client | Allow as legacy/classical mode with explicit label | No silent upgrade |
| PQ/hybrid-tagged conversation opened by old-only client | Refuse | No silent downgrade |
| PQ/hybrid-tagged conversation with missing algorithm tag | Refuse or recovery-required | Ambiguous state |
| Backup from classical state restored over PQ-tagged local state | Refuse or explicit recovery-required | Prevent rollback |
| PQ-tagged backup restored into old-only client | Refuse | Prevent downgrade |
| Mixed member capability without model | Refuse | Avoid fake compatibility |
| Outer-wrapper experimental conversation opened as OpenMLS-native PQ | Refuse / warn | Prevent false claim |
| Credential/signature PQ metadata without trust model | Treat as unverified / future dependency | Identity remains nonclaim |

## 12. Relay Space and Cypher coordination implications

Cypher is server-side coordination authority and delivery/routing authority.

Cypher is not:

- plaintext authority;
- verified identity authority;
- OpenMLS group-secret authority;
- PQ security authority.

Future PQ/hybrid metadata may eventually affect:

- envelope `content_type`;
- envelope `protocol_version`;
- algorithm/mode tags;
- capability markers;
- Relay Space compatibility labels;
- migration/refusal metadata;
- operator-readable warnings.

But Cypher schema must not be changed just because PQ exists as a concept.

Future Cypher/PQ changes need a model answering:

- which metadata belongs server-side;
- which metadata belongs local-only;
- which metadata is privacy-sensitive;
- which metadata can be lied about by a relay;
- which metadata is enforced by Comms;
- which metadata is only operator evidence.

Server-provided PQ metadata must not silently mutate local trust.

Relay Space membership must not imply PQ capability or verified identity.

---

## 13. Trust and identity implications

PQ/hybrid identity work is deferred behind stronger trust/enrollment modeling.

Current posture:

- verified sender identity remains a nonclaim;
- `from_device` and `sender_device_id` remain unverified relay metadata;
- `trust.json` and `identity-candidates.json` are safety-sensitive now;
- trust/candidate stores become runtime authority only once wired into send/receive/enrollment policy.

Future credential/signature PQ must define:

- how identity credentials are generated;
- how they are distributed;
- how they are verified;
- how they are rotated;
- how they are revoked;
- how stale identity material is refused;
- how backup/restore affects identity continuity;
- how peer-visible continuity is proven or explicitly not proven.

Do not implement credential/signature PQ before this model exists.

## 14. Experimental branch/workdir rules

PQ experiments are allowed only after this placement model is accepted.

First experiments should happen in:

- isolated branch;
- isolated workdir;
- no release package;
- no public release;
- no `full`;
- no `release-snapshot`;
- no registry promotion unless a later design explicitly adds an experimental command surface.

Experiment output must state:

- what layer was touched;
- what was not touched;
- whether OpenMLS group secrets were affected;
- whether identity credentials were affected;
- whether Cypher schema was affected;
- whether backup/restore was affected;
- whether migration was affected;
- what claims are still forbidden.

Late v0.7.x may carry Option E/D experiments.

Early v0.8.x may attempt a more mature implementation shape after:

- experiment results exist;
- state tags are defined;
- compatibility rules are defined;
- backup/restore implications are defined;
- migration/refusal behavior is defined;
- operator warnings are defined.

- recovery model;

## 18. Summary

The v0.6.28 PQ/hybrid placement position is:

    PQ/hybrid must be modeled before it is implemented.

    PQ/hybrid must carry durable state tags and migration semantics.

    Existing conversations must not silently become PQ/hybrid.

    PQ-tagged state must not silently downgrade.

    Outer-envelope experiments can be useful but must not claim OpenMLS-level PQ security.

    Protocol-level PQ/hybrid belongs at the OpenMLS/ciphersuite/HPKE/KEM/credential/signature layer when support and migration reality allow.

    Credential/signature PQ belongs behind future identity/trust modeling.

    Experiments belong in isolated branch/workdir contexts.

    No v0.6.x work may claim quantum-safe messaging.
