# v0.5.5 trust-state model

Status: planning model
Phase: v0.5.x state correctness and persistence planning
Scope: CarbonStackComms trust state, OpenMLS provider identity linkage, future vault and UX boundary
Date: 2026-06-07 local session

## 1. Purpose

v0.5.5 defines the CarbonStack trust-state model.

v0.5.2 identified state-bearing islands.
v0.5.3 inventoried state domains.
v0.5.4 defined storage domains.

v0.5.5 answers:

    what does each trust state mean?
    when should sending warn or block?
    what must be visible to the user?
    what trust events must persist?
    how should provider identity changes eventually map into Comms trust?
    what remains dev-only today?

This document is still a planning model.

It does not implement:

    provider-state linkage;
    real OpenMLS trust import;
    secure vault storage;
    mature send/inbox UX;
    Relay Space join;
    local-backbone;
    PQ/hybrid ciphersuites;
    hostile-server safety.

## 2. Current trust implementation baseline

Current Comms trust code lives in:

    carbonstack-comms/internal/trust/trust.go
    carbonstack-comms/internal/trust/trust_test.go

Current local trust files:

    .carbonstack-comms/trust.json
    .carbonstack-comms/trust-events.jsonl

Current trust states in code:

    unknown
    unverified
    verified
    changed
    revoked
    compromised

Current event types in code:

    device_verified
    device_key_changed
    device_revoked

Current trust commands:

    fingerprint
    verify-device
    trust-history
    trust-list
    simulate-key-change
    revoke-device

Current send behavior:

    dev mode warns and allows unknown/unverified/changed devices;
    strict mode blocks unknown/unverified/changed devices;
    verified devices are allowed;
    revoked and compromised devices block.

Important current limitation:

    Fingerprints are currently development fingerprints derived from public identity key strings.
    They are not a production safety-number system.

## 3. Trust-state definitions

### 3.1 unknown

Meaning:

    The local client has no trust record for the target device.

Typical sources:

    first contact;
    device record fetched from Cypher but not verified locally;
    OpenMLS runtime dev send to a device ID with no local trust record;
    missing trust store entry.

Current behavior:

    dev mode may warn and allow;
    strict mode blocks.

Mature behavior:

    should block by default for sensitive send paths;
    should require verification or explicit unsafe override;
    should display as unknown / not verified.

Required UX:

    loud warning before send;
    no silent promotion to verified;
    no server-trusted identity acceptance.

Provider linkage:

    provider identity observed without local verification should map conceptually to unknown or unverified, not verified.

### 3.2 unverified

Meaning:

    The local client has seen or recorded a device identity, but the user has not completed a verification ceremony.

Typical sources:

    future automatic observation of provider/device identity;
    future contact import;
    future bootstrap flow that records a candidate identity but does not verify it.

Current behavior:

    code has the state constant;
    current flows mostly create verified records through explicit verify-device;
    strict mode blocks unverified.

Mature behavior:

    should block by default for high-trust send paths;
    may allow explicit unsafe/dev override only with warning;
    should be visually distinct from verified.

Required UX:

    display fingerprint/safety-number material;
    prompt verification;
    explain that the server cannot make this safe.

Provider linkage:

    provider identity imported but not user-verified should become unverified unless the import path is explicitly a verified ceremony.

### 3.3 verified

Meaning:

    The local user has accepted the device identity through an explicit verification action.

Typical sources:

    current verify-device command;
    future QR / hardware-key / safety-number ceremony;
    future re-verification after key change or device recovery.

Current behavior:

    strict mode allows verified devices;
    trust.json records public identity key, fingerprint, label, and state;
    trust-events.jsonl records a device_verified event.

Mature behavior:

    verified should mean locally accepted identity, not server-approved identity.

Required UX:

    show stable verified identity state;
    preserve first-seen and last-seen metadata;
    show fingerprint/safety-number material;
    preserve history.

Provider linkage:

    provider identity matching an existing verified record should remain verified.
    provider identity mismatch must not silently remain verified.

### 3.4 changed

Meaning:

    A known device identity appears to have changed from the locally trusted record.

Typical sources:

    simulated key change today;
    future provider identity mismatch;
    future device replacement;
    future restore/re-enrollment event;
    possible malicious substitution.

Current behavior:

    simulate-key-change marks device changed;
    strict mode blocks changed;
    dev mode warns and may allow override;
    verify-device can reverify changed material.

Mature behavior:

    should block by default;
    should require re-verification;
    should preserve the old and new fingerprint/history where possible;
    should never be silently accepted.

Required UX:

    loud warning such as:

        This device identity changed. Reverify before trusting it.

    show old/new fingerprint where available;
    explain possible benign and hostile causes.

Provider linkage:

    provider.identity.changed or equivalent mismatch should map to changed or reverify-required behavior.

### 3.5 revoked

Meaning:

    The device has been explicitly removed from the local trust set or marked as no longer acceptable.

Typical sources:

    current revoke-device command;
    future signed revocation;
    future group/device removal;
    future compromise recovery.

Current behavior:

    revoked blocks even in dev mode;
    trust-events.jsonl records a device_revoked event.

Mature behavior:

    revoked should remain blocked unless a deliberate re-enrollment flow creates a new identity record.

Required UX:

    show revoked state clearly;
    block send/open actions where appropriate;
    explain that re-adding the device requires a new verification ceremony.

Provider linkage:

    server/device records must not silently undo local revocation.

### 3.6 compromised

Meaning:

    Reserved state for a device or identity believed to be compromised.

Current behavior:

    code defines the state;
    current tested flows do not meaningfully exercise compromised.

Mature behavior:

    should block by default;
    should require recovery/re-enrollment path, not simple reverify;
    may imply wider group or identity hygiene actions.

Required UX:

    severe warning;
    recovery guidance;
    no quiet downgrade to changed/unverified.

Current v0.5.5 policy:

    keep compromised reserved.
    Do not pretend it is fully implemented.

Provider linkage:

    terminal/fatal trust-security provider events may eventually produce compromised or re-enrollment-required behavior, but this must be designed separately.

## 4. Trust-state transition model

Current and future conceptual transitions:

| From | To | Source | Current? | Notes |
|---|---|---|---|---|
| none | unknown | no local record | yes | implicit lookup result, not stored transition |
| unknown | verified | verify-device | yes | current manual verification path |
| unverified | verified | verify-device / future ceremony | partly | state exists; most current flows skip unverified |
| verified | changed | simulate-key-change / future provider mismatch | yes / future | must be loud |
| changed | verified | verify-device after recheck | yes | reverify path exists |
| verified/changed/unverified | revoked | revoke-device / future revocation | yes / future | must block |
| any | compromised | future compromise detection | reserved | not currently meaningful |
| revoked | verified | new enrollment ceremony only | future | should not be ordinary verify over same record without policy |
| compromised | verified | recovery/re-enrollment only | future | should be stricter than changed -> verified |

## 5. Send policy model

### 5.1 Current dev/strict behavior

Current behavior should remain described as dev/pre-alpha:

| Trust state | Dev mode | Strict mode |
|---|---|---|
| unknown | warn + allow | block |
| unverified | warn + allow | block |
| verified | allow | allow |
| changed | warn + allow | block |
| revoked | block | block |
| compromised | block | block |

### 5.2 Mature default target

Mature default should be stricter than dev mode:

| Trust state | Mature default target |
|---|---|
| unknown | block unless explicit unsafe override exists |
| unverified | block or require explicit unsafe override |
| verified | allow |
| changed | block until reverified |
| revoked | block |
| compromised | block and require recovery/re-enrollment |

v0.5.5 does not implement this mature mode.

## 6. Trust event model

Trust events should be append-only from the user/model perspective, even if the current JSONL file is not cryptographically protected yet.

Current event fields:

    event_id
    event_type
    account_id
    device_id
    previous_trust_state
    new_trust_state
    fingerprint
    event_time
    source
    note

Current event types:

    device_verified
    device_key_changed
    device_revoked

Future event types likely needed:

    device_observed
    provider_identity_changed
    provider_identity_missing
    provider_identity_recovered
    device_compromised
    device_reenrolled
    trust_store_recovered
    trust_store_imported
    trust_store_exported
    ciphersuite_changed
    group_reinit_required

Rules:

    trust history must survive restart;
    trust history loss should become loud;
    verification, key change, revocation, compromise, and recovery should be recorded;
    provider-originated trust events should be distinguishable from manual user actions.

## 7. Provider identity linkage model

Current boundary:

    OpenMLS bootstrap wrappers do not mutate Comms trust state.
    Sidecar provider state is separate from Comms trust state.
    Provider event descriptors can classify trust-relevant events, but they do not execute user-facing trust policy.

Future linkage should be explicit:

    provider identity observed -> unknown/unverified unless verified by ceremony;
    provider identity matches verified record -> no warning;
    provider identity mismatches verified record -> changed / reverify-required;
    provider trust-security event -> loud warning or block depending severity;
    provider terminal-fatal event involving secret/group state -> block and require recovery plan;
    provider membership change -> append history and warn where group trust changes.

Do not let Cypher or the server decide any of these trust transitions.

## 8. Display model

Trust display should include:

    device label;
    device ID;
    account ID where meaningful;
    trust state;
    fingerprint / safety number material;
    first seen time;
    last seen time;
    latest relevant event;
    warning text for unknown/unverified/changed/revoked/compromised.

Future display should distinguish:

    server-reported device ID;
    locally verified identity key;
    provider sidecar identity label;
    group/conversation membership state;
    ciphersuite/protocol version when it affects trust.

## 9. Reverification model

Reverification is appropriate for:

    unknown -> verified;
    unverified -> verified;
    changed -> verified after user confirms new identity.

Reverification is not enough by itself for:

    revoked -> verified;
    compromised -> verified;
    group state rollback;
    provider storage replacement;
    suspicious recovery from missing signer/provider storage.

Those require explicit recovery/re-enrollment policy later.

## 10. Local storage and vault implications

Trust state belongs to the local-trust-state domain from docs/170.

Trust files:

    must survive restart;
    must not silently regenerate;
    should eventually be protected by the vault or authenticated storage;
    must eventually have migration/tamper/recovery behavior.

Current trust files are useful dev scaffolding, not production secure vault storage.

## 11. PQ / ciphersuite implications

PQ/hybrid ciphersuite work must include trust-state implications:

    ciphersuite choice should be visible in state/docs/validation;
    ciphersuite migration may require group reinit/rekey;
    KeyPackage/Welcome compatibility changes should not appear as ordinary harmless churn;
    trust display should not claim quantum safety from one successful test;
    migration should generate explicit trust/history records where user safety changes.
