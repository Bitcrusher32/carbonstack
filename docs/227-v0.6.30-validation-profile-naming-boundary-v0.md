# CarbonStack v0.6.30 Validation Profile Naming Boundary v0

Status: docs/model checkpoint after v0.6.30A validation profile naming preflight.

Scope: validation profile naming, release-package validation boundary, live-dev runtime aggregation boundary, compatibility naming, and future alias/profile gates.

This document is not an implementation.

This document does not add a runner profile.

This document does not add an alias.

This document does not change `full`.

This document does not change `release-snapshot`.

This document does not add `full-runtime-dev`.

This document does not claim production security, deployment readiness, or hostile-server safety.

---

## 1. Purpose

v0.6.30A inspected the current validation/profile naming surface after the v0.6.29 bounded state-substrate checkpoint.

The problem is not that validation is missing.

The problem is that validation names can silently overclaim.

Current CarbonStack has:

- release-package validation;
- package-root/layout/checksum/core validation;
- Cypher-only local lifecycle validation;
- live-umbrella OpenMLS runtime validation;
- live-umbrella integrated runtime validation;
- same-state positive and failure-hardening profiles;
- non-mutating state-boundary inventory through `state-audit-dev`.

These are not the same thing.

This document defines what each major validation name means and what it must never imply.

---

## 2. Current naming facts

### 2.1 `full`

Current command:

    go run . --profile full

Current meaning:

    release-package validation ladder

Current known composition:

    release-snapshot
    local-cypher

Current nonclaims:

- not deployment;
- not local-backbone;
- not runtime Comms UX;
- not production security proof.

`full` is therefore not a full system security proof.

It is not live-dev runtime aggregation.

It is not hostile-server validation.

It is not deployability validation.

It is not production readiness.

### 2.2 `release-snapshot`

Current command:

    go run . --profile release-snapshot

Current meaning:

    package-root validation component

It validates release-like package root properties such as:

- required files;
- release metadata;
- checksums;
- forbidden generated/private/build artifacts;
- then core validation.

It does not:

- package releases;
- upload releases;
- deploy;
- prove runtime Comms UX;
- prove live integrated runtime;
- prove production security.

### 2.3 `integrated-runtime-dev`

Current command:

    go run . --profile integrated-runtime-dev

Current meaning:

    live-umbrella integrated runtime-dev composition

It composes Relay onboarding proof and wrapper normal-message runtime proof.

It is explicitly:

- not included in `full`;
- not included in `release-snapshot`;
- not release-package validation;
- not package-root validation;
- not production secure messaging;
- not production E2EE;
- not hostile-server safety;
- not metadata privacy;
- not identity verification;
- not secure enrollment;
- not local-backbone;
- not deployment;
- not mature messenger UX.

### 2.4 Same-state profiles

Same-state profiles are live-umbrella dev/pre-alpha validation profiles.

They are not:

- `full`;
- `release-snapshot`;
- package-root validation;
- release validation;
- hostile-server proof;
- production security proof.

They prove case-specific dev/pre-alpha behavior.

### 2.5 `state-audit-dev`

Current command:

    go run ./cmd/comms state-audit-dev

Current meaning:

    non-mutating local state-domain inventory / proto-substrate surface

It is not:

- vault encryption;
- production key storage;
- recovery;
- deletion or cleanup;
- trust verification;
- local-backbone;
- production secure messaging.

`state-audit-dev` may become a future input to `full-runtime-dev`.

It must not be added to `full` or `release-snapshot` by default.

## 3. Naming contract

### 3.1 `full`

Contract:

    `full` remains the compatibility name for the existing release-package validation ladder through v0.7.0.

Current meaning:

    release-snapshot + local-cypher

Allowed:

- keep working as-is;
- remain documented as release-package validation;
- eventually emit a compatibility note after `full-validate-release` exists.

Forbidden:

- silently add live-dev runtime profiles;
- silently add same-state profiles;
- silently add `state-audit-dev`;
- silently add adversarial harness profiles;
- silently change package-root assumptions;
- silently become production/deployment/security validation.

Deprecation posture:

    Do not mark `full` deprecated yet.

Rationale:

`full` is known and useful. Breaking or warning too aggressively before an explicit replacement exists would create operator confusion. However, it must stop being the preferred long-term name because it sounds broader than what it proves.

### 3.2 `full-validate-release`

Contract:

    `full-validate-release` is the preferred explicit future name for release/package-root validation.

Intended meaning:

    exact alias to current `full` behavior at first

Allowed future implementation:

- add runner alias/profile name;
- route to current `full` behavior;
- update registry and generated command reference;
- document `full` as compatibility name;
- optionally print a compatibility note from `full`.

Forbidden:

- changing validation semantics while adding the name;
- adding live-dev profiles;
- adding state-substrate checks;
- adding adversarial harness checks;
- implying production security.

Implementation posture:

    Safe candidate for optional v0.6.30C if the docs model is accepted.

### 3.3 `release-snapshot`

Contract:

    `release-snapshot` remains package-root/layout/checksum/core validation.

Allowed:

- keep as component of `full` / future `full-validate-release`;
- keep strict package-root artifact hygiene;
- keep checksum and metadata behavior.

Forbidden:

- adding live-dev runtime assumptions;
- adding same-state profiles;
- adding `state-audit-dev`;
- becoming deployment validation;
- becoming production security validation.

### 3.4 `full-runtime-dev`

Contract:

    `full-runtime-dev` is future-only for now.

Intended future meaning:

    live-umbrella runtime-dev aggregation

Candidate future inputs:

- `integrated-runtime-dev`;
- `same-state-integrated-dev`;
- selected same-state normal-message failure profiles;
- `state-audit-dev`;
- possibly focused Relay/onboarding checks after explicit decision.

Forbidden:

- package-root release validation;
- replacing `full`;
- replacing `release-snapshot`;
- implying production/deployment/security readiness;
- silent membership growth without a model/contract.

Implementation posture:

    Do not implement in v0.6.30 by default.

Rationale:

`full-runtime-dev` is useful but higher risk than `full-validate-release`, because its member set defines what “runtime-dev aggregation” means. That must not happen accidentally.

### 3.5 `integrated-runtime-dev`

Contract:

    `integrated-runtime-dev` remains the highest current live-dev aggregate until `full-runtime-dev` is deliberately created.

Allowed:

- remain callable;
- remain live-umbrella only;
- remain excluded from `full` and `release-snapshot`;
- remain a future `full-runtime-dev` input candidate.

Forbidden:

- treating it as package-root validation;
- folding it into `full` silently;
- treating it as production secure messaging.

### 3.6 Same-state profiles

Contract:

    same-state profiles remain leaf or focused live-dev profiles.

Allowed:

- remain individually callable;
- remain deterministic failure-hardening evidence;
- become future `full-runtime-dev` inputs after explicit selection.

Forbidden:

- adding them to `full`;
- adding them to `release-snapshot`;
- claiming hostile-server safety;
- claiming replay safety beyond case-specific classification;
- claiming package-root validation.

## 4. Future implementation gates

### 4.1 `full-validate-release` alias gate

Before implementation:

- this document must be accepted;
- runner alias behavior must be exact;
- registry row must be added or updated;
- generated command reference must be regenerated/checked;
- tests must prove `full` and `full-validate-release` share behavior;
- docs must state that `full` remains compatibility name.

The first implementation must not change validation semantics.

### 4.2 `full` compatibility-note gate

A future note from `full` is allowed only after `full-validate-release` exists.

Acceptable wording:

    note: `full` is the compatibility name for release-package validation; prefer `full-validate-release` for explicit release validation.

Forbidden wording:

    deprecated
    insecure
    full system validation
    production validation

### 4.3 `full-runtime-dev` creation gate

Before implementation:

- member profiles must be explicitly selected;
- each member profile must preserve its own nonclaims;
- aggregate failure behavior must be defined;
- generated artifact cleanup behavior must be defined;
- state-audit inclusion must be decided;
- registry and generated reference must be updated;
- docs must state it is not package-root validation.

Do not implement `full-runtime-dev` as part of the first alias patch.

## 5. Validation proof expectations

### 5.1 Docs/model checkpoint proof

For this v0.6.30B docs checkpoint, proof means:

- document exists;
- docs README references it;
- generated command reference remains unchanged/current;
- runner tests pass;
- registry missing-nonclaims scan passes;
- no registry/reference/runner mutation occurs.

### 5.2 Future alias implementation proof

If v0.6.30C implements `full-validate-release`, proof should include:

- `go run . --profile full-validate-release` works;
- it executes the same behavior as `full`;
- `full` still works;
- no live-dev profile is added to release validation;
- registry has entries for both names;
- generated command reference is current;
- runner tests pass.

### 5.3 Future runtime-dev aggregate proof

If `full-runtime-dev` is created later, proof should include:

- exact member list;
- exact run order;
- generated artifact cleanup rules;
- state-audit inclusion decision;
- no package-root release claims;
- no production/security/deployment claims;
- explicit failure semantics.

## 6. Relationship to adversarial harness contract

The adversarial harness contract/evidence matrix comes after this naming model.

Reason:

A harness contract must distinguish:

- release-package validation;
- live-dev runtime validation;
- deterministic failure-hardening profiles;
- adversarial case families;
- hostile-server claims;
- state-substrate checks.

Without naming boundaries, a harness profile could be accidentally interpreted as a global security proof.

v0.6.x should design the harness contract.

It should not claim hostile-server safety.

It should not start with one mega-profile.

---

## 7. Relationship to v0.7.0 release prep

v0.7.0 release prep should happen after:

- validation naming boundary;
- optional `full-validate-release` alias decision;
- adversarial harness contract/evidence matrix;
- package-root rehearsal plan;
- claim-boundary review;
- source hygiene review;
- public page wording review.

v0.7.0 should remain a cumulative pre-alpha engineering release boundary.

It must not be framed as production, secure-use, hostile-server-safe, or general-public ready.

## 8. Current decisions

v0.6.30B records the following decisions:

1. `full` remains a compatibility name for release-package validation through v0.7.0.

2. `full-validate-release` is the preferred explicit future name for that same release/package-root validation meaning.

3. `full` should not emit a compatibility note until `full-validate-release` exists.

4. `full` should not be marked deprecated yet.

5. `full-runtime-dev` is future-only for now.

6. `integrated-runtime-dev` remains the highest current live-dev aggregate.

7. Same-state profiles remain live-umbrella dev evidence.

8. `state-audit-dev` is a future `full-runtime-dev` candidate only.

9. No live-dev profile is added to `full` or `release-snapshot` by this checkpoint.

10. No runner implementation happens in this checkpoint.

## 9. Done means

This model is done when it establishes:

- what `full` currently means;
- what `full-validate-release` should mean;
- what `release-snapshot` must remain;
- what `full-runtime-dev` should eventually mean;
- why `full-runtime-dev` is not implemented yet;
- why live-dev profiles stay out of release-package validation;
- where `state-audit-dev` may belong later;
- what the optional alias implementation may do;
- what it must not do.

This model does not solve:

- full alias implementation;
- runtime-dev aggregate implementation;
- adversarial harness contract;
- v0.7.0 release prep;
- production deployment;
- production security.

---

## 10. Summary

The v0.6.30 validation naming position is:

    full remains compatibility release-package validation through v0.7.0.

    full-validate-release is the preferred explicit future name for release/package-root validation.

    release-snapshot remains package-root validation.

    full-runtime-dev is future-only until its member set and semantics are deliberately modeled.

    integrated-runtime-dev remains the highest current live-dev aggregate.

    same-state profiles remain live-umbrella dev evidence.

    state-audit-dev is a future full-runtime-dev candidate, not a release validation input.

    No validation name should silently expand its claim surface.
