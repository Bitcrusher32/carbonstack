# CarbonStack v0.6.26 Load-Check Provider/Summary Output v0

Status: output/docs cleanup after v0.6.22 state-authority classification, v0.6.24 load-check semantic recon, and v0.6.26B output-semantics scout.

## Scope

This checkpoint clarifies `openmls-conversation-load-check-dev` output around provider reloadability and summary metadata presence.

It does not change message-open behavior.

It does not change ack/drain behavior.

It does not change provider-state behavior.

It does not make `conversation-summary.json` runtime authority for existing message-open.

## Background

Prior recon established:

    conversation-level provider-storage.json is runtime authority for existing normal message-open;
    final conversation directory is the runtime authority container;
    conversation-summary.json is metadata/evidence for existing message-open;
    message-inbox-dev can still open a valid queued message when provider storage is valid even if summary metadata is missing;
    conversation-load-check-dev is stricter than message-open when summary metadata is missing.

That mismatch is a command-semantics/output issue, not a no-ack/no-drain runtime bug.

## Output cleanup

Successful load-check output now distinguishes the relevant surfaces:

    group_reloadable: true
    provider_reloadable: true
    summary_metadata_present: true
    provider_storage_present: true
    summary_metadata_path: <path>
    provider_storage_path: <path>
    summary_metadata_warning: none

When summary metadata is missing, the command emits an explicit metadata-missing block before returning failure:

    status: metadata_missing
    group_reloadable: false
    provider_reloadable: not_evaluated_by_load_check
    summary_metadata_present: false
    provider_storage_present: true/false
    summary_metadata_warning: conversation-summary metadata is missing; conversation-load-check-dev is stricter than message-open and cannot confirm reloadability without summary metadata

## Interpretation

`provider_reloadable` means the load-check path successfully asked the OpenMLS sidecar to reload the conversation using its current load-check semantics.

`summary_metadata_present` means expected sidecar summary metadata is present for the load-check surface.

`provider_storage_present` means expected provider storage is present for the load-check surface.

`provider_reloadable: not_evaluated_by_load_check` means this command did not prove reloadability, usually because required summary metadata was missing before the sidecar load-check could complete.

This preserves the current model:

    provider storage is runtime authority for existing message-open;
    summary metadata is evidence/metadata;
    load-check is allowed to be stricter than message-open, but must say so clearly.
