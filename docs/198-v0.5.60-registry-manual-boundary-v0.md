# v0.5.60 registry/manual boundary

Status: docs-only registry/manual boundary checkpoint
Phase: v0.5.60-REFACTOR-2
Scope: command registry meaning, public/manual classification, release-surface gates, generated manual preconditions
Date: 2026-06-09 local session

## 1. Purpose

v0.5.60 records the registry/manual boundary after the v0.5.59 evergreen surface cleanup.

This checkpoint exists because CarbonStack now has many command-like surfaces:

    public release validation runner profiles;
    source-development runner profiles;
    hidden/private validation profiles;
    Comms dev commands;
    Comms legacy/stub-era commands;
    sidecar internal commands;
    Cypher API surfaces;
    release helper scripts;
    historical PowerShell helpers;
    future placeholders.

Without an explicit boundary, the command registry could accidentally look like a public CLI manual.

This checkpoint says clearly:

    the registry is a navigation and claim-boundary artifact;
    the registry is not public CLI polish;
    registry presence is not command promotion;
    include_in_front_readme is only a candidate flag, not automatic exposure;
    release runbooks remain authoritative for release-package validation;
    relay-openmls-join-dev remains hidden/dev-only until a deliberate v0.6.0 decision.

## 3. Command-surface classes

CarbonStack command-like surfaces should be read in the following classes.

### 3.1 Public release validation surfaces

These are commands a release runbook may tell a tester to run.

Current examples:

    verify-checksums
    full
    doctor where needed

Rules:

    must be documented in the release runbook when release-facing;
    must preserve release-specific meaning;
    must not imply deployment;
    must not imply production security;
    must not imply local-backbone unless a later release explicitly proves and claims that.

### 3.2 Source developer validation surfaces

These are useful from live umbrella checkouts.

Current examples:

    core
    local-cypher
    dev-runtime-openmls
    dev-runtime-openmls-wrappers
    relay-openmls-join-dev

Rules:

    may be documented for developers;
    must state live-checkout / dev-only boundaries where applicable;
    must not silently become release-package validation;
    must not be added to full or release-snapshot without an explicit design decision.

### 3.3 Hidden/private validation surfaces

These are implemented and useful, but not front-door public commands.

Current key example:

    relay-openmls-join-dev

Rules:

    may exist in the registry;
    may have examples for maintainers;
    should keep include_in_front_readme false;
    should not appear in the top-level README as a recommended public command;
    should not be included in full/release-snapshot until a deliberate v0.6.0 release-surface decision.

### 3.4 Comms dev command surfaces

These are development UX and scaffolding commands.

Current examples:

    openmls-send-dev
    openmls-inbox-dev
    openmls-relay-keypackage-submit-dev
    openmls-relay-keypackage-inbox-dev
    openmls-relay-welcome-submit-dev
    openmls-relay-welcome-inbox-dev
    openmls-relay-add-member-dev
    openmls-relay-join-dev

Rules:

    dev/pre-alpha only;
    not mature public messaging UX;
    not production E2EE claim;
    not verified identity;
    not local-backbone;
    not release-package validation by registry presence alone.

### 3.5 Legacy/stub-era surfaces

These exist for continuity and tests but are not the future UX.

Current examples:

    comms send
    comms inbox
    comms ack
    older PowerShell smoke scripts

Rules:

    must not be described as OpenMLS-backed mature messaging;
    should remain registry-visible for continuity;
    should not be front-door recommended unless a release-specific runbook says so.

### 3.6 Sidecar internal surfaces

These are provider/internal commands, usually wrapped by Comms.

Examples:

    provider-info
    identity-create
    identity-status
    public-bundle-export
    conversation-create
    conversation-add-member
    conversation-join
    message-protect
    message-open

Rules:

    internal/dev provider surfaces;
    not public UX;
    not secure vault;
    not trust verification ceremony;
    not server trust.

### 3.7 API/operator surfaces

These include Cypher CLI/API routes and local operator helpers.

Rules:

    route/API presence is not production deployment readiness;
    Cypher remains routing/storage infrastructure;
    Cypher is not identity authority, plaintext authority, or trust authority.

### 3.8 Future placeholders

Future entries may be named for planning continuity.

Rules:

    must be explicitly marked future/unsupported;
    must not appear in generated public docs as available commands;
    must not be treated as release evidence.

## 4. Front README inclusion rule

`include_in_front_readme: true` means:

    this command may be considered for front-door docs if the current release/runbook context supports it.

It does not mean:

    auto-promote this command;
    include in every README;
    include in release runbooks;
    include in full;
    include in release-snapshot;
    claim production readiness.

`include_in_front_readme: false` means:

    keep out of top-level public quick-start docs by default.

## 5. Generated command reference rule

A generated command reference does not exist yet.

Before generating one, CarbonStack needs:

    stable registry schema;
    resolved audience/maturity vocabulary;
    explicit filtering rules;
    explicit nonclaim rendering;
    release-facing vs dev-only separation;
    legacy/stub-era warnings;
    future/unsupported entry suppression;
    hidden/private profile suppression or separate maintainer-only section.

A generated command reference must not become a claim surface without preserving nonclaims.

## 6. v0.6.0 promotion gates

A command/profile can move toward v0.6.0 release-surface inclusion only after answering:

    What exact evidence does it provide?
    Does it run in a fresh release package root or only a live umbrella checkout?
    Does it create generated/private state?
    Does it clean only runner-owned/generated state?
    Does it mutate trust/candidate state?
    Does it require sidecar provider state?
    Does it require local Cypher?
    Does it fail safely when state is stale?
    Does it preserve nonclaims in output/docs?
    Does it belong in full, release-snapshot, a separate profile, or maintainer docs only?

For relay-openmls-join-dev specifically:

    it remains positive-path;
    it remains hidden from front README;
    it remains outside full;
    it remains outside release-snapshot;
    it may be reconsidered during v0.6.0 inclusion planning.
