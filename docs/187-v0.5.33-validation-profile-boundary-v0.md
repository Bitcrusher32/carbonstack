# v0.5.33 validation profile boundary

Status: validation-profile boundary planning record
Phase: v0.5.x post-provider-live-flow-boundary / pre-local-backbone go-no-go
Scope: validation profile claims, generated-state boundaries, cleanup limits, release-package vs live-umbrella distinction
Date: 2026-06-08 local session

## 1. Purpose

v0.5.33 defines validation-profile boundaries before any Relay Space schema/API, provider live-flow, local-backbone, CLI, or registry implementation.

This is a planning record only.

v0.5.33 does not implement:

    new validation profiles;
    local-backbone validation;
    Relay Space schema;
    Relay Space API routes;
    Relay Space join flow;
    provider live-flow wiring;
    Cypher schema changes;
    Comms client wrapper changes;
    CLI/registry entries;
    destructive reset/recovery;
    backup/restore;
    re-enrollment mutation;
    vault;
    PQ/hybrid crypto.

Decision:

    no validation profile implementation yet.
    no local-backbone profile yet.
    live-git umbrella validation and release-package validation must stay distinct.
    generated state and cleanup boundaries must be explicit.
    future local-backbone validation must define exactly what it proves and does not prove.
    trust/candidate/provider/generated state must not be destructively cleaned without narrow rules.
    CLI/registry remains deferred.
    v0.5.34 should be local-backbone go/no-go reassessment.

## 2. Current validation profile state

Existing runner profiles include:

    doctor;
    core;
    local-cypher;
    dev-runtime-openmls;
    dev-runtime-openmls-wrappers;
    full;
    release-snapshot;
    write-checksums;
    verify-checksums.

Existing boundaries are important:

    dev-runtime-openmls is live-umbrella only;
    dev-runtime-openmls-wrappers is live-umbrella only;
    release-snapshot is package-root oriented;
    full runs release-snapshot then local-cypher;
    clean-generated is explicit opt-in;
    artifact scans are non-destructive unless clean-generated is requested.

These should not be collapsed into a premature local-backbone profile.

## 3. Release-package vs live-umbrella distinction

Release-package validation and live-umbrella validation must remain separate.

Release-package validation may prove:

    package layout exists;
    required docs/files exist;
    checksums match;
    strict pre-test artifact scan passes;
    package-root core validation passes;
    release snapshot can be validated from a fresh extracted/staged root.

Release-package validation must not claim:

    local-backbone works;
    live Relay Space works;
    provider live-flow works;
    deployment works;
    hostile-server safety;
    production security;
    metadata privacy;
    mature UX;
    certification.

Live-umbrella validation may prove:

    sibling git checkout layout exists;
    live dev scripts exist;
    Cypher can run locally;
    OpenMLS dev runtime smoke proof can run;
    wrapper-based OpenMLS dev smoke proof can run;
    package tests pass across current working repos.

Live-umbrella validation must not claim:

    release package reproducibility;
    deployability;
    production readiness;
    hostile-server safety;
    security certification.

## 4. What future local-backbone validation may prove

A future local-backbone validation profile may eventually prove a narrow development path such as:

    Cypher local server starts;
    Relay Space schema/API exists;
    Relay Space can be created;
    invite can be created and claimed;
    routing member can be registered;
    Relay Space-scoped envelope can be submitted and retrieved;
    provider/OpenMLS lifecycle can run through explicit dev paths;
    candidate identity material can be observed without verification;
    trust/recovery boundaries are preserved;
    ack remains sidecar-open/consume gated;
    generated state remains inside known generated roots.

It may only prove this if the corresponding implementation exists.

v0.5.33 does not add such a profile.

## 5. What future local-backbone validation must not prove

Even if future local-backbone validation passes, it must not claim:

    production secure messaging;
    hostile-server safety;
    metadata privacy;
    external audit;
    certification;
    mature verification UX;
    general-public usability;
    deployability;
    key-compromise recovery correctness;
    PQ/hybrid security;
    vault security;
    server trustworthiness;
    verified identity import from provider observation;
    local trust from Relay Space membership;
    local trust from OpenMLS/provider membership.

Passing validation is a development proof, not a security certification.

## 6. Generated state boundaries

Future profiles must explicitly classify generated state.

Known generated/build roots may include:

    OpenMLS sidecar target;
    OpenMLS sidecar .carbonstack-openmls-sidecar-state;
    temporary local Cypher DBs;
    local runner temp directories;
    release/checksum artifacts;
    provider-storage.json;
    signer.json;
    Go cache/temp roots.

Trust-sensitive state may include:

    trust.json;
    trust-events.jsonl;
    identity-candidates.json;
    provider identity state;
    provider storage/checkpoint state;
    sidecar signer state.

Cleanup must distinguish:

    build artifacts;
    dev fixture artifacts;
    temporary runner artifacts;
    trust-bearing state;
    identity-bearing state;
    recovery-relevant state.

## 7. Cleanup boundary

Cleanup must remain explicit and narrow.

Allowed cleanup class:

    known generated/build roots created by the validation profile;
    temporary local test DBs under runner-owned temp directories;
    known OpenMLS sidecar generated roots when explicitly requested.

Disallowed cleanup class unless a future destructive/reset design exists:

    user trust.json;
    user trust-events.jsonl;
    user identity-candidates.json;
    user provider identity state;
    user provider storage/checkpoint state;
    non-temp Cypher DBs;
    unknown DBs;
    unknown .carbonstack-* directories;
    repo docs/source files;
    release artifacts not created by the running profile.

Rule:

    validation cleanup must not become recovery/reset.

## 8. Trust and identity boundary

Validation profiles must not mutate trust semantics unless the profile explicitly exists to test such mutation and the test state is isolated.

Default validation must not:

    verify devices;
    mark devices changed;
    revoke devices;
    promote candidate identities;
    replace keys;
    suppress reverify warnings;
    bypass candidate review;
    bypass recovery classification.

Test-only isolated trust stores may be used only under temp directories or explicitly generated roots.

## 9. Ack boundary

Future validation profiles must preserve ack-after-open:

    Relay Space routing membership is not enough;
    invite claim is not enough;
    envelope retrieval is not enough;
    artifact write is not enough;
    provider report generation is not enough;
    trust-history append is not enough;
    candidate observation is not enough;
    recovery classification is not enough;
    only successful sidecar message-open/consume may permit ack unless a later negative-ack/quarantine design is explicitly created.

A future validation profile may test this boundary, but must not weaken it.

## 10. Registry / CLI boundary

Do not add CLI or registry entries yet for:

    Relay Space;
    local-backbone;
    provider live-flow;
    recovery execution;
    destructive reset;
    re-enrollment;
    vault;
    PQ/hybrid.

Registry/CLI entries should wait until:

    implementation exists;
    validation boundary exists;
    generated-state cleanup is clear;
    claim wording is honest;
    commands are useful as a supported dev surface.

Existing registry entries may continue to document current dev/runtime surfaces.

## 11. Future profile shape

Future validation work should be split rather than bundled.

Possible future profiles:

    relay-space-schema-dev;
    relay-space-api-dev;
    relay-space-routing-dev;
    provider-join-dev;
    local-backbone-dev;
    local-backbone-cleanup-dev;
    release-local-backbone-snapshot only much later if package-safe.

Do not create all of these at once.

The first future implementation should likely be Cypher Relay Space schema/API before broad Comms provider live-flow.
