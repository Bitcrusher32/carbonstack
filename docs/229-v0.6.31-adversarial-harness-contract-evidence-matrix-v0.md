# CarbonStack v0.6.31 Adversarial Harness Contract / Evidence Matrix v0

Status: docs/model checkpoint after v0.6.31A deep recon.

Scope: adversarial harness contract, evidence matrix vocabulary, profile-placement rules, claim boundaries, and future test-family staging.

This document is not an implementation.

This document does not add a runner profile.

This document does not add an adversarial mega-profile.

This document does not change `full`, `full-validate-release`, or `release-snapshot`.

This document does not add `full-runtime-dev`.

This document does not add hostile-server safety.

This document does not claim production security, deployment readiness, PQ/hybrid security, or audit/certification.

---

## 1. Purpose

v0.6.17 through v0.6.30 substantially hardened the dev/pre-alpha normal-message spine and clarified validation boundaries.

The next risk is not merely missing tests.

The next risk is overclaiming tests.

CarbonStack now has:

- normal-message wrapper proof surfaces;
- direct OpenMLS implementation proof surfaces;
- Relay Space onboarding proof surfaces;
- same-state positive-path proof;
- deterministic same-state failure-hardening profiles;
- state-boundary inventory through `state-audit-dev`;
- `full-validate-release` as explicit release-package validation naming.

These are useful evidence seeds.

They are not, by themselves, an adversarial harness.

They are not hostile-server proof.

They are not production security proof.

This document defines the contract that future adversarial harness work must follow so evidence can accumulate without claim drift.

## 3. Existing deterministic evidence seeds

Existing deterministic profiles are evidence seeds. They are not adversarial harness coverage unless a future harness explicitly wraps, mutates, records, and classifies them under this contract.

### 3.1 Positive same-state seed

Profile:

    same-state-integrated-dev

Seed value:

    proves Relay onboarding plus normal message send/open/ack in one coherent same-state live-dev universe.

Nonclaim:

    not hostile-server safety; not production E2EE; not release-package validation.

### 3.2 Wrong-conversation seed

Profile:

    same-state-message-failure-dev

Seed value:

    proves wrong-conversation normal message open does not ack or drain the inbox after same-state Relay join.

Nonclaim:

    currently covers wrong-conversation message-open failure only.

### 3.3 Unsupported-content seed

Profile:

    same-state-message-unsupported-dev

Seed value:

    proves unsupported normal application-message `content_type` does not ack or drain the inbox after same-state Relay join.

Nonclaim:

    currently covers unsupported normal application-message content type only.

### 3.4 Wrong-recipient/device seed

Profile:

    same-state-message-recipient-failure-dev

Seed value:

    proves wrong recipient/device/sidecar attempts do not falsely open, ack, or drain Bob's inbox after same-state Relay join.

Nonclaim:

    currently covers wrong recipient/device/sidecar no-false-success only.

### 3.5 Malformed-payload seed

Profile:

    same-state-message-malformed-payload-dev

Seed value:

    proves malformed normal application-message payloads do not falsely open, ack, drain, mutate provider state, or rewrite envelope state.

Nonclaim:

    malformed-payload coverage is deterministic dev evidence, not full adversarial input fuzzing.

### 3.6 Replay/duplicate classification seed

Profile:

    same-state-message-replay-classification-dev

Seed value:

    classifies normal application-message duplicate/replay behavior.

Nonclaim:

    not replay safety.

### 3.7 Welcome join failure seed

Profile:

    same-state-welcome-join-failure-dev

Seed value:

    proves corrupt Welcome join fails without ack, Relay inbox drain, or final/staging sidecar state poison, then restored Welcome joins and acks.

Nonclaim:

    not Welcome replay handling; not KeyPackage replay handling; not hostile-server onboarding safety.

## 4. Contract fields

Every future adversarial case must declare the following fields.

### 4.1 Required identity fields

- `case_id`
- `case_family`
- `title`
- `status`
- `introduced_in`
- `owner_surface`
- `profile_or_command_surface`

`status` must use one of:

- `contract_only`
- `evidence_seed`
- `implemented_dev_case`
- `implemented_adversarial_case`
- `deferred`
- `blocked`

### 4.2 Threat model fields

- `threat_actor`
- `attacker_capability`
- `trusted_components`
- `untrusted_components`
- `out_of_scope_capabilities`

Acceptable `threat_actor` values for v0:

- `local_operator_error`
- `malformed_client_input`
- `buggy_client`
- `buggy_relay`
- `curious_relay`
- `malicious_relay`
- `stale_state_source`
- `migration_or_restore_bug`
- `future_pq_downgrade_actor`

A case that uses `malicious_relay` must not automatically grant hostile-server safety.

### 4.3 Setup fields

- `setup_state`
- `required_profiles`
- `required_repos`
- `required_artifacts`
- `preconditions`
- `state_authority_domains`

`state_authority_domains` should use the v0.6.27/v0.6.29 state-boundary vocabulary where possible:

- `runtime_authority`
- `safety_sensitive_future_runtime_authority`
- `metadata_evidence`
- `dev_runtime_authority_container`
- `generated_disposable`
- `server_side_coordination_authority_inventory_only`

### 4.4 Action/mutation fields

- `mutation_or_action`
- `mutation_location`
- `mutation_timing`
- `mutation_mechanism`
- `expected_invariant`

Mutation examples:

- payload bytes changed;
- content type changed;
- recipient changed;
- conversation id changed;
- envelope metadata changed;
- Welcome artifact corrupted;
- KeyPackage artifact replayed;
- envelope duplicated;
- envelope reordered;
- envelope dropped;
- state restored from older snapshot;
- algorithm tag downgraded.

### 4.5 Output and invariant fields

- `allowed_outputs`
- `forbidden_outputs`
- `ack_drain_expectation`
- `state_mutation_expectation`
- `trust_mutation_expectation`
- `cypher_mutation_expectation`
- `operator_warning_expectation`

Common forbidden outputs:

- false successful open;
- ack after failed open;
- inbox drain after failed open;
- final state promotion after failed join;
- silent trust promotion;
- silent identity continuity claim;
- silent rollback acceptance;
- silent downgrade acceptance;
- production-security claim.

### 4.6 Evidence fields

- `evidence_files`
- `stdout_markers`
- `stderr_markers`
- `db_assertions`
- `state_assertions`
- `artifact_assertions`
- `negative_assertions`
- `cleanup_expectation`

Evidence must be inspectable after the run.

Evidence must not print raw secrets.

Evidence must distinguish:

- classification;
- refusal;
- warning;
- no-op;
- mutation;
- cleanup;
- failure.

### 4.7 Claim fields

- `claim_granted`
- `claim_not_granted`
- `explicit_nonclaims`
- `deferred_work`

Claims must be narrow.

Acceptable claim examples:

- `classifies duplicate normal-message envelope behavior`
- `rejects malformed normal-message payload without ack`
- `fails corrupt Welcome join without final state promotion`
- `detects unsupported normal-message content type without inbox drain`

Forbidden claim examples:

- `hostile-server safe`
- `replay safe`
- `metadata private`
- `production E2EE`
- `secure enrollment`
- `PQ secure`
- `audited`
- `deployment ready`

## 6. Harness placement rules

### 6.1 Release validation exclusion

Future adversarial harness cases must not be added to:

    full
    full-validate-release
    release-snapshot

unless a later model explicitly changes release-validation semantics.

Default posture:

    adversarial harness work is dev/operator evidence, not release-package validation.

### 6.2 Live-dev aggregation exclusion

Future adversarial harness cases must not automatically create or join:

    full-runtime-dev

`full-runtime-dev` remains future-only until its member list, run order, artifact cleanup, state-audit inclusion, failure semantics, and nonclaims are modeled.

### 6.3 Registry posture

A future implemented adversarial case may receive a registry entry only when:

- the command/profile exists;
- nonclaims are explicit;
- maturity is not overstated;
- audience is not overstated;
- generated command reference is updated;
- runner tests cover registry/reference freshness.

Registry presence is classification, not promotion.

### 6.4 Evidence storage posture

Future evidence files should be local/dev artifacts unless explicitly elevated.

Evidence storage must not contain raw secrets.

Evidence storage must not be treated as a production audit log.

Evidence schema files, if added later, should start as docs/dev artifacts.

## 9. Required invariants for future implementation

Future implementation must preserve these invariants unless a later model explicitly changes them:

1. Failed open must not ack.

2. Failed open must not drain the inbox.

3. Failed join must not ack.

4. Failed join must not promote final sidecar state.

5. Malformed payloads must not falsely open.

6. Unsupported content types must not silently succeed.

7. Wrong recipient/device attempts must not falsely open.

8. Duplicate/replay classification must not be described as replay safety.

9. Sender metadata must not be described as verified identity.

10. Relay metadata must not be described as private or authentic by default.

11. State inventory must not be described as recovery.

12. Trust import/restore must not silently promote trust.

13. Algorithm/PQ downgrade handling must not be claimed before implementation exists.

14. Evidence must not print raw secrets.

15. Dev evidence must not become production/security wording.

## 12. Summary

v0.6.31 defines the adversarial harness contract before writing the harness.

Existing same-state and failure-hardening profiles are evidence seeds.

They are not adversarial harness coverage by default.

Future cases must declare threat actor, setup state, mutation/action, expected invariant, allowed outputs, forbidden outputs, evidence files, claim granted, nonclaims, and deferred work.

Future adversarial work must not silently enter `full`, `full-validate-release`, `release-snapshot`, or `full-runtime-dev`.

The next public-surface/manual-docs refresh should use this contract as a claim-boundary spine before v0.7.0 release-boundary rehearsal.
