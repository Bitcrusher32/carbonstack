# Gate B5c Idempotent KeyPackage Publication

Status: implemented development contract for v0.7.6

## Result

Gate B5c publishes one explicitly selected, already-generated B5b KeyPackage generation through a dedicated Relay Space publication route.

The publication path performs B5a inspection before network submission and preserves separate identities for:

- B5b generation ID;
- B5b request ID;
- OpenMLS KeyPackage reference;
- serialized artifact SHA-256;
- Cypher payload SHA-256;
- Relay envelope ID;
- Relay Space and recipient destination.

## Route

    POST /v0/relay-spaces/{relay_space_id}/keypackage-publications

Request:

    sender_device_id
    recipient_device_id
    key_package_ref
    ciphertext_b64
    client_created_at optional

The route fixes:

    content_type:
      carbonstack.mls.keypackage.v0

    protocol_version:
      carbonstack-openmls-sidecar-v0

## Persistent publication authority

Cypher stores a narrow `keypackage_publications` binding referenced by the ordinary generic envelope.

Sender-scoped uniqueness covers:

    sender_device_id + key_package_ref
    sender_device_id + payload_sha256

The table is not a KeyPackage directory, lifecycle store, trust store, consumption receipt, or Welcome store.

## Classifications

New publication:

    HTTP 201
    publication_classification: created
    idempotent: false

Exact same sender, reference, bytes, Relay Space, and recipient replay:

    HTTP 200
    publication_classification: already_published
    idempotent: true
    envelope_id: original envelope ID

Same sender-scoped KeyPackage reused for another recipient or Relay Space:

    HTTP 409
    keypackage_publication_reuse_conflict

Reference and serialized-payload disagreement:

    HTTP 409
    keypackage_publication_identity_conflict

A changed `client_created_at` does not create another publication.

Replay after acknowledgement returns the original envelope and its current acknowledged state. It does not create or requeue another envelope.

## Transaction and concurrency

Relay Space existence, device existence, active sender membership, active recipient membership, existing publication classification, envelope insertion, and publication binding occur under one retrying SQLite transaction.

Required concurrent outcome:

- exact concurrent attempts produce one creation and idempotent replays;
- competing destinations produce one creation and reuse conflicts;
- no partial envelope remains after a uniqueness race.

This authority survives process restart.

## Comms command

    openmls-relay-keypackage-publish-dev

Required:

    --relay-space
    --to-device
    --sidecar-device-label
    --generation-id

The command:

1. loads the B5b inventory;
2. selects exactly the requested generation;
3. refuses unknown or retired generations;
4. resolves the immutable artifact and generation manifest;
5. invokes B5a `keypackage-inspect`;
6. requires current lifetime, OpenMLS validation, local ownership agreement, and inventory/ref/SHA/size/lifetime agreement;
7. publishes the exact artifact through the dedicated route;
8. prints created or replay classification and the stable envelope ID.

It never generates a replacement KeyPackage during publication.

## Legacy compatibility

`openmls-relay-keypackage-submit-dev` remains callable for historical transport proofs.

It still uses the fixed legacy public-bundle export and generic envelope submission. It is compatibility-only and does not provide:

- B5b generation selection;
- B5a generation-manifest inspection;
- B5c duplicate/reuse protection;
- stable exact-replay envelope identity.

## Recovery

Cypher is the publication authority.

If the server commits but the client loses the response, an exact retry returns the original envelope ID. No local publication receipt is required to decide publication identity.

## Validation

Permanent profile:

    keypackage-publication-dev

The profile and underlying package tests prove:

- B5b generation and B5a inspection;
- new publication and exact replay;
- stable envelope identity;
- destination reuse and reference/payload identity conflicts;
- concurrent serialization;
- migration and restart persistence;
- replay after acknowledgement without requeue;
- explicit generation selection;
- retired-generation refusal before network mutation;
- no KeyPackage ACK;
- no add-member;
- no Welcome submission;
- no trust/candidate mutation.

## Nonclaims

B5c does not implement:

- KeyPackage consumption;
- KeyPackage receipt/lock state;
- ACK-after-consume;
- OpenMLS add-member;
- Welcome submission or join;
- verified identity;
- trust promotion;
- secure enrollment;
- public KeyPackage lookup or directory;
- global copied-KeyPackage protection across distinct sender devices;
- production key distribution;
- production E2EE;
- deployment, public ingress, audit, or certification.

B5d remains the next KeyPackage leaf.
