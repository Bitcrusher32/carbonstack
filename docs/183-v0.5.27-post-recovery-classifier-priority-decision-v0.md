## 3. Why recovery-history append should come next

v0.5.26 created classifications but does not record those classifications in trust history.

The next safe implementation step is not destructive recovery and not re-enrollment mutation.

The next safe step is append-only recovery-history event support.

Rationale:

    recovery classifications are security-relevant;
    missing/corrupt/re-enrollment-required states should be recordable;
    append-only history preserves evidence without mutating trust state;
    history helpers can reuse the existing provider/candidate append pattern;
    later orchestration becomes cleaner if classification-to-history conversion already exists.
