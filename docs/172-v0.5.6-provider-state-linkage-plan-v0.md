# v0.5.6 provider-state linkage plan

Status: planning model
Phase: v0.5.x state correctness and persistence planning
Scope: OpenMLS sidecar/provider state, CarbonStackComms trust state, runtime/bootstrap boundary
Date: 2026-06-07 local session

## 1. Purpose

v0.5.6 defines how OpenMLS sidecar/provider identity and provider events should eventually link into CarbonStackComms trust state.

Previous rungs:

    v0.5.2 identified state-bearing islands.
    v0.5.3 inventoried state domains.
    v0.5.4 defined storage domains.
    v0.5.5 defined trust-state semantics.

v0.5.6 answers:

    what provider events are trust-relevant?
    what provider events should remain provider-only?
    what should mutate trust.json?
    what should append trust-events.jsonl?
    what should block send/receive/open?
    what should require re-verification?
    what should be visible to the user?
    what is safe for a first implementation spike?

This document does not implement provider linkage.

It does not implement:

    secure vault storage;
    PQ/hybrid ciphersuites;
    mature send/inbox UX;
    Relay Space join;
    local-backbone;
    Cypher schema changes;
    provider-state mutation of Comms trust state.

## 3. Linkage objects

### 3.1 Comms device ID

The Comms device ID is currently the local/Cypher-facing device identifier used by Comms commands and trust records.

It appears in:

    .carbonstack-comms/state.json
    .carbonstack-comms/trust.json
    .carbonstack-comms/trust-events.jsonl
    Cypher device registration and envelope routing

Linkage policy:

    Comms device ID should remain the local trust record key until a better mature identity key is designed.
    Provider state must not silently replace it.
    Any future mapping from sidecar identity to Comms device ID must be explicit.

### 3.2 Sidecar device label

The sidecar device label is currently an explicit dev label passed to OpenMLS sidecar commands.

It appears in:

    openmls-identity-create-dev
    openmls-identity-status-dev
    openmls-bundle-export-dev
    openmls-conversation-* wrappers
    openmls-send-dev
    openmls-inbox-dev

Linkage policy:

    sidecar labels are not mature identity truth.
    sidecar labels are useful operator/dev handles.
    A sidecar label alone must not create a verified Comms trust record.
    Future linkage should store sidecar label as provider metadata, not as the trust root.

### 3.3 Provider public identity material

Provider public identity material is the future bridge between OpenMLS identity and Comms trust records.

Current limitation:

    The exact production-grade public identity / safety-number material is not finalized.
    Current Comms fingerprints are development fingerprints derived from public identity key strings.

Linkage policy:

    observed provider public identity material should create unknown/unverified candidate state unless a verification ceremony occurs.
    matching provider material can support continuity checks for already verified devices.
    mismatching provider material must become changed / reverify-required behavior.
    provider material must not silently become verified because Cypher delivered it.

### 3.4 KeyPackage / public bundle

KeyPackages are setup artifacts, not automatically verified identity.

Linkage policy:

    KeyPackage export may append history later.
    KeyPackage receipt may create candidate/unverified identity material later.
    KeyPackage replacement for a known device should be treated as trust-relevant.
    KeyPackage compatibility and size become important for PQ/hybrid work later.

### 3.5 Provider event

Provider events are structured observations from the sidecar/provider layer.

Current event classes:

    lifecycle
    public_setup
    membership
    message
    storage_checkpoint
    trust_security
    terminal_fatal
    unknown

Current severity levels:

    debug
    info
    notice
    warning
    security
    fatal

Linkage policy:

    provider events should feed trust history only after mapping through explicit policy.
    unknown future events should not automatically become fatal or trust-mutating.
    trust-security and terminal-fatal events must be loud and conservative.

## 4. Provider event categories and linkage policy

### 4.1 Lifecycle events

Examples:

    provider.fixture.started
    provider.fixture.completed
    provider.command.unsupported
    provider.command.invalid
    provider.command.not_implemented

Linkage policy:

    do not mutate trust.json;
    generally do not append trust-events.jsonl except debug/dev traces if a future dev log exists;
    do not affect verified/unverified/changed/revoked state;
    command invalid/unsupported may warn operator but is not identity truth.

### 4.2 Public setup events

Examples:

    provider.public_bundle.created
    provider.public_bundle.exported

Linkage policy:

    do not mutate trust.json by default;
    may append setup history later;
    should not mark a device verified;
    may create candidate/unverified import material only in an explicit future import flow.

### 4.3 Membership events

Examples:

    provider.conversation.created
    provider.conversation.exists
    conversation.welcome.created
    conversation.welcome.staged
    conversation.member_added
    conversation.joined
    conversation.loaded

Linkage policy:

    membership events are history-relevant;
    member-added should be user-visible;
    do not mutate device trust state by default;
    future group membership state should record these separately from device trust;
    unexpected membership changes should be loud later.

### 4.4 Message events

Examples:

    message.protected
    message.opened

Linkage policy:

    normal message protect/open should not mutate device trust state;
    successful open may allow ack behavior;
    failed open due to security/trust events must not ack silently;
    message events may append message lifecycle history in a future message DB, not trust.json by default.

### 4.5 Storage checkpoint events

Examples:

    storage.save.required
    storage.saved
    storage.load.started
    storage.loaded
    storage.missing
    storage.corrupt
    checkpoint.required
    checkpoint.completed
    checkpoint.failed
    provider.identity.loaded
    provider.identity.missing
    provider.identity.created
    provider.identity.exists

Linkage policy:

    normal loaded/saved/created events do not mutate trust.json;
    missing/corrupt/checkpoint-failed events should stop operations and show recovery path;
    missing/corrupt provider state should be loud because it may imply identity/group continuity loss;
    do not automatically recreate identity/provider state in mature mode;
    do not automatically downgrade verified trust records just because provider storage is missing;
    instead block relevant operations and require recovery/relink/reverify policy.

### 4.6 Trust-security events

Examples:

    provider.signature.invalid
    provider.identity.changed
    provider.identity.reverify.required
    provider.message.tamper.detected
    provider.replay.detected
    provider.epoch.stale

Linkage policy:

    must be user-visible;
    should append trust history;
    may block send, receive, or open depending event;
    provider.identity.changed should map to changed / reverify-required for the affected device when the device mapping is known;
    provider.identity.reverify.required should require re-verification;
    signature invalid, tamper, replay, stale epoch should block open or quarantine message;
    these must not be hidden as ordinary provider noise.

### 4.7 Terminal-fatal events

Examples:

    provider.fatal
    provider.state.inconsistent
    provider.group.unrecoverable
    provider.secret.material.unavailable
    provider.invariant.violation

Linkage policy:

    must be user-visible;
    should append trust/security history;
    should stop relevant operation;
    should block send/receive/open where state safety cannot be established;
    should show recovery path;
    should not silently mark devices verified/unverified/changed without a dedicated recovery model;
    may eventually feed compromised or re-enrollment-required state, but compromised remains reserved until designed.

## 5. Provider action to Comms behavior mapping

Current provider-trust actions:

    none
    append_history
    debug_only
    warn_user
    block_send
    block_receive
    block_open
    quarantine_message
    require_reverify
    mark_identity_changed
    show_recovery_path
    stop_operation
    fatal_local_state

Proposed linkage behavior:

| Provider action | Comms behavior | Trust mutation? | Event append? | Current implementation status |
|---|---|---|---|---|
| none | no user-facing action | no | no | action exists only |
| debug_only | dev/debug output only | no | maybe dev log later | action exists only |
| append_history | append relevant history | no by default | yes, future | action exists only |
| warn_user | print/display loud warning | no by default | yes if security-relevant | action exists only |
| block_send | prevent send | no by default | yes if security-relevant | action exists only |
| block_receive | prevent receive/sync path | no by default | yes if security-relevant | action exists only |
| block_open | do not open plaintext / do not ack | no by default | yes | action exists only |
| quarantine_message | isolate message artifact | no by default | yes | action exists only |
| require_reverify | require verification before trust resumes | maybe changed/unverified when mapped to device | yes | action exists only |
| mark_identity_changed | mark known device changed if mapping known | yes: changed | yes | action exists only |
| show_recovery_path | show recovery guidance | no by default | yes if persistent state issue | action exists only |
| stop_operation | abort operation | no by default | yes if user-visible | action exists only |
| fatal_local_state | treat local provider state as unsafe | maybe future compromised/recovery state | yes | action exists only |

## 6. What mutates trust.json

Trust store mutation should be narrow.

Allowed future mutators:

    explicit verification ceremony;
    explicit revocation command or signed revocation flow;
    explicit re-enrollment flow;
    explicit provider identity mismatch handling when a device mapping is known;
    explicit recovery flow after provider state loss/corruption.

Not allowed to mutate trust.json by itself:

    Cypher device lookup;
    Cypher envelope delivery;
    KeyPackage receipt alone;
    Welcome receipt alone;
    sidecar label existence;
    provider identity creation alone;
    provider identity loaded alone;
    conversation created/loaded alone;
    message opened alone.

Default provider observation policy:

    provider identity observed -> unknown/unverified candidate, not verified;
    provider identity matches verified record -> no trust-state mutation, possibly append continuity history later;
    provider identity mismatches verified record -> changed / reverify-required;
    provider fatal/local-state event -> block/recovery path, not automatic trust rewrite.

## 7. What appends trust-events.jsonl

Current event types:

    device_verified
    device_key_changed
    device_revoked

Future provider-originated events should use distinct names, for example:

    provider_identity_observed
    provider_identity_changed
    provider_reverify_required
    provider_signature_invalid
    provider_tamper_detected
    provider_replay_detected
    provider_state_missing
    provider_state_corrupt
    provider_secret_unavailable
    provider_group_unrecoverable
    provider_membership_changed

Future event records should distinguish:

    manual user action;
    local Comms command;
    OpenMLS sidecar/provider event;
    Cypher-observed routing metadata;
    recovery/import/export action.

v0.5.6 does not implement these event types.

## 8. What stays provider-only

The following should remain provider-only unless a future bridge deliberately promotes them:

    normal provider fixture start/complete;
    command invalid/unsupported/not implemented;
    identity-created as dev-local sidecar state;
    identity-loaded when it matches expected local state;
    storage save/load informational events;
    normal message-protected event;
    normal message-opened event;
    conversation-loaded event.

These may be useful for debug logs, but should not rewrite trust state.

## 9. What must block

Should block send:

    unknown/unverified/changed recipient in strict mode;
    revoked or compromised recipient always;
    provider identity changed for mapped recipient;
    provider reverify required for mapped recipient;
    provider storage missing/corrupt when local identity continuity is required;
    terminal-fatal provider state events.

Should block open:

    provider signature invalid;
    message tamper detected;
    replay detected;
    stale epoch;
    group unrecoverable;
    secret unavailable;
    invariant violation.

Should block receive/sync where applicable:

    provider state inconsistent;
    group unrecoverable;
    storage corrupt;
    terminal-fatal provider state event.

Should prevent ack:

    any message that fails sidecar open;
    any message quarantined due to trust/security provider event;
    any message blocked by stale epoch/replay/tamper decision.

## 10. First implementation spike eligibility

The first implementation spike after v0.5.6 should be small and testable.

Good candidates:

    expose a provider-trust decision CLI/dev helper;
    add tests for provider event -> trust action mapping completeness;
    add a non-mutating provider decision report to existing dev wrappers;
    add a helper that converts ProviderTrustDecision to human-readable warning/block text;
    add an explicit check that provider identity events do not mutate trust.json yet.

Bad first candidates:

    mutate trust.json from sidecar output;
    implement vault encryption;
    implement PQ/hybrid ciphersuites;
    replace send/inbox;
    add local-backbone;
    add Cypher schema for trust state;
    silently import provider identity as verified.

Recommended first spike:

    v0.5.7 provider-trust decision report.

It should stay non-mutating and prove that existing provider event decisions can be surfaced safely before trust-store mutation exists.

## 11. Future linkage stages

Suggested stages:

    Stage 0:
      current state: provider decisions exist as pure policy helpers.

    Stage 1:
      non-mutating provider decision report for dev commands.

    Stage 2:
      provider-originated history append for selected events.

    Stage 3:
      candidate/unverified identity import.

    Stage 4:
      mapped identity mismatch -> changed/reverify-required.

    Stage 5:
      recovery/re-enrollment behavior for missing/corrupt/terminal provider state.

    Stage 6:
      mature UX integration.

Do not skip from Stage 0 to Stage 4.
