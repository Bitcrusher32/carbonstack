# CarbonStack v0.6.18 Same-State Message Unsupported Dev Profile v0

Status: implementation checkpoint for second same-state failure-path hardening profile.

## Scope

This document records the committed profile:

    go run . --profile same-state-message-unsupported-dev --root <umbrella root> --clean-generated

The profile proves one narrow failure rule inside the same-state universe:

    unsupported normal application-message content_type must not ack and must not drain Bob's inbox.

It then restores the valid content type and proves the message remains recoverable by opening with the correct conversation and explicit `--ack`.

## Why this exists

v0.6.16 added the positive-path profile:

    same-state-integrated-dev

v0.6.17 added the wrong-conversation no-ack/no-drain profile:

    same-state-message-failure-dev

v0.6.18 adds unsupported normal-message classification without claiming an adversarial harness.

## Sequence

The profile performs:

1. Build a temporary Cypher binary.
2. Start one temporary Cypher server with one temporary DB.
3. Initialize Alice/Bob Comms state files against that server.
4. Create/claim dev invites and register devices.
5. Create one Relay Space and routing members.
6. Create Alice/Bob sidecar identities.
7. Alice creates one conversation.
8. Bob submits KeyPackage.
9. Alice add-member creates Welcome.
10. Bob joins with ACK_AFTER_JOIN enabled.
11. Alice sends a normal application message.
12. The runner mutates only that normal message envelope's `content_type` to `carbonstack.test.unsupported-normal-message.v0` inside the temporary Cypher DB.
13. Bob runs `message-inbox-dev --ack` with the correct conversation and message label.
14. Assert the unsupported envelope is skipped.
15. Assert ack count does not change.
16. Assert Bob inbox count does not change.
17. Assert output does not report `acked: true` or `ack_delivery_state: acknowledged`.
18. Restore the original `carbonstack.mls.application-message.v0` content type.
19. Bob opens the same message with the correct conversation.
20. Assert correct open succeeds and acks.
21. Assert Bob inbox is empty after the correct open/ack.

## Expected unsupported evidence

Unsupported attempt:

    message skipped
    reason: unsupported_envelope
    opened_envelopes: 0
    unsupported_envelopes: 1
    open_failures: 0
    ack_failures: 0

Expected counters:

    acks_after_unsupported_open == acks_before_unsupported_open
    bob_inbox_count_after_unsupported_open == bob_inbox_count_before_unsupported_open
    acks_after_correct_open == acks_before_unsupported_open + 1
    bob_inbox_count_after_correct_open == 0

## Relationship to future adversarial harness

This is a failure-path hardening profile, not an adversarial harness.

A later harness may include malformed payloads, replay, duplicate, drop, delay, stale Welcome, wrong Relay Space, wrong recipient, or server-equivocation behavior.

Do not use this profile alone to claim hostile-server safety.
