# CarbonStack v0.6.10 Integrated Runtime Policy v0

Status: dev/pre-alpha policy contract
Scope: future live integrated runtime validation profile
Checkpoint target: v0.6.10 Stage 1
Public release impact: none; current public release remains v0.6.0 State/UX Boundary Validation Pre-Release

## 1. Purpose

This document defines the policy boundary for `integrated-runtime-dev`.

Stage 1 recorded the intended proof shape, exclusions, cleanup rules, nonclaims, and graduation path before implementation. Stage 2 implements the first live-umbrella composition profile while preserving this policy boundary.

## 2. Current proof surfaces

Current separate proof surfaces:

- `relay-openmls-join-dev`
  - proves Relay Space OpenMLS KeyPackage -> add-member -> Welcome -> join;
  - includes no-ack and ACK_AFTER_JOIN subruns;
  - remains live-umbrella dev validation only;
  - remains outside `full` and `release-snapshot`.

- `dev-runtime-openmls-wrappers`
  - proves bootstrap wrappers -> `message-send-dev` -> Cypher -> `message-inbox-dev --ack`;
  - uses the recommended dev/pre-alpha normal-message wrapper path;
  - remains live-umbrella dev validation only;
  - remains outside `full`.

- `dev-runtime-openmls`
  - proves direct `openmls-send-dev` -> Cypher -> `openmls-inbox-dev --ack`;
  - remains the lower-level direct proof baseline;
  - remains outside `full`.

- `full`
  - remains release-package validation;
  - runs `release-snapshot`, then `local-cypher`;
  - is intended for fresh extracted or throwaway staged release package roots;
  - is not live integrated runtime validation.

## 3. Policy decision

The next integrated proof profile should be named:

    integrated-runtime-dev

Rationale:

- clear live-dev scope;
- avoids semantic collision with `full`;
- avoids prematurely introducing `full-runtime-dev`;
- preserves the option to later graduate into a fuller profile only after maturity, package-root rehearsal, adversarial work, and explicit release-profile decision.

Do not implement or document `full-runtime-dev` as active yet.

## 4. Intended integrated proof shape

The first `integrated-runtime-dev` implementation should prove the in-series happy path:

    Relay onboarding:
      KeyPackage submit/fetch/write
      -> add-member
      -> Welcome submit/fetch/write
      -> join

    Normal message:
      message-send-dev
      -> Cypher application-message envelope
      -> message-inbox-dev --ack after successful message-open

The integrated proof should prefer the wrapper normal-message path because `message-*` is the recommended dev/pre-alpha normal-message UX candidate.

The direct `openmls-send-dev` / `openmls-inbox-dev` profile remains separately useful for implementation visibility and should not be removed.

## 5. Individual-callability rule

Integrated runtime may call onboarding and message phases in series, but it must not erase the individual primitive surfaces.

The following remain individually callable:

- `openmls-relay-keypackage-submit-dev`
- `openmls-relay-keypackage-inbox-dev`
- `openmls-relay-welcome-submit-dev`
- `openmls-relay-welcome-inbox-dev`
- `openmls-relay-add-member-dev`
- `openmls-relay-join-dev`
- `message-send-dev`
- `message-inbox-dev`
- lower-level `openmls-*` direct proof commands

Reason:

Partial onboarding, trust-state depreciation, retry/rejoin, artifact inspection, and repair flows may need individual steps.

## 6. Ack policy

The integrated profile must preserve existing ack doctrine.

Application-message ack:

- no ack on fetch;
- no ack for unsupported envelope;
- no ack on artifact-write failure;
- no ack on sidecar message-open failure;
- ack only after successful sidecar message-open and explicit `--ack`.

Relay Welcome ack:

- no ack on fetch/write alone;
- no ack on failed join;
- ack only after successful join/reloadable state and explicit ack policy.

KeyPackage ack:

- current posture remains no ack in the integrated proof unless a later policy explicitly defines a safe terminal KeyPackage ack action.

## 7. Root and package policy

Initial `integrated-runtime-dev` should be live-umbrella only.

It should require the live Git umbrella layout:

    carbonstack/
    carbonstack-comms/
    carbonstack-cypher/

It should not run from release package roots yet.

It should not be part of:

- `full`;
- `release-snapshot`;
- public v0.6.0 release validation;
- package-root release validation.

Package-root rehearsal may be considered later only after repeated clean live runs and explicit policy update.

## 8. Cleanup policy

The profile may create OpenMLS sidecar generated roots and Rust build outputs.

It must support `--clean-generated` through the existing runner cleanup mechanism for known generated/build artifact roots:

    carbonstack-comms/internal/protocol/mls/openmls-sidecar/.carbonstack-openmls-sidecar-state
    carbonstack-comms/internal/protocol/mls/openmls-sidecar/target

It must not delete arbitrary operator state, unknown paths, local user DBs, or untracked files outside known generated roots.

Runner-owned temp roots should be created under system temp and removed after completion where possible.

## 9. Failure policy

The integrated profile should fail if any required phase fails:

- required paths/toolchains unavailable;
- Relay onboarding cannot complete;
- join does not produce reloadable state;
- Welcome ack policy is violated;
- normal message send fails;
- normal message open fails;
- application-message ack policy is violated;
- known generated artifact cleanup fails when `--clean-generated` is requested.

The profile should not mask failures by treating later success as proof of earlier skipped phases.

## 10. Relationship to full

`full` remains the release-package validation ladder:

    release-snapshot -> local-cypher

Do not mutate `full` in v0.6.10 Stage 1.

Do not make `full` pass from the live umbrella root by weakening release metadata checks.

A future `full-runtime-dev` or expanded `full` may be considered only after:

- `integrated-runtime-dev` exists;
- repeated clean runs pass;
- package/fresh-root behavior is understood;
- adversarial relay/message harness work has at least started or been explicitly deferred;
- release runbook, command registry, boundary table, and generated docs can state exact meaning and nonclaims.

## 11. Nonclaims

`integrated-runtime-dev` will not claim:

- production secure messaging;
- production E2EE;
- hostile-server safety;
- metadata privacy;
- identity verification;
- secure enrollment;
- production key distribution;
- production membership UX;
- local-backbone readiness;
- deployment readiness;
- mature messenger UX;
- general-public usability;
- audit or certification;
- that `full` validates integrated runtime;
- that release-snapshot validates integrated runtime;
- that Relay onboarding artifacts are ordinary application messages.

## 12. Stage 2 implementation checklist

When implementation begins, prefer a bounded runner patch:

- add `integrated-runtime-dev` to runner profile switch and help text;
- add `runner.integrated-runtime-dev` registry row;
- add command boundary table row;
- add runner README section;
- implement a Go runner profile that calls existing scripts/functions or a dedicated Comms script without fragile recursive profile shelling;
- include pre/post artifact scans;
- include `--clean-generated` support;
- validate:
  - runner tests;
  - registry tests;
  - `integrated-runtime-dev --clean-generated`;
  - existing `relay-openmls-join-dev --clean-generated`;
  - existing `dev-runtime-openmls-wrappers --clean-generated`;
  - existing `dev-runtime-openmls --clean-generated`;
  - doctor;
  - Comms package tests;
  - Cypher package tests.

## 14. Stage 2 implementation note

The first `integrated-runtime-dev` implementation composes existing validated dev profiles in sequence:

    relay-openmls-join-dev
    -> dev-runtime-openmls-wrappers

This validates the Relay onboarding proof and the recommended normal-message wrapper proof under one runner profile without mutating `full` or `release-snapshot`.

Important limit:

    The first implementation is profile composition, not yet a same-state/same-conversation package-root release proof.

This limit is intentional for v0.6.10 because it keeps the profile bounded and preserves all primitive surfaces while establishing an integrated validation name.
