# CarbonStack v0.6.5 Message Wrapper Implementation Boundary

**Status:** pre-alpha / experimental implementation checkpoint  
**Anchor:** v0.6.3 normalized OpenMLS message-flow contract and v0.6.4 command-level test-gap closure  
**Purpose:** Record the implementation boundary for opinionated dev/pre-alpha normal-message wrapper commands.

---

## 0. Summary

v0.6.5 introduces two Comms wrapper commands:

    message-send-dev
    message-inbox-dev

These wrappers are not thin aliases. They provide a cleaner public-testing command surface over the existing OpenMLS application-message implementation path while preserving implementation truth.

They coexist with:

    openmls-send-dev
    openmls-inbox-dev

The lower-level `openmls-*` commands remain the direct implementation/proof surfaces. The new `message-*` wrappers are dev/pre-alpha normal-message UX candidates.

---

## 1. Implemented Comms commands

### message-send-dev

Purpose:

    Opinionated dev/pre-alpha message send wrapper over the OpenMLS sidecar + Cypher application-message envelope path.

Implementation posture:

    Uses the same OpenMLS message-protect and Cypher application-message envelope submission seams as openmls-send-dev.
    Prints cleaner tester-facing output.
    Still exposes implementation_path and backend truth.
    Does not perform Relay onboarding.
    Requires existing Comms state, Cypher reachability, sidecar identity/conversation state, and send trust posture.

Required flags:

    --to-device
    --message
    --sidecar-device-label
    --conversation

Optional flags:

    --state
    --strict
    --sidecar-dir
    --message-label

### message-inbox-dev

Purpose:

    Opinionated dev/pre-alpha message inbox/open wrapper over the OpenMLS sidecar + Cypher application-message inbox path.

Implementation posture:

    Uses the same Cypher inbox, OpenMLS artifact write, sidecar message-open, and explicit ack-after-open seams as openmls-inbox-dev.
    Prints cleaner tester-facing output.
    Still exposes implementation_path and backend truth.
    Does not perform Relay onboarding.
    Does not ack on fetch.
    Does not ack unsupported envelopes.
    Does not ack artifact-write failure.
    Does not ack message-open failure.
    Acks only after successful message-open when --ack is explicitly passed.

Required flags:

    --sidecar-device-label
    --conversation

Optional flags:

    --state
    --sidecar-dir
    --message-label
    --limit
    --ack

## 2. Boundary versus OpenMLS implementation commands

The direct implementation/proof commands remain:

    openmls-send-dev
    openmls-inbox-dev

The wrapper commands are:

    message-send-dev
    message-inbox-dev

Current intended split:

    message-* commands:
        cleaner public-testing dev UX;
        opinionated normal-message wrapper output;
        still dev/pre-alpha;
        still exposes implementation_path/backend truth.

    openmls-* commands:
        lower-level OpenMLS/Cypher implementation proof surface;
        more backend-oriented IO;
        useful for debugging, tests, and maintaining implementation visibility.

Do not remove or merge the direct OpenMLS commands yet. A future maturity pass can decide whether wrappers become canonical and the direct commands become lower-level/internal-ish.

---

## 3. Relay onboarding boundary

The message wrappers do not perform Relay onboarding.

They assume the needed OpenMLS sidecar identity and conversation state already exist.

Relay Space onboarding/artifact commands remain separate:

    openmls-relay-keypackage-submit-dev
    openmls-relay-keypackage-inbox-dev
    openmls-relay-welcome-submit-dev
    openmls-relay-welcome-inbox-dev
    openmls-relay-add-member-dev
    openmls-relay-join-dev

KeyPackage and Welcome inboxes remain artifact inboxes, not normal message inboxes.

A future onboarding wrapper may exist, but it must not collapse artifact inbox semantics into ordinary message inbox semantics.

## 4. Registry/table policy

Because `message-send-dev` and `message-inbox-dev` are now real callable Comms commands, registry and command-boundary table rows are required.

This is not promotion to production UX.

Registry/table presence means:

    the commands exist;
    the commands are classified;
    their source path and nonclaims are explicit;
    runner coverage can verify command-surface honesty.

Registry/table presence does not mean:

    production secure messaging;
    production E2EE;
    hostile-server safety;
    verified identity;
    metadata privacy;
    mature messenger UX;
    general-public readiness.
