# CarbonStack v0.6.33 Release-Boundary / Package-Root Rehearsal Plan v0

Status: docs/model checkpoint after v0.6.33A release-boundary preflight and v0.6.0 release-shape inspection.

Scope: v0.7.0 release-boundary and package-root rehearsal planning.

This document is not a release, not a package rehearsal, not a tag, and not an asset upload.

It does not change registry semantics, add a runner profile, implement `full-runtime-dev`, implement adversarial harness cases, or claim deployment readiness, production security, hostile-server safety, PQ/hybrid security, backup/restore, CarbonStackOS readiness, audit, or certification.

## 1. Purpose

v0.6.33A confirmed that CarbonStack is ready to plan a v0.7.0 cumulative pre-alpha engineering release boundary, but not ready to blindly run or copy the v0.6.0 release scripts.

The v0.6.0 public release shape is useful prior art:

- one intended multi-repo package archive;
- release manifest;
- package checksums;
- asset checksums;
- validation freeze;
- testing runbook;
- release notes;
- LICENSE;
- explicit warning that Gitea default Source Code ZIP/TAR.GZ archives are not the intended multi-repo validation package.

The v0.6.0 staging and rehearsal scripts are useful prior art:

- stage tracked HEAD snapshots;
- include `carbonstack`, `carbonstack-comms`, and `carbonstack-cypher`;
- exclude `carbonstack-os`;
- write `release/manifest.json`;
- write release notes, testing runbook, validation freeze, and LICENSE;
- write and verify checksums;
- create an archive;
- fresh-extract the archive;
- verify checksums from fresh extraction;
- run package validation;
- check absence of generated/private/build artifacts.

But those scripts and release notes are v0.6.0-specific. v0.7.0 must translate the shape, not inherit stale claims.

## 2. Candidate v0.7.0 release boundary

Candidate target version:

    v0.7.0

Candidate release title:

    CarbonStack v0.7.0 Cumulative Pre-Alpha Engineering Boundary Pre-Release

Meaning:

    a source/package validation boundary for the current experimental multi-repo CarbonStack development line.

It is not a production release, secure-use release, finished messenger, deployment release, hostile-server safety claim, PQ/hybrid security claim, or CarbonStackOS readiness claim.

Current public release remains v0.6.0 until an explicit v0.7.0 release is cut.

## 3. Candidate package repository set

Candidate runnable package should include:

- `carbonstack`
- `carbonstack-comms`
- `carbonstack-cypher`

Candidate runnable package should continue to exclude:

- `carbonstack-os`

`carbonstack-os` remains future constrained-appliance OS work. Including it in the runnable package would risk implying Android/OS readiness.

## 5. Candidate validation ladder

Primary v0.7.0 validation path should be:

    go run . --profile verify-checksums --root <package-root>
    go run . --profile full-validate-release --root <package-root> --clean-generated

Compatibility validation path:

    go run . --profile full --root <package-root> --clean-generated

`full-validate-release` should be the preferred release-facing name because it describes the actual proof boundary.

`full` should remain a compatibility name through v0.7.0.

Current `full-validate-release` behavior is intentionally identical to `full`:

    release-snapshot
    local-cypher

`release-snapshot` already calls `core`, so neither `full` nor `full-validate-release` should call `core` a second time.

## 6. Script strategy decision

Decision:

    fork v0.6.0 scripts into v0.7.0-specific scripts before rehearsal.

Candidate new scripts:

- `scripts/stage-v0.7.0-package.sh`
- `scripts/rehearse-v0.7.0-package.sh`

Do not parameterize the v0.6.0 scripts yet.

Rationale:

- release scripts are release-critical evidence;
- v0.6.0 release notes and runbook text are version-specific;
- parameterization now risks hiding stale release claims behind variables;
- fork-first keeps the package rehearsal path explicit and reviewable.

v0.6.0 scripts should remain historical prior art.

v0.7.0 scripts must be committed before their output is treated as package evidence.

## 10. Package artifact hygiene

The v0.7.0 rehearsal should preserve or strengthen the v0.6.0 forbidden-artifact checks.

Final package should not contain:

- `.git` metadata;
- Rust `target` output;
- OpenMLS sidecar generated state;
- local `cypher.db`;
- SQLite `*.db-shm`;
- SQLite `*.db-wal`;
- provider storage;
- signer files;
- raw private LogDocs;
- raw private breakpoints;
- untracked local generated artifacts.

Staging should archive tracked HEAD snapshots, not working tree directories.

All script changes must be committed before using script output as release evidence.
