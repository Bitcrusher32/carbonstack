# CarbonStack v0.6.29 Bounded State Substrate Mechanics v0

Status: docs/model checkpoint after v0.6.29A bounded state substrate / vault-substrate-dev mechanics preflight.

Scope: bounded state substrate mechanics, first inventory/check posture, current `state-audit-dev` relationship, included/excluded surfaces, output semantics, refusal/warning behavior, and future implementation gates.

This document is not an implementation.

This document does not add a vault.

This document does not add encryption.

This document does not claim secure storage.

This document does not implement backup or restore.

This document does not implement PQ.

This document does not implement an adversarial harness.

---

## 1. Purpose

v0.6.29A performed a bounded state substrate mechanics preflight after two controlling model checkpoints:

* `223-v0.6.27-vault-security-nosilent-state-model-v0.md`
* `224-v0.6.28-pq-hybrid-placement-model-v0.md`

The preflight confirmed that the first bounded substrate should not be a vault.

The first safe shape is:

    non-mutating state inventory / state-boundary checking

The preflight also found that CarbonStackComms already has an existing surface:

    state-audit-dev

That command is already classified as a non-mutating local state-domain inventory for Comms, trust/candidate state, OpenMLS sidecar generated state, build output, and local Cypher DB boundaries.

Therefore v0.6.29 should not create a new first command by default.

The correct next posture is:

    document the bounded substrate mechanics;
    treat state-audit-dev as the current proto-substrate / inventory precursor;
    inspect and extend state-audit-dev only if later work shows a concrete gap.

## 2. Relationship to the state model

This document depends on the v0.6.27 state/security/no-silent model.

The bounded substrate must obey these categories:

* runtime authority;
* server-side coordination authority;
* metadata/evidence;
* secret-bearing state;
* privacy-sensitive state;
* safety-sensitive but not secret state;
* generated/disposable state;
* public/documentation state.

The bounded substrate must also obey the no-silent rules:

* no silent runtime-authority regeneration;
* no silent runtime-authority replacement;
* no silent verified trust promotion;
* no silent identity continuity after loss, reinstall, or restore;
* no silent backup restore over newer state;
* no silent migration;
* no silent algorithm upgrade or downgrade;
* no silent deletion of trust/security-relevant state;
* no ack/drain after failed open or failed join;
* no silent Relay Space membership or routing mutation.

A bounded substrate can help enforce or expose these boundaries later.

It does not itself prove secure storage.

---

## 3. Relationship to the PQ/hybrid placement model

This document also depends on the v0.6.28 PQ/hybrid placement model.

The bounded substrate must reserve room for future:

* algorithm family labels;
* protocol epoch labels;
* PQ/hybrid mode labels;
* migration state labels;
* backup compatibility labels;
* downgrade refusal markers;
* client capability markers.

However, this substrate checkpoint does not implement PQ.

It does not add PQ metadata to runtime state.

It does not change OpenMLS ciphersuites.

It does not change protocol behavior.

It only states that future substrate work must not make algorithm/migration tagging impossible.

    state-boundary-*

    state-audit-dev

The internal planning lane may continue to use:

    vault-substrate-dev

But `vault-substrate-dev` must be understood as a non-production modeling phrase, not a secure vault claim.

### 4.1 Preferred naming

Preferred future names:

* `state-audit-dev`
* `state-boundary-check-dev`
* `state-boundary-inventory-dev`
* `state-boundary-model-dev`

### 4.2 Acceptable internal/docs naming

Acceptable in docs/internal planning:

* bounded state substrate;
* vault-substrate-dev;
* substrate mechanics;
* state-boundary substrate.

### 4.3 Names to avoid

## 5. Current proto-substrate: state-audit-dev

`state-audit-dev` is the current proto-substrate surface.

It should be treated as:

    non-mutating;
    dev-only;
    inventory/check oriented;
    claim-bounded;
    not secure storage;
    not recovery;
    not cleanup;
    not trust verification.

It should not be treated as:

    a vault;
    a backup tool;
    a restore tool;
    a migration tool;
    an encryption layer;
    a production key store;
    a verified trust engine.

### 5.1 Current role

Current role:

* inventory local state-domain surfaces;
* classify Comms state;
* classify trust/candidate state where present;
* classify OpenMLS sidecar generated state;
* classify build output;
* classify local Cypher DB boundaries;
* help readers/operators understand what exists.

### 5.2 Future possible role

Future possible role:

* stronger state-boundary labels;
* explicit model-version output;
* clearer runtime-authority / metadata/evidence distinction;
* clearer dev/generated/secret-bearing labels;
* PQ tag reservation labels;
* no-silent warning labels;
* before/after non-mutation proof in validation profiles.

## 6. Included surfaces v0

The first bounded substrate model may include or inspect the following surfaces.

### 6.1 Comms local state

Include:

* local Comms state JSON path when provided;
* account/device/server binding;
* local state existence;
* local state classification.

Classification:

    runtime authority for account/device/server binding;
    safety-sensitive;
    possibly privacy-sensitive.

No-silent rule:

    no silent replacement, import, or restore over newer state.

### 6.2 OpenMLS sidecar device root

Include:

* sidecar device root;
* sidecar device label;
* signer state existence;
* identity summary existence;
* conversation directory existence.

Classification:

    dev/pre-alpha runtime state container;
    contains secret-bearing and safety-sensitive state;
    not production vault state.

No-silent rule:

    no silent regeneration for existing identity or conversation.

### 6.3 signer.json

Include existence/classification only.

Classification:

    cryptographic identity/signing authority;
    secret-bearing;
    safety-sensitive.

No-silent rule:

    no silent replacement;
    no silent identity continuity claim.

### 6.4 Conversation directories

Include:

* conversation directory existence;
* conversation labels;
* provider-storage existence;
* summary metadata existence;
* join-summary existence where relevant.

Classification:

    runtime authority container for conversation state.

No-silent rule:

    no silent replacement, rename, or merge.

### 6.5 provider-storage.json

Include existence/classification only.

Classification:

    runtime authority for existing conversation message-open;
    secret-bearing;
    safety-sensitive.

No-silent rule:

    no silent regeneration or fallback for existing conversation.

### 6.6 conversation-summary.json

Include existence/classification only.

Classification:

    metadata/evidence;
    safety-sensitive metadata;
    not runtime authority for existing message-open.

No-silent rule:

    no silent promotion to runtime authority.

### 6.7 join-summary.json

Include existence/classification only.

Classification:

    metadata/evidence;
    safety-sensitive join evidence.

No-silent rule:

    no silent promotion to joined-state authority.

### 6.8 Trust and candidate stores

Include if present:

* `trust.json`;
* `trust-events.jsonl`;
* `identity-candidates.json`;
* candidate state paths;
* trust event history paths.

Current classification:

    safety-sensitive now;
    future runtime authority once wired into send/receive/enrollment policy.

No-silent rule:

    no silent trust promotion;
    no silent verified import;
    no silent deletion or rewrite of trust event history.

### 6.9 Generated sidecar roots

Include with hard dev/test labels:

* sidecar `.carbonstack-openmls-sidecar-state`;
* sidecar `target/`;
* generated test/device/conversation roots.

Classification:

    dev/generated state;
    may contain secret-bearing state inside dev scope;
    not production storage;
    not user vault.

No-silent rule:

    cleanup is allowed only when scoped to generated dev/build/test roots.

### 6.10 Runner temp/generated roots

Include only when explicitly scoped to runner/profile output.

Classification:

    generated/disposable validation state;
    may contain privacy-sensitive or safety-sensitive test artifacts.

No-silent rule:

    runner cleanup must stay runner-owned and must not mutate user/deployment state.

## 7. Excluded or deferred surfaces v0

### 7.1 Cypher DB

First posture:

    inventory-only.

Cypher DB is:

    server-side coordination authority;
    delivery/routing authority;
    not message plaintext authority;
    not verified identity authority;
    not first-substrate backup/restore target.

The first substrate may report:

* path exists;
* path missing;
* ignored/dev-local DB detected;
* coordination-authority classification;
* no secure-storage claim.

The first substrate must not:

* backup Cypher DB;
* restore Cypher DB;
* reconcile Cypher DB;
* mutate delivery state;
* mutate Relay Space membership;
* mutate envelope ack state;
* imply hostile-server safety.

### 7.2 Release assets and checksums

Excluded from first substrate.

These belong to release-boundary and package-root validation work.

### 7.3 Backups

Model only.

No backup serialization, backup restore, stale-backup detection, or backup manifest implementation belongs in the first substrate.

### 7.4 PQ state

Reserve labels only.

No PQ implementation, no algorithm migration, no downgrade behavior implementation, and no quantum-safe claim belongs in the first substrate.

### 7.5 Android / CarbonStackOS

Excluded.

CarbonStackOS remains future constrained-appliance planning and is not a current runtime package.

### 7.6 Production deployment state

Excluded.

Deployment state belongs to v0.7.x deployability modeling and later operator docs.

## 9. Refusal and warning behavior

A bounded substrate should prefer:

    report;
    classify;
    warn;
    refuse where relevant;
    do not mutate.

It should not:

    repair silently;
    regenerate silently;
    restore silently;
    migrate silently;
    delete silently;
    promote trust silently;
    downgrade silently;
    ack/drain after failed cryptographic or state operations.

### 9.1 For docs/model-only work

Refusal behavior is specified as a future requirement.

### 9.2 For first inventory/check implementation

The first implementation should:

* print explicit warnings;
* avoid mutation;
* avoid cleanup;
* avoid recovery;
* avoid trust changes;
* avoid backup/restore;
* avoid PQ changes.

### 9.3 For future substrate implementation

Later substrate work may add refusal gates, but only after:

* model acceptance;
* code preflight;
* validation profile design;
* no-silent test expectations;
* command-boundary registry update if needed.

## 11. Registry posture

v0.6.29B does not add a registry entry.

Reason:

* `state-audit-dev` already exists as a registered Comms surface.
* The first model checkpoint should not create command-surface sprawl.
* If a later code patch changes `state-audit-dev` semantics, adds a wrapper, or adds an alias, then registry and generated reference updates may be required.

Current rule:

    no registry mutation for docs-only substrate mechanics.

## 12. Validation posture for future code

If future code lands, validation should prove:

* the command is non-mutating;
* classification labels are stable;
* no secure-vault language appears;
* no backup/restore behavior is present;
* no trust mutation occurs;
* no PQ mutation occurs;
* Cypher is inventory-only;
* generated roots are labeled dev/generated;
* generated command reference remains deterministic if registry changes.

Possible validation ingredients:

* unit tests for classification labels;
* live-dev smoke with generated sidecar state;
* before/after file hash or tree snapshot;
* dirty tree guard;
* nonclaims scan;
* registry reference check if command metadata changes.

---

## 13. First implementation allowance

A first implementation is allowed only if it is narrow.

Allowed:

* inspect state;
* classify state;
* print inventory;
* print warnings;
* preserve nonclaims;
* use existing `state-audit-dev` where possible.

Forbidden:

* encrypt state;
* unlock state;
* backup state;
* restore state;
* migrate state;
* delete state;
* repair state;
* regenerate runtime authority;
* promote trust;
* verify identity;
* mutate Cypher delivery/routing/membership state;
* implement PQ;
* join `full` or `release-snapshot` by default.

---

## 14. Relationship to full naming plan

The `full` / `full-validate-release` / `full-runtime-dev` naming plan should happen after substrate mechanics and before the adversarial harness contract.

Reason:

* substrate mechanics may affect what future `full-runtime-dev` should aggregate;
* package-root validation should remain separate from live-dev runtime aggregation;
* `full` should not silently absorb live-dev or state-substrate checks without explicit release-boundary decision.

Current intended contract remains:

    full = legacy compatibility alias for release-package validation
    full-validate-release = explicit package-root validation
    full-runtime-dev = live-dev runtime aggregation

No implementation happens in this document.

---

## 15. Relationship to adversarial harness contract

The adversarial harness contract should come after substrate mechanics.

Reason:

A useful harness contract needs:

* state categories;
* substrate warning/refusal semantics;
* PQ/migration/downgrade categories;
* backup/rollback categories;
* Relay Space/Cypher coordination categories.

This document prepares those inputs.

It does not implement the harness.

## 18. Summary

The v0.6.29 bounded state substrate position is:

    The first substrate is not a vault.

    The first substrate is not secure storage.

    The first substrate is non-mutating inventory/checking.

    Existing state-audit-dev is the current proto-substrate surface.

    Do not create a duplicate command unless later inspection proves it is needed.

    Cypher is inventory-only at first.

    Sidecar dev state can be inspected, but must be labeled dev/pre-alpha and secret-bearing where appropriate.

    PQ/migration/downgrade tags are reserved as future requirements, not implemented.

    full naming comes after substrate mechanics.
