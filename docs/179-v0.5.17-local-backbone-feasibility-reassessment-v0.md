## 3. Current feasibility result

Local-backbone is not ready to implement yet.

It is now architecture-discussable because:

    state domains have been inventoried;
    storage domains have been modeled;
    trust states have been defined;
    provider-state linkage has been planned;
    provider-originated trust-history append now has a staged helper path;
    provider identity candidate/unverified import has been planned;
    mapped provider identity mismatch behavior has been planned;
    Relay Space boundaries have been defined.

But it is not implementation-ready because:

    candidate identity storage does not exist;
    mapped mismatch behavior is not implemented;
    Relay Space join/invite/member lifecycle is not implemented;
    Relay Space schema/API does not exist;
    runtime provider events are not wired into live app flows;
    Comms send/inbox remain dev/stub-era split surfaces;
    mature reset/recovery/re-enrollment behavior is not designed;
    validation profile boundaries for a local-backbone claim are not yet honest enough;
    vault/PQ ordering is still later work.

## 4. What local-backbone should mean later

A future local-backbone surface should mean a repeatable local system proving the core Comms + Cypher + OpenMLS relay path under an honest validation profile.

It should not mean:

    production security;
    hostile-server safety;
    mature UX;
    metadata privacy;
    public deployment readiness;
    Android readiness;
    CarbonStackOS readiness;
    PQ/hybrid security;
    external audit or certification.

## 5. Minimum future local-backbone requirements

Before local-backbone becomes a profile or release-facing claim, CarbonStack should have:

    clear Relay Space join/invite/member model;
    candidate identity storage or explicit deferral;
    mapped mismatch classification implementation or explicit deferral;
    provider-originated trust history wired only where safe;
    reset/recovery behavior for generated provider state;
    clear ack-after-open behavior preserved;
    known generated-state cleanup boundaries;
    runner profile wording that does not overclaim;
    docs explaining what the profile proves and does not prove.

## 7. Roadmap refresh decision

    the existing roadmap is strategically useful but current-state stale;
