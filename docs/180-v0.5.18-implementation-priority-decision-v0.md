# v0.5.18 implementation-priority decision

Status: roadmap-refresh aftermath / implementation-priority decision record
Phase: v0.5.x post-roadmap-refresh implementation staging
Scope: candidate identity storage priority, implementation sequencing, trust/protocol boundaries
Date: 2026-06-07 local session

## 1. Purpose

v0.5.18 decides the first narrow implementation priority after the v0.5.17 local-backbone feasibility reassessment and roadmap refresh.

This is a decision record only.

v0.5.18 does not implement the chosen spike.

Decision:

    v0.5.19 should target candidate identity storage first.

Preferred implementation direction:

    separate identity-candidates.json;
    owned by carbonstack-comms/internal/trust;
    no trust.json mutation;
    no trust-events append in the first storage spike;
    no send/open/ack behavior change;
    no CLI/registry exposure yet.

## 2. Inputs

This decision follows:

    v0.5.14 provider identity candidate / unverified import plan;
    v0.5.15 mapped provider identity mismatch -> changed/reverify plan;
    v0.5.16 Relay Space architecture decision record;
    v0.5.17 local-backbone feasibility reassessment and roadmap refresh.

v0.5.17 concluded:

    local-backbone is closer, but not implementation-ready.

Major blockers included:

    candidate identity storage does not exist;
    mapped mismatch behavior is not implemented;
    Relay Space join/invite/member lifecycle is not implemented;
    provider event helpers are not wired into live app flows;
    reset/recovery/re-enrollment behavior is not mature;
    validation profile claims would overstate the current system.

## 3. Decision

The next implementation target should be:

    candidate identity draft/storage spike.

The first candidate storage implementation should be narrow.

It should prove:

    candidates can be represented;
    candidates can be saved and loaded;
    obvious duplicate observations can be handled deterministically;
    candidate material does not become verified trust;
    candidate material does not mutate trust.json;
    candidate material does not affect send/open/ack behavior.

## 4. Ownership boundary

Candidate identity storage should live in:

    carbonstack-comms/internal/trust

Rationale:

    candidate identity is local trust-adjacent state;
    it is not provider protocol truth;
    it must be separated from protocol observation/report/draft code;
    it will eventually interact with trust states, trust history, review status, and verification ceremony.

internal/protocol should remain responsible for:

    provider event taxonomy;
    provider trust decisions;
    provider trust reports;
    provider history drafts;
    provider trust-event-compatible drafts.

internal/trust should remain responsible for:

    trust.json;
    trust-events.jsonl;
    identity-candidates.json later;
    trust state;
    candidate state;
    local trust-adjacent persistence.

## 5. Storage decision

Preferred first storage file:

    identity-candidates.json

Preferred first shape:

    JSON object containing an identity_candidates array.

Rationale:

    candidate identities are state, not append-only history;
    candidates need load/save, dedupe, update, review, rejection, and possible later promotion;
    JSONL is better for append-only history, not current candidate state;
    a separate file reduces the chance that candidate material is mistaken for verified trust-store truth.

## 6. Initial candidate states

Initial state set should stay small:

    observed
    pending_review
    unverified
    conflicts_known_device
    rejected

Do not include verified promotion states yet.

Deferred states may include:

    stale;
    promoted_to_unverified;
    promoted_to_verified_by_ceremony.

Rationale:

    verified promotion should not exist until verification ceremony and storage/vault boundaries are better defined.

## 7. Raw identity material policy

The first dev implementation may store raw candidate public identity material.

This is allowed only as dev/pre-alpha local state.

It must be clearly documented as:

    sensitive-ish;
    future-vault-bound;
    not production-safe;
    not a public deployment claim.

Candidate records should also store a fingerprint for comparison/display.

Future vault work may decide:

    raw identity material belongs in a vault domain;
    fingerprints can remain visible outside the vault;
    candidate export/import needs stricter handling.

## 8. Dedupe policy

First implementation should use simple deterministic dedupe.

Preferred dedupe key:

    claimed_device_id + fingerprint + source

If claimed_device_id is blank:

    fingerprint + source

Do not attempt complex identity reconciliation in the first spike.

Dedupe should prevent obvious repeated candidate observations from creating unbounded duplicate records.

## 9. First implementation exclusions

v0.5.19 candidate storage spike should not:

    mutate trust.json;
    append trust-events.jsonl;
    mark any device verified;
    mark any device changed;
    replace existing device key material;
    affect send policy;
    affect open policy;
    affect ack policy;
    wire live provider import;
    expose CLI;
    update registry;
    implement verification ceremony;
    implement vault encryption;
    implement Relay Space join;
    create local-backbone.

## 10. Verify stub decision

Do not add a verify stub yet.

Reason:

    verify wording is dangerous before ceremony/storage/vault behavior is designed;
    a stub command could make verification appear more real than it is;
    registry entries should correspond to actual command/profile/script/API surfaces.

A future verify-stub or dev-only verification command may be considered after:

    candidate storage exists;
    candidate review semantics are clearer;
    mapped mismatch classifier exists or is planned in enough detail;
    verification ceremony boundary is documented;
    registry update can accurately describe nonclaims.

## 11. Research fallback

If candidate identity storage becomes too tangled, use a fallback path:

    either transition to trust.json unverified records with loud boundaries;
    or create an unstable/non-production research folder to prototype candidate models.

Possible research folder shape:

    carbonstack-comms/internal/trust/research/*

Research folder rules:

    unstable;
    non-prod;
    not release-facing;
    used only to learn an implementation shape;
    lessons must be brought back into mainline deliberately.
