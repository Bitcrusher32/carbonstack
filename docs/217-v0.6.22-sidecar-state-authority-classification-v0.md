# CarbonStack v0.6.22 Sidecar State Authority Classification v0

Status: docs/model checkpoint after stale sidecar/conversation/provider state recon.

## Purpose

v0.6.22 classifies which OpenMLS sidecar-generated state files are runtime authority for existing conversation message-open behavior, which files are metadata/evidence, and which files belong to identity/bootstrap rather than existing-conversation runtime authority.

This checkpoint exists because v0.6.20 and v0.6.21 proved that sidecar state behavior can affect correctness and recovery. The stale-state recon then tested whether missing, corrupt, or moved sidecar state can cause false open, accidental ack, inbox drain, or silent state repair.

## Inputs

The classification comes from v0.6.22A and v0.6.22B recon.

v0.6.22A first exposed the split:

    conversation provider-storage.json and missing conversation directory blocked open/ack/drain;
    conversation-summary.json, join-summary.json, and device-level provider-storage.json did not block message-open/ack.

v0.6.22B then refined the authority model and reported:

    cases_total: 12
    critical_runtime_bypass_cases: 0
    cases_with_target_rewrite_or_regeneration: 0

## Runtime-authoritative state

The following are runtime authority for existing conversation message-open behavior:

    conversation-level provider-storage.json
    final conversation directory

Observed behavior:

    deleting conversation provider-storage.json blocked message-open and prevented ack/drain;
    invalid conversation provider-storage.json blocked message-open and prevented ack/drain;
    truncated conversation provider-storage.json blocked message-open and prevented ack/drain;
    moving the final conversation directory blocked message-open and prevented ack/drain.

This is the desired safety shape.

Runtime-authority mutation should not be silently repaired by message-open or load-check.

## Metadata / evidence state

The following are currently metadata/evidence for existing conversation message-open behavior:

    conversation-summary.json
    join-summary.json

Observed behavior:

    deleting join-summary.json did not block message-open/ack;
    invalid join-summary.json did not block message-open/ack;
    valid-but-wrong join-summary.json did not block message-open/ack;
    invalid or valid-but-wrong conversation-summary.json did not block message-open/ack.

No tested summary mutation silently regenerated or rewrote the mutated target.

## Load-check mismatch

`conversation-summary.json` has one important command-semantics mismatch:

    deleting conversation-summary.json makes conversation-load-check-dev fail;
    message-inbox-dev --ack can still open and ack a valid queued message when provider-storage.json remains valid.

This means `conversation-load-check-dev` is currently stricter than message-open for missing conversation-summary metadata.

The current model should treat this as a command-semantics/documentation issue, not a runtime no-ack/no-drain bug.

Future cleanup may choose one of these options:

    rename or clarify load-check as "provider reload + metadata presence check";
    split provider reloadability from metadata integrity checks;
    add warnings when metadata is missing or malformed but provider storage remains usable;
    add a dedicated metadata-state-check command.

Do not treat conversation-summary.json as cryptographic runtime authority unless a future design explicitly changes that model.

## Device-level provider storage

Device-level provider-storage.json is currently identity/bootstrap substrate for bundle/join flows, not existing conversation runtime message-open authority.

Observed behavior:

    deleting device-level provider-storage.json did not block message-open/ack for an already joined conversation;
    invalid device-level provider-storage.json did not block message-open/ack for an already joined conversation.

This does not mean device-level provider state is unimportant. It means it was not required for existing conversation message-open in this recon.

Future vault/security modeling must distinguish:

    identity/bootstrap state;
    existing conversation runtime state;
    generated evidence/summary metadata;
    Relay/Cypher envelope and ack state.

## Silent regeneration / repair

The v0.6.22B recon reported:

    cases_with_target_rewrite_or_regeneration: 0

No tested load-check or message-inbox path silently regenerated or rewrote the mutated target state.

This is important because silent repair could hide state corruption or blur authority boundaries.

## Patch posture

Do not patch message-open to block on summary metadata merely because summary metadata can be corrupted or deleted.

Do patch later if any future recon finds:

    runtime provider storage bypass;
    final conversation directory bypass;
    silent regeneration/replacement of state;
    ack on failed open;
    inbox drain on failed open;
    false message-open success.

## Future profile posture

Do not add a committed stale-state runner profile until the intended command semantics are settled.

Possible later profile:

    same-state-stale-provider-state-dev

Likely profile scope, if added later:

    provider-storage missing/corrupt/truncated;
    conversation dir missing;
    no open;
    no ack;
    no inbox drain;
    no silent repair.

Summary metadata cases should either be excluded from that runtime-authority profile or included as explicit metadata non-authority cases, not mixed ambiguously.

## Relationship to full-* aggregation

This is a model checkpoint, not a `full-*` aggregation checkpoint.

Later `full-runtime-dev` or contextual `full-*` evaluators may call stale-state profiles after explicit aggregation policy exists.

Do not fold this into current `full` or `release-snapshot`.
