# CarbonStack v0.6.24 Load-Check Semantics and Replay Classification v0

Status: docs/model and profile checkpoint after v0.6.24A load-check semantics plus normal application-message replay recon.

## Scope

v0.6.24 records two related classifications:

1. `conversation-load-check-dev` remains stricter than `message-inbox-dev` when `conversation-summary.json` is missing.
2. Normal application-message duplicate/replay behavior is classified by the committed profile:

       go run . --profile same-state-message-replay-classification-dev --root <umbrella root> --clean-generated

## Load-check semantic classification

v0.6.24A recon reproduced the v0.6.22 semantic mismatch:

    missing conversation-summary.json
    -> conversation-load-check-dev fails
    -> message-inbox-dev --ack can still open and ack a valid queued message when conversation provider-storage.json remains valid

Classification:

    load_check_stricter_than_message_open_summary_metadata_missing

Current model:

    conversation provider-storage.json is runtime authority for existing message-open;
    final conversation directory is the runtime authority container;
    conversation-summary.json is metadata/evidence for existing message-open;
    conversation-load-check-dev currently checks metadata presence more strictly than message-open.

This is not a no-ack/no-drain bug.

Do not patch message-inbox-dev to block on summary metadata unless a future design explicitly makes summary metadata runtime authority.

Future cleanup options:

    clarify conversation-load-check-dev output;
    split provider reloadability checks from metadata presence/integrity checks;
    add metadata warnings;
    add a dedicated metadata-state-check command.

## Replay classification profile

Added profile:

    same-state-message-replay-classification-dev

Added registry ID:

    runner.same-state-message-replay-classification-dev

The profile covers normal application-message envelopes only.

Covered cases:

    duplicate same envelope_id insert attempt;
    same envelope after ack without requeue;
    same envelope manually requeued after ack;
    duplicate same ciphertext under new envelope_id before original ack;
    duplicate same ciphertext under new envelope_id after original ack.

## Expected classifications

### Duplicate same envelope ID

Expected classification:

    storage_rejected_duplicate_same_envelope_id_original_recovery_ok

Meaning:

    storage/DB uniqueness rejects a duplicate envelope_id;
    the original queued message can still open and ack.

Nonclaim:

    this is storage-level rejection, not protocol-level replay safety.

### Same envelope after ack without requeue

Expected classification:

    delivery_state_suppressed_same_envelope_after_ack

Meaning:

    after a successful open/ack, the same envelope is no longer queued;
    a second message-inbox-dev pass sees no queued envelope and does not re-open or re-ack.

Nonclaim:

    this is delivery-state suppression, not hostile-relay replay safety.

### Same envelope manually requeued after ack

Expected classification:

    detected_or_rejected_no_ack_no_drain_manual_requeue_same_envelope

Meaning:

    if a previously acked normal application-message envelope is manually forced back to queued, OpenMLS rejects the second open;
    no second ack is created;
    the queued replay is not drained.

Observed failure family:

    SecretReuseError

Nonclaim:

    this is deterministic local replay classification, not a complete malicious-server policy.

### Duplicate payload under new envelope ID before original ack

Expected classification:

    detected_or_rejected_no_ack_no_drain_duplicate_payload_new_envelope_before_ack

Meaning:

    when the same ciphertext is duplicated under a different envelope ID while both are queued, the first valid envelope can open/ack;
    the duplicate fails open;
    no second ack is created;
    the duplicate remains queued.

Observed failure family:

    SecretReuseError

### Duplicate payload under new envelope ID after original ack

Expected classification:

    detected_or_rejected_no_ack_no_drain_duplicate_payload_new_envelope_after_ack

Meaning:

    after the original envelope opens/acks, inserting the same ciphertext under a new envelope ID fails open;
    no extra ack is created;
    the duplicate remains queued.

Observed failure family:

    SecretReuseError

    KeyPackage replay handling;
