# CarbonStack Identity and Trust State v0

## Status

Classification: DRAFT / PHASE 2 FOUNDATION

This document defines the CarbonStack identity and trust-state model that future protocol integration must satisfy.

This document does not select a cryptographic protocol. It defines the application-level trust semantics that any candidate protocol must support.

## Purpose

CarbonStack needs a clear identity and trust model before applying Signal, MLS, Noise, or any other cryptographic foundation.

Protocols can provide cryptographic mechanisms. They do not automatically define CarbonStack's user experience, device ceremonies, trust history, revocation behavior, or compromise recovery model.

## Core Rule

The server must not be a source of identity truth.

CarbonStackCypher may route records, store encrypted envelopes, and publish device/key material, but clients must treat server-provided identity state as untrusted until verified through local trust rules.

## Entity Model

### Human User

A human operator or participant.

The human user is not directly trusted by server account ID alone.

### Account

A server-side namespace used for routing, invites, and device listing.

Account IDs are not cryptographic identity.

Account IDs may be useful for:

- delivery routing
- invite claim records
- device discovery
- operator debugging
- small-community administration

Account IDs must not be treated as proof of message authorship.

### Device

A client instance capable of sending and receiving CarbonStackComms messages.

A device has:

- device ID
- account ID
- device label
- device identity key material
- trust state
- creation/enrollment time
- revocation state

In Phase 1, device identity is stubbed.

In Phase 2, device identity must become cryptographic and locally verifiable.

### Contact

A locally stored view of another account/device relationship.

A contact may contain:

- display label
- account ID
- one or more known devices
- local trust state
- first-seen time
- last-seen time
- trust history entries
- warnings or unresolved changes

### Group

Deferred beyond initial Phase 2.

Groups require explicit membership state, epochs, device membership records, and rollback/tamper detection.

## Device Identity Model

Each device should eventually have a long-term identity key or protocol-equivalent identity credential.

Required properties:

- generated client-side
- not generated by server
- not silently replaceable by server
- locally persisted in a secure vault in later phases
- visible to other clients through safety number, fingerprint, QR ceremony, or equivalent
- key changes produce loud warnings

## Trust States

Suggested local trust states:

### unknown

The device exists according to server records, but the local client has not evaluated it.

### unverified

The device has been seen and stored locally, but no verification ceremony has occurred.

### verified

The user has explicitly verified the device identity through an approved ceremony.

### changed

A known device identity changed or a server-provided identity record conflicts with local trust history.

This must be loud.

### revoked

The device has been revoked by a trusted revocation event or local user action.

### compromised

The user has marked the device as compromised.

This may imply forced re-verification, group removal, and future message rejection.

## Trust History

Trust decisions should be append-only from the client's perspective.

A trust history entry may include:

- event ID
- event type
- account ID
- device ID
- previous trust state
- new trust state
- observed key fingerprint
- event time
- source of event
- user confirmation state

Example event types:

- device_first_seen
- device_verified
- device_key_changed
- device_revoked
- device_marked_compromised
- device_reenrolled
- server_record_conflict
- group_membership_changed

## Key Change Policy

Key changes must never be silent.

When a known device identity changes, the client should:

- mark the device as changed
- stop treating the device as verified
- display a warning before sending
- require re-verification before restoring verified trust
- preserve the old trust history

The server must not be able to erase the old local trust record.

## Device Enrollment Policy

Phase 2 should support explicit device enrollment semantics even if hardware-key enrollment is deferred.

Minimum required behavior:

- new device appears as unverified
- existing contacts see new device as new/unverified
- adding a device does not silently inherit trust from account ID
- device labels are user-facing hints, not trust anchors

Future target:

- QR ceremony
- hardware-key approval
- existing-device approval
- trust-history entry for enrollment

## Device Revocation Policy

Revocation must be visible and persistent.

Minimum required behavior:

- revoked device is not treated as valid for new outgoing messages
- messages from revoked devices are flagged or rejected depending on policy
- revocation appears in trust history
- revocation cannot be silently undone by server state

Future target:

- hardware-key-signed revocation
- group-visible revocation event
- forced group epoch change
- re-enrollment ceremony after recovery

## Account Recovery Policy

Account recovery must not imply message recovery.

If a user loses a device key, old message access should not be recoverable unless an explicit encrypted backup design exists.

Recovery may restore:

- account namespace
- ability to enroll a new device
- ability to publish revocation after network access returns

Recovery must not silently restore:

- old private identity keys
- old message plaintext
- old verified trust without warning

## Server Conflict Policy

If server records conflict with local trust history, local history wins.

Examples:

- server presents a new key for a verified device
- server removes a known device without trusted revocation
- server reintroduces a revoked device
- server rolls back device listing state

Client response should be conservative:

- mark conflict
- warn user
- block or degrade sending
- require explicit local action

## Phase 2 Minimal Local State

Phase 2 local trust state should include at least:

- account records
- device records
- identity fingerprints
- trust states
- trust history
- outbound send policy
- local warnings

This can begin as plaintext development state only if clearly marked insecure.

Secure vault storage remains a later hardening step.

## Protocol Integration Requirements

Any selected protocol must allow CarbonStack to represent:

- stable device identity
- session establishment
- local trust state
- visible key changes
- device revocation
- replay protection
- offline delivery
- future group membership transitions
- test vectors or reproducible harness behavior

## Non-Goals

This document does not implement:

- real cryptography
- secure local vault
- hardware-key enrollment
- Android Keystore integration
- group epochs
- MLS state
- libsignal sessions
- hostile-server harness
