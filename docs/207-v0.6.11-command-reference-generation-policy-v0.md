# CarbonStack v0.6.11 Command Reference Generation Policy v0

Status: docs/planning checkpoint
Scope: command reference / man-generation policy, registry hardening plan
Checkpoint target: v0.6.11
Public release impact: none; current public release remains v0.6.0 State/UX Boundary Validation Pre-Release

## 1. Purpose

This document records the v0.6.11 command reference generation policy after two command-reference recons.

It does not generate a command reference.

It does not generate man pages.

It does not mutate `full`, `release-snapshot`, `integrated-runtime-dev`, runtime profiles, Comms commands, Cypher APIs, or sidecar behavior.

The goal is to prevent polished-looking command docs from over-promoting incomplete or underdocumented dev/internal surfaces.

## 2. Current decision

Do not generate `COMMAND_REFERENCE.v0.md` yet.

Do not generate Unix man pages yet.

Before generation, perform a registry hardening pass that makes risky or underdocumented rows explicit enough for professional dev/tester-facing documentation.

Preferred future order:

    v0.6.11: command reference generation policy and registry hardening plan
    v0.6.12: registry hardening implementation pass
    v0.6.13 or later: first generated Markdown command reference if registry quality is sufficient

Man pages remain later.

## 3. Why not generate now

The v0.6.11 command-reference recon found the registry is useful, but not generator-ready.

Observed generation blockers:

    registry_entry_count: 79
    opaque_or_underidentified_count: 69
    missing nonclaims: 33 entries

Common gap classes:

    missing nonclaims;
    missing validation_surface;
    missing explicit flag metadata;
    missing lifecycle_status on risky command/profile surfaces;
    internal sidecar commands needing real-function summaries;
    Cypher API surfaces needing explicit API boundary wording;
    historical scripts needing demotion wording;
    generated-vs-hand-maintained boundary still not written down.

This is not a runtime blocker. It is a documentation-source-of-truth blocker.

## 4. Markdown first, not man pages

The first generated reference should be Markdown, not Unix man pages.

Preferred future output name:

    registry/COMMAND_REFERENCE.v0.md

Reason:

    Markdown fits the current repo and release-package shape.
    Markdown is easier to label as dev/operator reference.
    Unix man pages imply installability, polished CLI semantics, and stronger stability than the current dev/pre-alpha command surface deserves.

Man pages should wait until command names, flags, examples, and installation assumptions are materially more stable.

## 5. Boundary table policy

Keep this file hand-maintained for now:

    registry/COMMAND_BOUNDARY_TABLE.v0.md

Do not replace it with generated output in v0.6.11.

Reason:

    The boundary table is a compact classification artifact.
    It has narrative compression and release-boundary language that may not map one-to-one from `commands.v0.yaml`.
    A generated command reference can be added beside it later without disturbing the table.

Future possibility:

    Once `COMMAND_REFERENCE.v0.md` exists and the registry schema is stronger, reconsider whether parts of the boundary table should become generated or regression-checked from the registry.

## 6. Registry as source-of-truth, but only after hardening

The intended source for future command reference generation is:

    registry/commands.v0.yaml

However, registry presence is classification, not promotion.

A generated reference must preserve:

    audience;
    maturity;
    kind;
    lifecycle_status where relevant;
    validation_surface;
    source_path;
    related rows;
    replacement rows;
    required flags;
    optional flags;
    environment variables;
    nonclaims;
    inclusion/exclusion from front README;
    release-package/live-root boundaries.

Missing field data must not be rendered as “none” unless that is explicitly known.

## 7. Future generated reference scope

A future generated Markdown reference may include all registry entries, but only if heavily grouped.

Recommended section classes:

    1. Release/package validation profiles
    2. Public/diagnostic runner profiles
    3. Live-dev runtime profiles
    4. Recommended dev/pre-alpha normal-message wrappers
    5. Lower-level direct OpenMLS proof commands
    6. Relay onboarding artifact commands
    7. OpenMLS bootstrap/member commands
    8. Trust/state/dev account commands
    9. Legacy stub-era commands
    10. Historical scripts
    11. Internal sidecar commands
    12. Cypher server/API surfaces
    13. Future/unsupported placeholders

The generated reference should make public/dev/internal/legacy/future status impossible to miss.

## 8. Nonclaim formatting policy

Every generated command section should carry a short warning block when any of these apply:

    dev_only;
    legacy;
    internal;
    future;
    not included in full;
    not included in release-snapshot;
    not release-package validation;
    not package-root validation;
    not production secure messaging;
    not production E2EE;
    not hostile-server safety;
    not metadata privacy;
    not identity verification;
    not secure enrollment;
    not local-backbone;
    not deployment readiness;
    not mature UX.

Recommended generated format:

    Boundary:
      <one sentence from registry short_help / why_exists / lifecycle>

    Scope:
      audience: ...
      maturity: ...
      kind: ...
      validation: ...

    Not claims:
      - ...
      - ...

Avoid burying nonclaims in long paragraphs.

## 9. Registry hardening pass required before generation

The next implementation rung should harden registry data before generating docs.

Minimum targets:

    runner profiles:
      add explicit optional flags / environment where appropriate;
      add lifecycle_status to risky profiles;
      clarify full vs release-snapshot vs integrated-runtime-dev.

    Comms CLI:
      add flag metadata for real current flags;
      add missing nonclaims for state/account/trust commands;
      add lifecycle_status for risky trust/state/OpenMLS bootstrap commands;
      keep legacy demotion wording explicit.

    Relay/OpenMLS:
      preserve artifact/message separation;
      preserve ack doctrine;
      classify bootstrap/member commands without treating them as normal-message UX.

    Sidecar CLI:
      add validation_surface;
      add nonclaims;
      classify internal-only surfaces;
      classify unsupported/future placeholders.

    Cypher API:
      add validation_surface;
      add nonclaims;
      mark API surfaces as dev/internal-ish infrastructure, not stable public API;
      distinguish core envelope API from Relay Space artifact API.

    Scripts:
      identify historical PowerShell scripts as legacy continuity surfaces;
      identify staging/rehearsal scripts as release-helper scripts;
      include destructive/temp-root boundaries where scripts remove staged roots.

## 10. Known high-risk categories from recon

Do not generate polished docs for these until hardening is complete:

    sidecar.* rows with missing validation_surface/nonclaims;
    cypher.api.* rows with missing validation_surface/nonclaims;
    historical PowerShell script rows;
    Comms state/trust/dev-account commands with missing nonclaims;
    runner/full/release-snapshot/integrated-runtime-dev rows unless the full/package/live-root boundary is explicit;
    commands whose help flags are not reflected in registry flag metadata.

## 11. Future generator behavior

A future generator should be deterministic and checked in only after its policy is stable.

Preferred shape:

    input:
      registry/commands.v0.yaml

    output:
      registry/COMMAND_REFERENCE.v0.md

    generator location:
      tools/carbonstack-validate or carbonstack/scripts, to be decided during implementation

    validation:
      go test ./... for registry parsing;
      generator output is stable;
      missing required generation fields fail tests for included sections;
      generated reference includes visible nonclaims;
      generated reference does not replace COMMAND_BOUNDARY_TABLE.v0.md;
      generated reference does not get copied to release/ without explicit package decision.

## 12. Man page deferral

Do not generate man pages until:

    Markdown reference exists and is stable;
    command examples are reliable;
    install/run assumptions are documented;
    dev-only/internal/legacy commands have safe grouping;
    package-root vs live-umbrella boundaries are encoded;
    the project actually wants installable CLI docs.

Until then, man pages risk over-polishing pre-alpha surfaces.

## 13. Relationship to v0.6.10 integrated-runtime-dev

`integrated-runtime-dev` now exists and must appear in future generated reference as:

    live-dev runtime profile;
    composition profile;
    proof: relay-openmls-join-dev -> dev-runtime-openmls-wrappers;
    live umbrella only;
    not full;
    not release-snapshot;
    not package-root validation;
    not production/security proof;
    not same-state same-conversation UX proof.

Do not merge it into `full`.

Do not describe it as release-facing validation.

## 14. Relationship to full and release-snapshot

Future generated docs must preserve:

    full:
      release-package validation ladder;
      release-snapshot -> local-cypher;
      intended for fresh extracted or throwaway staged package roots.

    release-snapshot:
      package layout/checksum/core validation;
      package-root boundary;
      not integrated runtime.

    integrated-runtime-dev:
      live-umbrella dev composition profile;
      not package-root validation;
      not release validation.

This separation is mandatory.

## 15. Acceptance criteria for a future generated reference

Before generating and committing `registry/COMMAND_REFERENCE.v0.md`, require:

    no risky generated section without nonclaims;
    no internal/API generated section without validation_surface;
    every included Comms CLI row has usable flag metadata or is explicitly marked as flag metadata incomplete;
    every runner profile explains root expectations;
    full/release-snapshot/integrated-runtime-dev are separated;
    legacy scripts are clearly demoted;
    sidecar commands are internal-only;
    Cypher API surfaces are not presented as stable public API;
    generated output is deterministic;
    tests prevent stale/malformed registry shape.
