# v0.5.32 provider live-flow boundary

Status: provider live-flow boundary planning record
Phase: v0.5.x post-Relay-Space-planning / pre-validation-profile planning
Scope: provider/OpenMLS live-flow wiring, Relay Space dependency, Comms trust boundary, Cypher downstream substrate
Date: 2026-06-08 local session

## 1. Purpose

v0.5.32 defines the provider/OpenMLS live-flow wiring boundary after the v0.5.31 Relay Space join/invite/member planning record.

This is a planning record only.

v0.5.32 does not implement:

    provider live-flow wiring;
    Relay Space schema;
    Relay Space API routes;
    Relay Space join flow;
    Cypher schema changes;
    Comms client wrapper changes;
    validation profile changes;
    CLI/registry entries;
    local-backbone;
    destructive reset/recovery;
    backup/restore;
    re-enrollment mutation;
    vault;
    PQ/hybrid crypto.

Decision:

    provider live-flow should not be broadly wired next.
    provider live-flow depends on Relay Space schema/API substrate.
    the first future implementation after the planning/go-no-go sequence should likely be Cypher Relay Space schema/API, not broad Comms live-flow.
    Comms live-flow must preserve candidate/review/recovery/trust boundaries.
    provider observation must not verify identity.
    provider observation must not mutate trust.json by itself.
    ack must remain sidecar-open/consume gated.
    v0.5.33 should be validation profile boundary planning.

## 2. Current doctrine carried forward

v0.5.31 established:

    Relay Space is a vector to OpenMLS join and a routing/conversation container.
    Relay Space is not local trust.
    OpenMLS/provider join is cryptographic group participation.
    Local verification is the actual trust/auth/presence decision.
    Cypher may store routing membership.
    Cypher must not become identity authority.
    Comms remains local trust/candidate/recovery authority.

v0.5.32 applies that doctrine to provider/OpenMLS live-flow wiring.

## 3. Provider live-flow definition

Provider live-flow means runtime wiring between Comms application/client flows and OpenMLS/provider sidecar operations.

Relevant provider operations include:

    identity create/load/status;
    public bundle / KeyPackage export;
    conversation/group create;
    member add;
    Welcome creation;
    Welcome consume/join;
    message protect;
    message open;
    storage/checkpoint behavior;
    provider event/report emission;
    provider trust classification;
    candidate identity observation;
    trust-history append where explicitly safe.

Current dev surfaces already prove parts of the OpenMLS lifecycle, but that is not the same as a mature provider live-flow.

## 4. Why broad live-flow wiring is not next

Broad provider live-flow wiring is still premature because:

    Relay Space schema/API does not exist;
    Relay Space join/invite/member implementation does not exist;
    routing membership is not yet represented as a first-class server substrate;
    validation profile claims are not defined;
    cleanup/reset boundaries for generated provider state are not mature enough;
    provider observations still must not verify identity;
    send/open/ack behavior must not be weakened;
    mature verification UX does not exist;
    CLI/registry exposure would overstate maturity.

Therefore the next implementation should not be:

    broad provider event import;
    automatic candidate promotion;
    automatic trust.json mutation;
    automatic local-backbone profile;
    automatic Relay Space join;
    automatic OpenMLS group trust.

## 5. Smallest safe future wiring shape

The smallest safe future provider live-flow should be narrow and staged.

Preferred future order:

    Cypher Relay Space schema/API substrate;
    Comms client wrappers for Relay Space APIs;
    provider/OpenMLS join wiring against explicit Relay Space artifacts;
    candidate observation handoff only when identity material is actually present;
    recovery/trust safety checks before trust-sensitive operations;
    validation-profile planning and implementation only when claim-safe.

A safe provider live-flow may:

    call sidecar operations;
    produce provider events;
    build provider trust reports;
    build provider trust-history/event drafts;
    append explicitly selected trust-history events;
    observe candidate identity material;
    classify mapped mismatch;
    classify recovery state;
    block or warn on unsafe state;
    preserve ack-after-open.

A safe provider live-flow must not:

    mark identity verified;
    mutate trust.json from provider observation alone;
    silently replace known key material;
    bypass candidate review;
    bypass recovery classification;
    weaken send/open/ack behavior;
    trust Cypher routing membership as identity;
    trust Relay Space membership as identity;
    treat provider membership as local verification.

## 6. Relay Space dependency

Provider live-flow should wait for Relay Space schema/API substrate because provider join has to be anchored to routable server/conversation mechanics.

Relay Space implementation should likely provide:

    relay_spaces table;
    relay_space_invites table;
    relay_space_members table;
    relay_space_id-scoped envelope routing;
    create/list/get Relay Space APIs;
    invite create/claim APIs;
    routing member registration/list APIs;
    Relay Space-scoped envelope submit/retrieve/ack APIs.

These are routing primitives.

They must not create verified trust.

## 7. Candidate and trust interaction

Provider live-flow may eventually surface identity material.

That material should enter:

    candidate identity storage;
    candidate review/update;
    mapped mismatch classifier;
    candidate/mismatch history events;
    candidate observation orchestration;
    recovery classification/orchestration.

It must not enter:

    verified trust directly;
    trust.json mutation directly;
    key replacement directly;
    local verified device status directly.

Core rule:

    provider-observed identity material is candidate/unverified material until local verification says otherwise.

## 8. Recovery interaction

Provider live-flow must account for recovery state.

Unsafe recovery classifications should block or warn before trust-sensitive operations.

Examples:

    missing trust store:
      do not claim continuity or verified trust.

    corrupt trust store:
      block trust-sensitive promotion and trusted send/open paths.

    requires reverify:
      allow candidate observation and diagnostics, but block trusted promotion.

    blocked revoked or compromised:
      block promotion and trusted send.

Recovery-history append is not recovery execution.

Recovery orchestration is not destructive reset.

## 9. Ack boundary

Provider live-flow must preserve ack-after-open:

    Relay Space routing membership is not enough;
    invite claim is not enough;
    envelope retrieval is not enough;
    artifact write is not enough;
    provider report generation is not enough;
    trust-history append is not enough;
    candidate observation is not enough;
    recovery classification is not enough;
    only successful sidecar message-open/consume may permit ack unless a later negative-ack/quarantine design is explicitly created.

v0.5.32 does not create negative ack.

## 10. Cypher boundary

Cypher may eventually store and route Relay Space-scoped artifacts.

Cypher may provide:

    routing membership;
    invite claim;
    device registration/lookup;
    Relay Space-scoped envelope queues;
    ack state;
    operational metadata.

Cypher must not provide:

    verified identity;
    local trust state;
    provider safety truth;
    local verification result;
    key replacement authority;
    trust.json mutation authority.

Provider live-flow should treat Cypher outputs as routing inputs, not trust truth.

## 11. Comms boundary

Comms owns:

    local identity state;
    local trust state;
    local trust history;
    candidate identity state;
    mismatch classification;
    recovery classification/orchestration;
    provider event classification;
    provider trust reports/history;
    send/open/ack policy;
    future verification UX.

Provider live-flow belongs under Comms policy, not under Cypher authority.

## 12. Validation profile implication

v0.5.33 should define validation profile boundaries before any local-backbone-style implementation.

A future profile must answer:

    what is proved;
    what is not proved;
    whether it requires live git umbrella;
    whether it can run from release packages;
    what generated state it creates;
    what cleanup is safe;
    what trust/candidate/provider state it touches;
    what claims are forbidden even when it passes.

Do not add a local-backbone profile in v0.5.32.

## 13. CLI / registry implication

Do not add CLI or registry entries yet.

Existing dev commands may remain documented, but provider live-flow/Relay Space/local-backbone command exposure should wait until:

    Relay Space schema/API exists;
    validation profile boundary exists;
    local-backbone go/no-go is complete;
    command semantics are honest;
    cleanup/reset safety is clear.

## 14. Recommended next rungs

Recommended sequence:

    v0.5.33 validation profile boundary planning;
    v0.5.34 local-backbone go/no-go reassessment;
    v0.5.35 cleanup / roadmap refresh / possible dev-only CLI-registry prep;
    v0.5.36+ first narrow implementation if claim-safe, likely Cypher Relay Space schema/API before Comms broad provider live-flow.
