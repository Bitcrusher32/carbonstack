# CarbonStack v0.7.1 Gate A Operational Workflow Contract v0

Status: accepted architecture and workflow contract
Checkpoint: v0.7.1 Breakpoint 1
Target release: v0.8.0 Operational Spine Maturation Pre-Release
Scope: planning and contract authority before implementation

## 1. Purpose

This document closes the Gate A design decision package for the v0.7.x operational-spine integration epoch.

It defines:

- the preferred operator lifecycle;
- explicit workspace and operator context;
- workflow ownership;
- preferred Relay-scoped normal messaging;
- identity-domain separation;
- mutation classifications;
- structured partial-completion results;
- acknowledgement discipline;
- Relay membership authority;
- Cypher-membership and MLS-membership mismatch behavior;
- state-path, concurrency, atomicity, and no-silent policy;
- validation-surface separation;
- the future full-operational-spine-dev aggregate classification.

This document does not implement the workflow engine, runner aggregate, Relay enforcement, state locking, migration, deployment, TUI, containers, PQ support, Android, or CarbonStackOS.

## 2. Gate A acceptance status

The Gate A positions A1 through A12 are accepted.

The accepted lifecycle contract is now durable project direction.

Implementation remains dependency ordered:

    accepted contract
      -> normalize live workflow and state maps
      -> select one narrow leaf
      -> implement and validate leaf behavior
      -> converge Relay lifecycle
      -> enforce state boundaries
      -> add aggregate only after leaf stability

## 3. Preferred operator lifecycle

The preferred lifecycle is:

    inspect environment
      -> initialize or select workspace
      -> load explicit operator context
      -> inspect local and server state
      -> create or select Relay Space
      -> register or select device
      -> perform explicit onboarding stages
      -> inspect compatibility and membership
      -> send, receive, open, and acknowledge messages
      -> stop and restart dependencies
      -> resume and re-inspect state
      -> explicitly reset only scoped development state

The lifecycle must eventually be represented in the command table under a full-prefixed validation classification.

The accepted future classification name is:

    full-operational-spine-dev

This name is a future registry and command-table placeholder only.

It is not currently implemented.

The aggregate must not be implemented before the underlying leaf workflows are stable.

The aggregate must not silently execute every development profile.

Internal and leaf calls must remain:

- documented;
- independently inspectable;
- directly callable where mechanically appropriate;
- separately testable;
- separately classifiable by mutation and evidence type.

## 4. Operator context model

The preferred lifecycle uses an explicit and inspectable workspace context.

Minimum context fields:

    schema_version
    context_id
    server_url
    account_id
    device_id
    comms_state_root
    openmls_state_root
    relay_space_id
    conversation_id
    capability_domain
    environment_classification
    created_at
    updated_at

Rules:

- Current working directory must not silently grant authority.
- Hidden files must not silently select a device, account, Relay Space, or conversation.
- Environment-variable overrides must be explicitly reported.
- Human labels are aliases and not identity proof.
- Secrets are not stored in the context file by default.
- Mutating workflows must expose the resolved context before mutation or provide a distinct inspect phase.
- Unknown or unsupported context schema must refuse safety-sensitive mutation.

## 5. Workflow ownership

Accepted ownership:

    cmd/comms
      argument parsing
      presentation
      exit-code mapping

    internal/app or a future internal/workflow package
      lifecycle orchestration
      precondition evaluation
      mutation declaration
      structured workflow result
      refusal classification

    internal/relay
      Cypher transport
      Relay artifact mechanics
      server request and response mapping

    internal/protocol
      OpenMLS sidecar boundary
      cryptographic artifact operations

    internal/state
      workspace context
      path policy
      state adapters
      compatibility and refusal helpers

CarbonStackComms owns the reusable noninteractive workflow engine.

A future TUI or other presentation layer must call this workflow engine rather than implement a separate lifecycle.

## 6. Preferred normal-message path

Accepted direction:

    Relay Space-scoped normal messaging
      preferred v0.7.x operational path

    existing unscoped normal messaging
      retained temporarily as an explicit dev or legacy proof surface

    silent scoped-to-unscoped fallback
      forbidden

    removal of the unscoped path
      deferred until replacement and compatibility evidence exist

Relay onboarding and ordinary messaging should converge on one explicit Relay lifecycle.

## 7. Identity-domain classification

Current domains:

    Cypher device identity
      server registration and routing metadata

    Comms trust and candidate state
      local policy and future enrollment authority

    OpenMLS signer identity
      cryptographic message and group identity

Current relationship:

    correlated but unbound

Required behavior:

- No automatic trust promotion from Relay membership.
- No verified-identity claim from successful MLS join.
- No claim that Cypher sender metadata authenticates the MLS sender.
- No silent key replacement.
- No silent identity continuity.
- No automatic enrollment binding.
- Display unverified or unbound status unless a future binding protocol proves otherwise.

Gate A does not define or claim a complete cryptographic enrollment protocol.

## 8. Mutation classes

Every workflow operation must declare one or more mutation classes:

    READ_ONLY

    LOCAL_METADATA_MUTATION

    LOCAL_POLICY_MUTATION

    CRYPTOGRAPHIC_STATE_MUTATION

    SERVER_COORDINATION_MUTATION

    SERVER_DELIVERY_MUTATION

    MULTI_DOMAIN_MUTATION

Meaning:

READ_ONLY

    Intended to inspect state without persistent mutation.

LOCAL_METADATA_MUTATION

    Mutates non-authoritative local context, summaries, or indexes.

LOCAL_POLICY_MUTATION

    Mutates trust, candidate, recovery-policy, or comparable local authority.

CRYPTOGRAPHIC_STATE_MUTATION

    Mutates signer, provider, group, epoch, message, or other cryptographic state.

SERVER_COORDINATION_MUTATION

    Mutates accounts, devices, Relay Spaces, memberships, invites, or comparable coordination state.

SERVER_DELIVERY_MUTATION

    Mutates envelope submission, acknowledgement, queue, or delivery state.

MULTI_DOMAIN_MUTATION

    Spans two or more authority domains.

Multi-domain operations must report which domains were actually mutated.

## 9. Structured workflow result

Workflow results must be stage-aware.

Minimum result fields:

    workflow_id
    operation
    resolved_context
    stages_attempted
    stage_status
    mutation_classes
    mutations_completed
    mutations_not_attempted
    external_artifacts_created
    acknowledgements_performed
    final_classification
    recovery_or_retry_guidance
    non_secret_evidence_paths

Accepted final classifications:

    completed
    refused_precondition
    failed_no_mutation
    failed_partial_local
    failed_partial_server
    failed_partial_cryptographic
    recovery_required
    compatibility_blocked
    operator_action_required

A generic failed result is insufficient when partial mutation occurred.

## 10. Acknowledgement discipline

KeyPackage:

    acknowledge only after successful add-member
    or an explicit safe terminal classification

Welcome:

    acknowledge only after successful staged join
    and final state promotion

Application message:

    acknowledge only after successful message-open
    unless a future explicit discard or quarantine workflow exists

Unsupported, malformed, or ambiguous artifact:

    no automatic acknowledgement

Failure after fetch but before local completion:

    report queued and unacknowledged state explicitly

Existing no-ack-after-failed-open and no-ack-after-failed-join behavior remains a required invariant.

## 11. Relay membership authority

Relay Space membership becomes an enforced prerequisite for Relay-scoped routing.

Cypher may enforce:

    sender is an active Relay Space member
    recipient is an active Relay Space member
    envelope belongs to the named Relay Space

Cypher must not infer:

    MLS group membership
    verified identity
    trust
    authorization to mutate MLS state

Relay membership is server routing and coordination authority only.

## 12. Cypher and MLS membership mismatch

Accepted mismatch classifications:

    aligned
    cypher_member_mls_unknown
    mls_member_cypher_absent
    cypher_removed_mls_present
    pending_onboarding
    pending_removal
    stale_or_ambiguous
    unsupported_state

Rules:

- Read-only inspection may report mismatch.
- Safety-sensitive workflows refuse on ambiguous mismatch.
- Cypher membership must not silently add or remove MLS members.
- Local MLS membership must not silently mutate Cypher membership.
- Reconciliation requires an explicit named workflow.
- Reconciliation requires explicit operator confirmation.
- Reconciliation must emit partial-completion evidence.

## 13. State path and concurrency policy

Gate A establishes policy. Gate C will implement enforcement.

Accepted policy:

- One explicit state root per workspace or profile.
- No source-tree-relative runtime authority in the preferred lifecycle.
- One writer per authoritative state domain unless supported locking exists.
- Safety-sensitive writes use temporary files and atomic replacement where applicable.
- Related store and history mutations require transactional or recoverable ordering.
- Concurrent mutation without supported locking refuses.
- Unknown or newer safety-sensitive schemas refuse mutation.
- No generic global force flag.
- No silent migration.
- No silent repair.
- No silent trust promotion.
- No silent identity continuity.
- No silent backup restoration.
- No silent algorithm transition.

## 14. Validation separation

Release validation:

    full-validate-release

Workflow leaf validation:

    named lifecycle-specific profiles

State inspection:

    state-audit-dev or a successor with the same claim boundary

Failure evidence:

    named case-specific profiles

Preferred operational lifecycle aggregate:

    future full-operational-spine-dev
    only after leaf stability

Adversarial evidence:

    later dependency-driven leaf testing
    comprehensive deployment campaign during v0.9.x

The future aggregate must remain visible in the command table.

Its internal calls must remain documented and callable where applicable.

The aggregate must not absorb:

- release-package validation;
- state inspection;
- every failure profile;
- every development profile;
- comprehensive adversarial testing.

## 15. Future aggregate composition boundary

A future full-operational-spine-dev profile may eventually compose:

    environment and prerequisite inspection
    Cypher lifecycle
    workspace and context initialization
    Relay Space creation or selection
    device registration or selection
    onboarding lifecycle
    membership and compatibility inspection
    scoped normal message send
    scoped inbox retrieval
    successful open
    acknowledgement
    dependency restart
    state resume
    bounded state assertions
    explicit scoped cleanup

It must not be implemented until each required leaf has:

- an explicit owner;
- an explicit mutation contract;
- a structured result;
- deterministic positive evidence;
- relevant negative-path evidence;
- documented refusal behavior.

## 17. Gate A closure criteria

Gate A is complete when:

- this contract is committed;
- the docs index references it;
- the future aggregate is classified in the registry;
- the generated command reference is current;
- the command boundary table contains the future aggregate;
- registry nonclaim validation passes;
- runner tests pass;
- the repository is clean and pushed;
- the working LogDoc and Breakpoint record Gate A closure.

Gate A closure does not mean the workflow engine or aggregate exists.

## 18. Next implementation-planning sequence

After Gate A closure:

1. Normalize the current live command, route, and state read/write matrix.
2. Select the first narrow implementation leaf.
3. Prefer a leaf that removes ambiguity needed by Gate B.
4. Preserve existing lower-level proof commands.
5. Do not implement the aggregate first.
6. Add deterministic positive and negative-path evidence with each leaf.
7. Update registry and docs only when behavior actually exists.

Likely early candidates include:

- explicit workspace/context model;
- Relay-scoped normal-message contract;
- scoped versus unscoped inbox separation;
- Relay membership routing enforcement;
- workflow result and mutation-class substrate.

The exact first implementation leaf requires a separate dependency review.
