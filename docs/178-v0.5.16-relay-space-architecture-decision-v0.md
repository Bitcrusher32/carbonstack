## 3. Definition

A Relay Space is an addressable relay/conversation space served by CarbonStackCypher and consumed by CarbonStackComms clients.

A Relay Space may provide:

    routing namespace;
    encrypted envelope storage;
    group/conversation addressing;
    invite claim surface;
    delivery queues;
    basic rate limits;
    device registration lookup;
    revocation/notice propagation later;
    operational metadata needed for delivery.

A Relay Space must not provide:

    plaintext access;
    trusted identity authority;
    silent key replacement authority;
    silent membership truth;
    verified contact status;
    final group-trust truth;
    user verification ceremony;
    local trust-store mutation by itself.

## 4. Core rule

Relay Space is routing/conversation infrastructure.

Relay Space is not identity authority.

Relay admin is not a trust root.

Cypher delivery is not trust.

Server membership claims are not enough for client trust.

Client trust history and verification remain local/client-owned.

## 5. Cypher responsibilities

CarbonStackCypher may own:

    Relay Space creation/configuration later;
    invite creation/claim mechanics;
    device registration endpoint;
    device lookup endpoint;
    encrypted envelope submit/retrieve/ack;
    relay storage;
    basic rate limits;
    local operator runbook;
    future Relay Space metadata;
    future server-side moderation primitives that do not become identity trust.

Cypher should not own:

    plaintext message content;
    verified device identity;
    verified group membership;
    safety-number verification;
    trust.json mutation;
    candidate identity promotion;
    provider identity verification;
    client-side changed/reverify decisions.

## 6. Comms responsibilities

CarbonStackComms owns:

    local identity state;
    local trust state;
    local trust history;
    provider event classification;
    provider trust reports;
    provider trust-history drafts;
    provider trust-event drafts;
    candidate identity policy later;
    mapped mismatch/reverify policy later;
    send/open/ack behavior;
    user-visible trust warnings later;
    verification ceremonies later.

Comms must independently verify or classify any server-delivered identity material.

## 7. Server-hostile assumption

Relay Space design must assume:

    server may be compromised;
    server may equivocate;
    server may hide or delay messages;
    server may replay stale routing data;
    server may lie about membership;
    server may deliver malicious identity material;
    server may be administered by a malicious or coerced operator.

Therefore:

    clients must not trust server membership as verification;
    clients must not trust server key material as verified identity;
    clients must detect or loudly surface key changes;
    clients must preserve append-only local trust history;
    clients must require explicit verification for verified identity.

## 8. Membership model

Relay Space membership is not the same as trusted membership.

Possible layers:

    server-visible routing membership;
    client-observed group membership;
    MLS/provider group membership;
    local trust-known devices;
    locally verified devices;
    locally blocked/revoked/changed devices.

A server can help route to members.

A server must not silently create trusted members.

Future group membership UX should distinguish:

    server says this device exists;
    provider says this device is in the group;
    local trust store says this device is verified/unverified/changed/revoked;
    user has or has not verified this device.

## 9. Invite model

A Relay Space invite may authorize access to a routing space.

It must not authorize verified trust.

Invite claim can mean:

    server accepted a join credential;
    server issued routing access;
    server associated a device/account claim with the Relay Space.

Invite claim must not mean:

    device is verified;
    identity is trusted;
    group safety is complete;
    existing members accepted identity silently;
    server can replace keys.

Future invite flow should produce candidate identity material for local review, not verified trust.

## 10. Admin/operator boundary

Relay Space admins may operate server infrastructure.

They may:

    configure Relay Space policy;
    rotate server secrets;
    manage storage retention;
    set rate limits;
    revoke server-side access;
    moderate routing access later;
    export operational logs later if designed.

They must not be able to:

    decrypt messages;
    mark client identity verified;
    silently replace client keys;
    mutate a client's trust store;
    make a client accept changed identity;
    suppress local trust warnings;
    complete verification ceremonies for users.

Admin action can affect availability.

Admin action must not become trust truth.

## 11. Metadata boundary

Relay Space cannot hide all metadata.

Likely visible to Cypher:

    Relay Space identifier;
    timing;
    envelope size;
    sender routing identity or pseudonym depending implementation;
    recipient/delivery queue metadata;
    device registration metadata;
    IP/network metadata unless hidden by other layers.

v0.5.16 does not solve metadata privacy.

Future work may reduce metadata but must not claim metadata-private messaging prematurely.

## 12. Trust-history interaction

Relay Space events may later produce local trust/history observations.

Possible future event families:

    relay_space_join_observed
    relay_space_invite_claimed
    relay_space_membership_observed
    relay_space_membership_changed
    relay_space_delivery_anomaly
    relay_space_server_key_changed
    relay_space_admin_policy_changed

These should not automatically mutate trust.json.

Trust mutation requires explicit local policy and, for identity verification, explicit ceremony.

## 13. Provider/candidate/mismatch interaction

Relay Space may carry identity material or trigger provider artifacts.

But v0.5.14 and v0.5.15 remain controlling:

    provider-observed identity material is not trust;
    candidate import and verification are separate;
    mapped provider mismatch can become review/reverify/changed only by explicit policy;
    unmapped material must not mutate known devices;
    known verified device mismatch must not silently replace material.

Relay Space join should feed candidate/review flows later, not verified trust.

## 14. Ack boundary

Relay Space architecture must preserve existing ack policy.

Rules:

    server delivery is not enough;
    envelope retrieval is not enough;
    artifact write is not enough;
    provider report generation is not enough;
    trust-history append is not enough;
    event draft generation is not enough;
    only successful sidecar message-open/consume may permit ack, unless a later negative-ack/quarantine design is explicitly created.

v0.5.16 does not create negative ack.

## 15. One Relay Space vs many

Default architecture:

    one Relay Space maps to one addressable server/conversation-space concept.

Do not prematurely multiplex many unrelated trust domains into one Relay Space.

Future pressure may justify:

    multiple conversations per Relay Space;
    multiple groups per server;
    federated relay spaces;
    bridge spaces;
    public/private subspaces.

But default v0.5.x mental model should remain simple.

## 16. Local-backbone implication

Local-backbone is not ready just because provider append and Relay Space docs exist.

Before local-backbone:

    Relay Space concept must be stable;
    join/invite/member model must be specified;
    Comms provider identity candidate/mismatch behavior must be specified;
    ack policy must remain strict;
    local reset/recovery behavior must be clearer;
    validation profile boundaries must be defined.

v0.5.16 should feed v0.5.17 local-backbone feasibility reassessment.
