# CarbonStack v0.6.9 Relay Onboarding Boundary Contract v0

Status: dev/pre-alpha boundary contract  
Scope: Relay Space OpenMLS KeyPackage / Welcome / add-member / join onboarding artifact lifecycle  
Checkpoint target: v0.6.9  
Public release impact: none; current public release remains v0.6.0 State/UX Boundary Validation Pre-Release

## 1. Purpose

This document standardizes the Relay Space OpenMLS onboarding boundary after the v0.6.8 test/lookup/release-asset confidence checkpoint.

It does not add a new user-facing command and does not promote Relay onboarding to production UX. It records the intended relationship between:

- Relay Space KeyPackage transport;
- Relay Space Welcome transport;
- OpenMLS sidecar `conversation-add-member`;
- OpenMLS sidecar `conversation-join`;
- normal `message-send-dev` / `message-inbox-dev` application-message send/open;
- future integrated runtime validation.

## 2. Boundary statement

Relay onboarding artifacts are not ordinary messages.

KeyPackages and Welcomes are onboarding artifacts. They may be transported through Relay Space, fetched from Relay Space, written to local artifact files, consumed by OpenMLS sidecar commands, and optionally acknowledged only after a safe terminal action. They must not be silently mixed into ordinary `message-inbox-dev` application-message open semantics.

Normal application-message flow is:

    message-send-dev -> Cypher application-message envelope -> message-inbox-dev --ack after successful message-open

Relay onboarding flow is:

    KeyPackage submit/fetch/write
    -> add-member consumes KeyPackage and creates/submits Welcome
    -> Welcome fetch/write
    -> join consumes Welcome
    -> optional ack only after successful join/reloadable state

Future integrated runtime may call these phases in series, but the phases must remain individually callable.

## 3. Current Relay onboarding command classes

### 3.1 Artifact transport commands

These commands transport or fetch onboarding artifacts. They do not perform OpenMLS membership state transitions by themselves.

    openmls-relay-keypackage-submit-dev
    openmls-relay-keypackage-inbox-dev
    openmls-relay-welcome-submit-dev
    openmls-relay-welcome-inbox-dev

Boundary:

- dev/pre-alpha only;
- no identity verification claim;
- no production key distribution or membership UX claim;
- no local-backbone claim;
- no automatic join;
- inbox/write success is not sufficient to ack unless a future command explicitly defines a safe terminal policy.

### 3.2 Artifact bridge command

This command bridges a fetched KeyPackage artifact into OpenMLS sidecar membership update behavior and submits the resulting Welcome.

    openmls-relay-add-member-dev

Boundary:

- consumes a Relay Space KeyPackage artifact;
- invokes sidecar `conversation-add-member`;
- writes/submits a Welcome artifact;
- does not join the recipient;
- does not ack KeyPackage or Welcome envelopes by itself;
- does not prove identity verification or production membership UX.

### 3.3 Join transition command

This command consumes a fetched Welcome artifact and attempts to join the sidecar conversation.

    openmls-relay-join-dev

Boundary:

- consumes a Relay Space Welcome artifact;
- invokes sidecar `conversation-join`;
- may ack only after successful join/reloadable state and only when explicitly requested;
- failed join must not ack;
- fetch-only or artifact-write-only behavior must not ack;
- does not claim hostile-server safety, metadata privacy, identity verification, or production UX.

## 4. Ack rules

### 4.1 Normal application-message ack

Application-message ack remains:

    no ack on fetch;
    no ack for unsupported envelope;
    no ack on artifact-write failure;
    no ack on sidecar message-open failure;
    ack only after successful sidecar message-open and explicit --ack.

### 4.2 Relay onboarding artifact ack

Relay onboarding artifact ack is stricter because artifact fetch/write is not a successful terminal action.

KeyPackage envelope:

    fetch/write alone: no ack;
    add-member success alone: current posture remains no ack unless explicitly introduced later;
    failed add-member: no ack.

Welcome envelope:

    fetch/write alone: no ack;
    join success/reloadable state: ack may be allowed only under explicit flag;
    join failure: no ack;
    missing/malformed/unusable Welcome: no ack.

### 4.3 Future integrated runtime ack

Future integrated runtime may sequence:

    KeyPackage submit/fetch/write
    add-member
    Welcome submit/fetch/write
    join
    normal message send/open

but it must preserve the terminal-action ack rule for each artifact class. Integrated runtime must not convert fetch/write into ack eligibility.

## 5. Why primitives remain individually callable

The current Relay onboarding primitives must remain callable independently because real onboarding and repair scenarios may need partial lifecycle steps, including:

- refreshing or re-submitting KeyPackages;
- inspecting Welcome artifacts;
- retrying failed join;
- re-onboarding after trust-state depreciation;
- separating transport, membership mutation, and message-open behavior;
- debugging sidecar state without forcing a full integrated flow.

A future wrapper may orchestrate these steps, but it should not remove the primitive surfaces.

## 6. Registry lifecycle status mapping

v0.6.9 classifies the six Relay onboarding commands as:

    relay_onboarding_artifact_transport:
        openmls-relay-keypackage-submit-dev
        openmls-relay-keypackage-inbox-dev
        openmls-relay-welcome-submit-dev
        openmls-relay-welcome-inbox-dev

    relay_onboarding_artifact_bridge:
        openmls-relay-add-member-dev

    relay_onboarding_join_transition_candidate:
        openmls-relay-join-dev

These are dev/operator classification labels only. Registry presence is not public command promotion.

## 7. Nonclaims

This boundary contract does not claim:

- production secure messaging;
- production E2EE;
- hostile-server safety;
- metadata privacy;
- identity verification;
- secure enrollment;
- production key distribution;
- production membership UX;
- local-backbone readiness;
- deployment readiness;
- mature messenger UX;
- general-public usability;
- that Relay onboarding is part of `full`;
- that Relay onboarding is part of release-snapshot;
- that Relay onboarding artifacts are ordinary application messages.

Do not mutate `full` until the integrated-runtime policy is explicitly decided.
