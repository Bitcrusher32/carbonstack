# Gate B9 Integration Closure

Status: accepted implementation document  
Scope: v0.7.x Gate B9  
Profile: `gate-b-relay-lifecycle-closure-dev`

## Summary

B9 introduces a Gate B closure profile and closure documentation. It does not add a new Comms command or a new runtime path.

The purpose is to prove that the already-implemented B1-B8 dev/pre-alpha Relay lifecycle leaves are mechanically coherent when validated as one closure ladder.

## Closed leaves preserved

B9 preserves these leaves as distinct evidence, not hidden implementation details:

- B1 unscoped inbox isolation;
- B2 scoped active routing-membership enforcement;
- B3 Relay Space-scoped normal-message path;
- B4 invite/member lifecycle;
- B5 prerequisite scoped inbox/ACK active-membership authority;
- B5a KeyPackage inspection;
- B5b KeyPackage generation/rotation;
- B5c KeyPackage publication;
- B5d KeyPackage consume/receipt/ACK-after-persist;
- B5e KeyPackage lifecycle closure;
- B6 Welcome consume/join/ACK-after-join;
- B7 Cypher/MLS mismatch inspection/refusal;
- B8 workflow report/evaluator.

## Profile

`gate-b-relay-lifecycle-closure-dev` validates the Gate B profile ladder:

- Relay Space invite claim;
- Relay Space member state;
- Relay Space member restart;
- Relay Space delivery authority;
- KeyPackage inspect;
- KeyPackage rotation;
- KeyPackage publication;
- KeyPackage consume;
- Welcome lifecycle;
- Cypher/MLS mismatch;
- workflow relay onboarding;
- lower-level Relay OpenMLS join;
- same-state Welcome failure;
- same-state integrated normal messaging;
- dev runtime OpenMLS wrappers;
- registry/reference freshness;
- missing-nonclaims check.

## Closure meaning

Gate B closure means the dev/pre-alpha Relay lifecycle is mechanically coherent and evidence-backed across scoped delivery, membership, KeyPackage, Welcome, mismatch refusal, and workflow evaluation.

## Nonclaims

B9 does not claim:

- Gate C state enforcement;
- Gate D runtime aggregate;
- Gate E native deployment;
- Gate F v0.8.0 maturity;
- `full-runtime-dev`;
- production E2EE;
- verified identity;
- trust promotion;
- secure enrollment;
- hostile-server safety;
- deployment readiness;
- containers;
- PQ/hybrid support;
- vault, backup, or restore safety;
- Android or CarbonStackOS implementation.
