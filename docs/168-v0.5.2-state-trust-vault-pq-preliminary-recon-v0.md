## 4. Current state-bearing islands

CarbonStack currently has multiple state-bearing islands rather than one unified state architecture.

### 4.1 Comms local app state

Relevant surfaces:

    carbonstack-comms/internal/state/state.go
    carbonstack-comms/internal/state/state_test.go
    carbonstack-comms/docs/05-local-state-model-v0.md

Likely contents / role:

    local profile/server/account/device context;
    CLI/dev client state;
    state loaded by current Comms commands;
    bridge between user-facing command state and Cypher account/device identifiers.

Current classification:

    dev/pre-alpha local app state.

Open questions:

    Which fields are authoritative?
    Which fields are derived/cache?
    Which fields must survive restart?
    Which fields must not silently regenerate?
    Which fields become vault-protected later?

### 4.2 Comms trust state

Relevant surfaces:

    carbonstack-comms/internal/trust/trust.go
    carbonstack-comms/internal/trust/trust_test.go
    carbonstack/docs/20-identity-and-trust-state-v0.md
    carbonstack/docs/23-phase2a-trust-state-plan.md
    carbonstack/docs/38-provider-trust-state-mapping-v0.md

Relevant commands:

    fingerprint
    verify-device
    trust-history
    trust-list
    simulate-key-change
    revoke-device

Current classification:

    dev/pre-alpha trust-state model and test surface.

Important boundary:

    OpenMLS bootstrap wrapper commands currently do not mutate Comms trust state.
    This is intentional and must not be hidden.
    Future mature runtime UX needs an explicit trust-state integration plan.

Open questions:

    What is the stable trust record shape?
    What is a key-change event versus a new-device event?
    What does revocation mean locally versus server-visible?
    How does trust history survive backup/restore?
    Which trust events must be loud and irreversible without re-verification?

Current classification:

    dev-only OpenMLS sidecar state and generated provider material.

Important boundary:

    Sidecar state is real enough to power OpenMLS lifecycle tests and dev runtime smoke proofs.
    It is not a production vault.
    It is not a final storage layout.
    signer/provider material must not be treated as safe public source.

Open questions:

    Which sidecar files are identity-critical?
    Which sidecar files are group/conversation-critical?
    Which can be regenerated?
    Which must never silently regenerate?
    What is the future ownership boundary between Comms state and sidecar provider state?
    Should Comms eventually own a provider-state directory and pass explicit paths to the sidecar?

## 5. Preliminary state-domain classification

Suggested first classification vocabulary:

    source:
      tracked source code or docs.

    generated-build:
      build artifacts such as Rust target.

    generated-dev-provider:
      dev-only sidecar/provider state such as signer/provider storage.

    generated-dev-runtime:
      runtime smoke/test artifacts.

    local-app-state:
      Comms client profile/account/device/trust state.

    server-relay-state:
      Cypher account/device/invite/envelope/ack state.

    release-package-state:
      release metadata, checksums, package roots, validation roots.

    future-vault-state:
      state that should eventually be encrypted/protected by local vault design.

    ephemeral:
      state that should be safe to delete after a run.

    must-not-silently-regenerate:
      identity/trust/provider/conversation state whose unexpected replacement should trigger loud warnings.

## 6. Immediate design implications

### 6.1 State correctness comes before vault design

Vault design should not start by encrypting arbitrary current files.

First, CarbonStack needs to know:

    which files are identity-bearing;
    which files are trust-bearing;
    which files are group/conversation-bearing;
    which files are relay staging;
    which files are cache;
    which files are reproducible;
    which files are dangerous if silently replaced.

### 6.2 Trust UX depends on accurate state domains

A mature trust display cannot be designed until CarbonStack can distinguish:

    same device / same identity;
    known device / changed key;
    new device;
    revoked device;
    recovered device;
    re-enrolled device;
    group epoch change;
    ciphersuite or protocol-version change.

### 6.3 PQ/hybrid migration is a state migration problem

PQ/hybrid work is not only ciphersuite selection.

It affects:

    KeyPackage compatibility;
    group state;
    provider storage;
    protocol_version;
    content_type;
    trust display;
    reinit/rekey/recovery policy;
    artifact sizes;
    runner assumptions;
    release claims.

Do not implement PQ/hybrid behavior until the state/trust/provider boundaries are clearer.

### 6.4 Cypher persistence is relevant but not the whole problem

Cypher already validates local relay lifecycle and restart behavior through local-cypher.

That proves useful server-side persistence behavior.

It does not solve:

    Comms local state persistence;
    OpenMLS sidecar provider persistence;
    trust history persistence;
    vault boundaries;
    migration behavior for future protocol/ciphersuite changes.

## 7. Preliminary risk list

Current risk areas for v0.5.x:

    identity material and provider state are still dev-local sidecar artifacts;
    Comms trust state and OpenMLS provider state are not yet a unified mature model;
    old send/inbox remain stub-era and must not be confused with OpenMLS dev commands;
    runtime OpenMLS direct/wrapper profiles remain outside full;
    local-backbone remains reserved;
    vault design is not ready until state domains are explicit;
    PQ/hybrid migration could break KeyPackage/group/provider assumptions if attempted too early;
    server-side persistence does not imply client-side persistence safety;
    generated sidecar roots must remain ignored, classified, and cleaned.
