## 3. Core rule

Provider-observed identity material is not trust.

It may become:

    a candidate;
    an unverified record;
    an append-only history event;
    a warning;
    a reverify-required condition;
    a block condition.

It must not become:

    verified;
    silently accepted;
    silently substituted for a known device;
    a server-trusted identity root;
    a sidecar-label-trusted identity root.

## 4. Definitions

### 4.1 Provider-observed identity material

Provider-observed identity material means identity-relevant material surfaced by OpenMLS sidecar/provider flows.

Examples:

    public identity material;
    KeyPackage/public bundle material;
    Welcome-derived identity observations;
    sidecar identity status output;
    provider identity-loaded / identity-created / identity-changed events;
    future safety-number/fingerprint material;
    future device enrollment material.

Current limitation:

    The mature production identity material and safety-number format are not finalized.

Therefore:

    v0.5.14 should define policy, not final cryptographic identity format.

### 4.2 Candidate identity

A candidate identity is observed identity material that CarbonStack may remember for review, comparison, or later import.

Candidate does not mean trusted.

Candidate does not permit mature send by itself.

Candidate does not prove the server or provider is honest.

### 4.3 Unverified identity

An unverified identity is an identity record known to the local client but not verified by an explicit user/hardware/ceremony path.

Unverified may be enough for dev-mode visibility.

Unverified should block mature strict send until verification or explicit override policy exists.

### 4.4 Verified identity

Verified identity requires explicit verification ceremony.

Provider observation alone must not create verified identity.

Cypher delivery alone must not create verified identity.

KeyPackage receipt alone must not create verified identity.

Welcome receipt alone must not create verified identity.

Sidecar label existence alone must not create verified identity.

## 6. Storage options

v0.5.14 does not choose a final storage format.

Possible options:

### Option A: trust.json with trust_state=unverified

Benefits:

    simple;
    reuses current DeviceRecord;
    send policy already understands non-verified states;
    easier first implementation.

Risks:

    candidate identity may be confused with existing trust records;
    trust.json may become overloaded;
    unknown provider material may look more authoritative than it is;
    future vault separation may become harder.

### Option B: identity-candidates.json

Benefits:

    separates candidate observations from trust records;
    reduces accidental verification confusion;
    easier to preserve source/provenance metadata;
    easier to expire, compare, or discard candidates;
    cleaner bridge to future vault domains.

Risks:

    requires new storage file and APIs;
    send policy must explicitly consult or ignore it;
    more plumbing before first implementation.

### Option C: append-only history first

Benefits:

    records observations without promoting them to state;
    matches v0.5.13 append helper direction;
    safest from a trust perspective.

Risks:

    hard to build UX from history alone;
    repeated observations may be hard to reconcile;
    candidate review flow still needs a state model later.

### Option D: future vault-bound pending identity domain

Benefits:

    likely best long-term security model;
    separates sensitive identity/provider material from plain dev state.

Risks:

    vault does not exist yet;
    too heavy for immediate implementation.

## 7. Recommended staged storage policy

Recommended policy:

    v0.5.14: plan only.
    v0.5.15: mapped identity mismatch / changed-reverify plan.
    Later implementation spike:
      start with append-only observation plus non-authoritative candidate draft.

Preferred future direction:

    avoid direct verified insertion into trust.json;
    use separate candidate/pending domain if implementation complexity stays manageable;
    only write trust.json unverified records if the semantics are clearly labelled and tests prove send policy blocks as expected.

Practical recommendation:

    For first implementation, consider an identity candidate domain before trust.json mutation.

Candidate file name if chosen later:

    identity-candidates.json

But do not create it in v0.5.14.

## 10. Conflict policy

Candidate identity material should be compared against existing local trust records when a mapping is available.

Cases:

    no known device mapping:
      record candidate only;
      do not invent verified identity;
      do not mutate trust.json;

    known device, same fingerprint/material:
      record continuity observation if useful;
      do not mutate trust.json;

    known unverified device, new material:
      record conflict;
      require review;

    known verified device, new material:
      record conflict;
      require reverify;
      later mapped mismatch plan may mark changed;

    known revoked device:
      block promotion;
      show warning;

    known compromised-reserved device:
      block promotion;
      show warning;
      keep compromised behavior reserved until designed.

## 11. Send policy implications

Candidate identity alone should not allow mature strict send.

Strict send should require:

    verified identity;
    no changed/revoked/compromised state;
    no pending provider reverify requirement;
    no unresolved conflict.

Dev-mode may allow override, but must warn loudly.

## 12. Trust-history implications

## 13. Verification ceremony boundary

Verification ceremony may later include:

    manual fingerprint comparison;
    QR code ceremony;
    hardware-key signed enrollment;
    in-person device ceremony;
    recovery/re-enrollment procedure.

v0.5.14 does not choose the final ceremony.

Hard rule:

    candidate import and verification ceremony are separate steps.

## 14. Cypher/server boundary

Cypher may deliver identity material.

Cypher must not become identity authority.

Cypher delivery proves at most:

    the server delivered bytes;
    the server associated bytes with routing metadata.

It does not prove:

    the sender is who they claim;
    the device key is trustworthy;
    group membership history is honest;
    the server did not equivocate.

## 15. Provider/sidecar boundary

The provider/sidecar may expose local identity and MLS artifacts.

The provider/sidecar must not silently promote identity into verified trust.

Sidecar labels are local/dev handles, not trust roots.

Provider identity-loaded is continuity information, not verification.

Provider identity-created is local state creation, not peer verification.
