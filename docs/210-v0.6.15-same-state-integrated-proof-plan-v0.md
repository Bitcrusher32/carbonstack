## Recon question

The v0.6.15 recon asked:

    Can Relay onboarding plus normal message send/open be proven in one coherent state story, rather than only as sequential profile composition?

The answer is:

    likely yes, but not with the current integrated-runtime-dev shape as-is.

## Current integrated-runtime-dev meaning

Current `integrated-runtime-dev` means:

    relay-openmls-join-dev -> dev-runtime-openmls-wrappers

It is an honest live-umbrella composition profile.

It proves:

    Relay onboarding proof completes;
    wrapper normal-message runtime proof completes;
    the two proof surfaces can run in sequence from the runner.

It does not prove:

    same runner temp universe;
    same Cypher server and DB across onboarding and normal message flow;
    same Alice/Bob Comms state files;
    same Alice/Bob device IDs;
    same sidecar labels;
    same conversation label;
    same conversation state;
    same-state/same-conversation normal send/open after Relay join.

The current profile must therefore keep its existing nonclaim:

    first implementation composes existing profile proofs in sequence; does not claim same-state package-root release proof.

## Recon-positive evidence

The Relay onboarding profile already has many ingredients needed for same-state proof.

Observed positive shape:

    runner-owned temp root;
    local Cypher server and temp DB;
    Alice/Bob Comms state files;
    Alice/Bob account/device setup;
    Relay Space setup;
    unique Alice/Bob sidecar labels;
    one conversation label;
    Alice sidecar conversation creation;
    Bob KeyPackage transport through Relay Space;
    Alice add-member through sidecar;
    Welcome transport through Relay Space;
    Bob conversation-join;
    group_reloadable true;
    member_count 2;
    no-ack subrun DB assertions;
    ack-after-join subrun DB assertions;
    trust/candidate files absent.

This means the same-state proof is not blocked by missing conceptual pieces. It is mostly a runner/wiring and proof-boundary task.

## Recon blocker

The wrapper runtime smoke path is not reusable as same-state proof as-is.

Reason:

    dev-runtime-openmls-wrappers currently creates its own independent temp workspace;
    starts its own local Cypher server;
    creates fresh Alice/Bob state;
    uses its own wrapper-side labels;
    cleans OpenMLS sidecar generated state as part of its standalone profile behavior.

That behavior is correct for an independent wrapper smoke proof, but it breaks state continuity if used directly after Relay onboarding.

## Target state-continuity levels

The implementation should reason in levels.

Level 0: sequential composition

    Existing integrated-runtime-dev.
    relay-openmls-join-dev runs, then dev-runtime-openmls-wrappers runs.
    Honest, useful, but not same-state proof.

Level 1: same runner temp root

    One top-level temp root owns all generated state.
    Profiles may still use separate subroots.
    Better cleanup and provenance, but not a strong same-state proof.

Level 2: same Cypher server/account/device universe

    Relay onboarding and normal message proof share one Cypher server/DB and the same Alice/Bob account/device state.
    Stronger evidence that Relay/Cypher state continuity is real.

Level 3: same sidecar identity and conversation state

    Bob joins the conversation through Relay onboarding and the resulting sidecar identity/conversation state is reused for normal message handling.
    This starts becoming true same-state integrated proof.

Level 4: same conversation normal-message proof

    Alice and Bob use the same conversation label and sidecar conversation state from Relay onboarding for normal message send/open.
    Bob opens a normal message with `message-inbox-dev --ack`.
    Bob inbox is empty after ack.
    This is the target if feasible.

## Target proof sequence

The v0.6.16 proof should attempt:

1. Create one runner-owned temp root.
2. Start one local Cypher server with one temp DB.
3. Initialize Alice and Bob Comms state files against that server.
4. Create/claim dev invites for Alice and Bob.
5. Register Alice and Bob devices.
6. Create one Relay Space.
7. Register Alice and Bob as Relay Space members.
8. Create Alice/Bob OpenMLS sidecar identities with unique labels.
9. Alice creates one conversation label.
10. Bob submits a KeyPackage through Relay Space.
11. Alice consumes KeyPackage, runs sidecar add-member, submits Welcome to Bob.
12. Bob consumes Welcome and runs sidecar conversation-join.
13. Assert Bob joined successfully:
        joined true;
        group_reloadable true;
        member_count 2;
        expected epoch after join.
14. Alice sends a normal message with `message-send-dev` using:
        same Alice state;
        same Alice sidecar label;
        same conversation label;
        Bob device ID from the same Cypher universe.
15. Bob opens with `message-inbox-dev --ack` using:
        same Bob state;
        same Bob sidecar label;
        same conversation label.
16. Assert:
        message opened;
        plaintext matches expected probe payload;
        acked true;
        Bob inbox empty after ack.
17. Assert no forbidden trust/candidate mutations:
        no trust.json;
        no trust-events.jsonl;
        no identity-candidates.json.
18. Assert generated artifacts are under known runner-owned or known sidecar generated roots.
19. Cleanup only known generated roots.

## Ack doctrine to preserve

Application-message ack rule:

    no ack on fetch;
    no ack for unsupported envelope;
    no ack on artifact-write failure;
    no ack on sidecar message-open failure;
    ack only after successful sidecar message-open;
    ack only when --ack is explicit.

Relay onboarding ack rule:

    KeyPackage fetch/write alone is not ack eligibility;
    add-member success alone currently does not imply ack;
    Welcome fetch/write alone is not ack eligibility;
    Welcome join success/reloadable state may ack only under explicit flag;
    failed join must not ack.

v0.6.16 may start positive-path only if explicitly documented, but follow-up tests should cover failure-path ack rules before promotion.

## Decision rules after v0.6.16 probe

If the temporary probe passes cleanly:

    add a named runner profile;
    add registry metadata;
    regenerate COMMAND_REFERENCE.v0.md;
    update docs and runner README;
    run generated-reference freshness test;
    commit as a bounded runtime/profile checkpoint.

If the temporary probe partly passes:

    document the highest reached state-continuity level;
    patch the narrowest state-boundary blocker;
    avoid naming the profile as same-state until Level 4 is proven.

If the temporary probe fails because current wrappers cannot reuse joined state:

    document blockers;
    do not mutate integrated-runtime-dev;
    keep current integrated-runtime-dev as honest sequential composition;
    decide whether wrappers need reusable state flags or a lower-level runner helper.

If the proof requires changing normal message wrapper semantics:

    stop and preflight that as its own boundary decision.

## Follow-up backlog after first proof

Later rungs should add failure-path coverage:

    missing KeyPackage;
    missing Welcome;
    sidecar add-member failure;
    sidecar join failure;
    no ack on Welcome write failure;
    no ack on sidecar join failure;
    no ack on message-open failure;
    wrong Relay Space ack rejection;
    wrong recipient ack rejection;
    wrong conversation/group rejection;
    stale generated-state refusal;
    malformed relay payload;
    duplicate/replay envelope behavior.

These belong after the first same-state positive proof unless implementation naturally exposes a cheap safe test.
