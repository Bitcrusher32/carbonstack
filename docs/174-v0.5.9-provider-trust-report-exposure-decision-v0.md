# v0.5.9 provider-trust report exposure decision

Status: decision record
Phase: v0.5.x provider-linkage implementation staging
Scope: CarbonStackComms provider-trust report helper, future CLI/registry boundary
Date: 2026-06-07 local session

## 1. Purpose

v0.5.9 records the exposure decision for the provider-trust report helper.

v0.5.7 added the internal non-mutating provider-trust report helper.
v0.5.8 clarified the report contract:

    structured JSON fields are the diagnostic source of truth;
    human summaries are interpretive helper text;
    the helper remains non-mutating;
    no CLI command exists yet;
    no registry update is needed without a command/profile/script/API surface.

v0.5.9 decides:

    keep provider-trust report internal-only for now.

## 2. Decision

Decision:

    Do not add a dev-only CLI command yet.

Rationale:

    the helper is already test-backed;
    no operator workflow currently needs arbitrary terminal event reporting;
    no runner profile needs command-level provider-trust report coverage yet;
    adding a CLI command would expand registry/README/help surface before the use case is concrete;
    the next valuable work is provider-originated trust-history append planning, not command exposure.

The helper remains available internally for tests and future integration.

## 3. Current implementation boundary

Current implementation surfaces:

    carbonstack-comms/internal/protocol/provider_trust.go
    carbonstack-comms/internal/protocol/provider_trust_report.go
    carbonstack-comms/internal/protocol/provider_trust_report_test.go

Current component-local docs:

    carbonstack-comms/docs/08-provider-trust-report-contract-v0.md

Current report boundary:

    no trust.json mutation;
    no trust-events.jsonl append;
    no provider identity import;
    no message ack/open behavior;
    no send/inbox replacement;
    no local-backbone;
    no final UX.

## 4. JSON and summary policy

Structured report fields remain the diagnostic source of truth.

Human summaries remain interpretive documentation.

Policy:

    future automation must inspect structured fields;
    future CLI JSON output should be treated as the stable output;
    human summary output may be displayed, but must be labelled interpretive;
    summary text must not become a parser contract;
    summary text must not become final user-facing trust UX.

## 5. CLI exposure gate

A future dev-only CLI command becomes justified only if at least one of these is true:

    humans need to inspect arbitrary provider events from the terminal during active debugging;
    runner validation needs command-level coverage;
    docs need a visible diagnostic workflow;
    provider-originated trust-history append work needs a before/after diagnostic comparison;
    registry/local-help generation work needs this command as a real surface.

Possible future command name:

    provider-trust-report-dev

Possible future shape:

    provider-trust-report-dev --event <provider-event-name> --json
    provider-trust-report-dev --event <provider-event-name> --summary

Required future behavior:

    non-mutating by default;
    JSON-first;
    summary labelled interpretive;
    unknown future event handling preserved;
    registry update in same or next checkpoint;
    tests for command output shape if command is added.

## 6. Registry decision

No registry update in v0.5.9.

Reason:

    no CLI command was added;
    no runner profile was added;
    no script was added;
    no API surface was added;
    no sidecar command was added.

When `provider-trust-report-dev` or equivalent exists, update:

    carbonstack/registry/commands.v0.yaml
    carbonstack registry tests if schema/coverage requires it
    carbonstack-comms README/docs
    carbonstack docs index or command-surface notes as needed

## 7. Next implementation direction

The next useful architecture/implementation target is not CLI exposure.

Recommended next checkpoint:

    v0.5.10 provider-originated trust-history append plan

Goal:

    define which provider-trust reports may become trust-events.jsonl entries later;
    define event names, source fields, no-mutation cases, block-only cases, and append-only cases;
    preserve the rule that provider observation does not automatically verify identity.

Potential later implementation:

    v0.5.11 provider-originated trust-history append spike

That later spike should still avoid provider identity import unless separately planned.
