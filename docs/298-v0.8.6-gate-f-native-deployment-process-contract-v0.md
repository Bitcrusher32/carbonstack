## Why F1 is carbonstack-only

F1 is not the whole Gate F implementation. F1 freezes the native/process contract, subgate plan, case matrix, service/systemd/helper threat model, report schema, registry entry, and validation profile in `carbonstack`.

This is intentionally `carbonstack`-only because `carbonstack` owns docs, registry, command reference, validation runner, and claim/nonclaim classification. It should define the target and prove the contract shape before Comms or Cypher component behavior is mutated.

Material Comms/Cypher changes are expected later under F2 if the F2 probe contract requires component-owned runtime/config/process tests or fixtures.

## Gate F subgate split

- **F1 — Contract / model / case matrix / threat-model scaffold**
  - Mutation scope: `carbonstack` only.
  - Purpose: freeze this contract, case matrix, report schema, registry/profile surface, and service/systemd/helper design-only threat model.
  - No component runtime behavior mutation.
  - No real Debian laptop validation.

- **F2 — Component runtime/process probes**
  - Mutation scope: `carbonstack`, `carbonstack-comms`, and/or `carbonstack-cypher` as justified by F1/F2 evidence.
  - Purpose: implement disposable-run-root process/DB/log/config/state-root/CLI probes and component-owned tests.
  - Cypher may be mutated only for narrow config/DB/process test fixtures or terminating inspection behavior.
  - Comms may be mutated only for client/operator runtime-root/state/log/artifact probes and tests.
  - `carbonstack-os` remains blocked.

- **F3/F4 — Full local validation and real Debian host validation**
  - WSL/development validation must pass first.
  - Laptop validation must use a bounded git-pull or cache-free export plan.
  - No major bug should be discovered for the first time on the slow Debian laptop.

## Target environment

Gate F targets real Debian host manual-private native operation. WSL is the fast development and reproduction environment. The old Debian laptop is final validation hardware only after local validation passes and the transfer/command plan is bounded.

## Process and DB probe rule

Gate F may launch processes and create DB/log/state artifacts during preflight or implementation only under an explicit disposable run root. Repo-root DB/log/state artifact creation is a finding.

## Sensitive-output rule

Treat invite tokens, secrets/private material, account IDs, device IDs, Relay Space IDs, KeyPackage fingerprints, OpenMLS signer or credential fingerprints, DB paths, state roots, and runtime roots as sensitive-enough for Gate F classification.

## Abort conditions

- Tracked repo files change before contract acceptance.
- Native probes write DB/log/state artifacts inside repo roots.
- Logs expose invite tokens, secrets, private material, or unnecessary identity/state-root metadata.
- Cleanup can delete outside an explicit disposable run root.
- Gate F implies service/systemd/helper readiness.
- Gate F implies public ingress readiness.
- Gate F implies container readiness.
- Cypher config/DB mutation becomes necessary without a component-local contract.
- `full-runtime-dev` is promoted by convenience before Gate G.
- Real Debian laptop validation is attempted before full local validation passes.

## Nonclaims

Gate F F1 does not claim service readiness, systemd readiness, helper install readiness, public ingress, container readiness, deployment hardening certification, production security, production E2EE, verified identity, trust promotion, secure enrollment, vault security, backup/restore, migration safety, repair implementation, destructive cleanup safety, TUI readiness, Android readiness, CarbonStackOS implementation, PQ/hybrid security, external audit, or external pen-test completion.
