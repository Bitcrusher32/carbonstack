# CarbonStack v0.6.25 Normal Message Envelope Metadata Classification v0

Status: docs/model checkpoint after v0.6.25A malformed normal application-message typed/envelope metadata recon.

## Scope

This checkpoint classifies how current dev/pre-alpha normal application-message open behavior treats selected envelope metadata fields.

It does not add a runner profile.

It does not patch Comms or Cypher runtime behavior.

It does not claim identity verification, hostile-server safety, replay safety, adversarial harness coverage, metadata authenticity, or production secure messaging.

## Case classifications

Classification:

    detected_or_rejected_no_ack_no_drain_recovery_ok

Observed behavior:

    message-open fails at artifact_write;
    no ack;
    no inbox drain;

Meaning:

    payload_sha256 is enforced before message-open.

### sender_device_id wrong

Classification:

    metadata_not_runtime_enforced_open_ack_drain

Observed behavior:

    message opens;
    message acks;
    envelope delivery_state becomes acknowledged;
    output from_device reflects the mutated sender_device_id;
    provider state changes as part of normal successful OpenMLS open.

Meaning:

    sender_device_id is currently relay envelope metadata for normal message-open display/reporting.
    It is not verified identity.
    It is not runtime-enforced as the cryptographic sender identity by the current wrapper.

Design implication:

    Do not present from_device as verified identity.
    Future identity/trust modeling must decide how verified sender identity is represented, displayed, checked, and warned.

## Critical model update

Current normal-message envelope metadata categories:

Runtime-enforced before message-open:

    payload_sha256;
    payload_size_bytes;
    protocol_version support gate.

Routing / fetch selectors:

    recipient_device_id;
    delivery_state.

Relay metadata not currently identity-enforced by message-open:

    sender_device_id.

The most important warning:

    from_device in current message-inbox-dev output is relay envelope sender metadata.
    It must not be treated as verified identity.

## Why this is not a runtime patch yet

A simple patch that blocks all sender_device_id mismatch would be premature because the current system does not yet have the full identity/trust ceremony needed to define what the sender identity must be checked against, how mismatch is represented, what recovery looks like, and how false positives are handled.

A future patch may still be appropriate after identity/trust modeling.

Near-term safer options:

    document from_device as unverified relay metadata;
    rename output to make that boundary louder;
    add warning output when sender metadata is empty or suspicious;
    design verified sender identity semantics during vault/security/trust modeling.
