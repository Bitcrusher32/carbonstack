# v0.5.51 validation-profile design contract

Status: validation-profile design contract
Phase: v0.5.x Relay Space + OpenMLS narrow validation-profile design
Scope: local-dev profile claim boundary, generated-state ownership, cleanup/refusal rules, implementation gates
Date: 2026-06-09 local session

## 1. Purpose

v0.5.51 defines the design contract for a future narrow local-dev validation profile.

This checkpoint is intentionally docs-only.

It does not add:

    validation profile;
    runner profile;
    public README promotion;
    new Comms app command;
    new script;
    command registry entry;
    Cypher route;
    trust.json mutation;
    identity-candidates.json mutation;
    candidate observation;
    local-backbone claim;
    hostile-server harness;
    destructive cleanup behavior.

## 2. Evidence baseline

v0.5.49 proved the live no-ack narrow smoke path under fresh generated state:

    KeyPackage submit;
    add-member + Welcome submit;
    Welcome join;
    ACK_AFTER_JOIN unset;
    ack_requested false;
    welcome_acked false.

v0.5.50 proved the complementary explicit ACK_AFTER_JOIN path under fresh generated state:

    KeyPackage submit;
    add-member + Welcome submit;
    Welcome join;
    ACK_AFTER_JOIN=1;
    ack_requested true;
    welcome_acked true;
    Welcome envelope acknowledged;
    KeyPackage envelope remained queued;
    one envelope_acks row existed.

Together, these are sufficient evidence to design a narrow local-dev validation profile.

They are not sufficient to claim local-backbone, production security, hostile-server safety, metadata privacy, verified identity, secure enrollment, audit, or certification.

## 3. Proposed future profile name

Preferred future profile name:

    relay-openmls-join-dev

Rationale:

    names the actual surface being validated;
    avoids local-backbone overclaim;
    distinguishes Relay Space + OpenMLS join dev proof from earlier dev-runtime-openmls profiles;
    keeps local-backbone reserved for a later whole-stack profile.

Avoid these names for the first profile:

    local-backbone;
    local-backbone-dev;
    secure-join;
    production-openmls;
    hostile-server;
    verified-join.

## 4. Maximum allowed claim

If implemented and passing, the future profile may claim only:

    In a fresh runner-owned local/dev environment, CarbonStack can start a local Cypher dev server, create isolated Alice/Bob Comms/Cypher/Relay Space state, create isolated OpenMLS sidecar state, run the KeyPackage -> add-member -> Welcome -> join path, prove no-ack and ACK_AFTER_JOIN behavior, and confirm checked trust/candidate stores are not created or mutated by that path.

The profile may also claim:

    package tests passed for the involved repos;
    Cypher health responded;
    Relay Space scoped envelopes behaved as expected;
    Welcome ack occurred only after join success when explicitly requested.

## 5. Forbidden claims

Passing the profile must not claim:

    local-backbone;
    production secure messaging;
    hostile-server safety;
    metadata privacy;
    verified identity;
    secure enrollment;
    mature provider live-flow;
    public CLI readiness;
    deployment readiness;
    audit;
    certification;
    general-public usability;
    trust-store correctness;
    candidate-store correctness;
    key-compromise recovery correctness;
    vault security;
    PQ/hybrid security.

## 6. Generated-state ownership

The future profile must own all generated state it creates.

Required generated roots should be under a runner-owned temp root, for example:

    /tmp/carbonstack-validate-relay-openmls-join-dev-<random>/

Under that root, profile-owned generated state should include:

    cypher/cypher.db;
    cypher/cypher.log;
    comms/alice-state.json;
    comms/bob-state.json;
    smoke/no-ack.log;
    smoke/ack-after-join.log;
    evidence/db-summary.txt;
    evidence/trust-candidate-before.txt;
    evidence/trust-candidate-after.txt.

Sidecar state must be isolated either by:

    unique labels per run; or
    an explicit sidecar state root override if implemented later.

Since current sidecar behavior uses repo-local .carbonstack-openmls-sidecar-state, v0.5.52 implementation must use unique labels and must refuse to proceed if those labels already exist.

## 7. State labels and IDs

The profile should generate unique labels per run:

    carbonstack-v0552-<random>-alice-device;
    carbonstack-v0552-<random>-bob-device;
    carbonstack-v0552-<random>-conversation;
    relay space ID relay-openmls-join-dev-<random>;
    invite codes relay-openmls-join-dev-alice-<random> and relay-openmls-join-dev-bob-<random>.

Exact version prefix can change with the implementation rung.

The important rule is uniqueness and runner ownership.

## 8. Cleanup and refusal rules

First implementation should prefer safe refusal over destructive cleanup.

Required refusal cases:

    Cypher port already occupied by an unknown process;
    runner-owned temp root already exists;
    sidecar device label directory already exists;
    sidecar conversation directory already exists;
    Comms state file already exists outside runner-owned temp root;
    Cypher DB path exists outside runner-owned temp root;
    required repo paths are missing;
    required toolchains are missing.

Allowed cleanup:

    runner-owned temp root created by this profile invocation;
    profile-owned temporary Cypher DB;
    profile-owned logs/evidence files.

Disallowed cleanup:

    user trust.json;
    user trust-events.jsonl;
    user identity-candidates.json;
    unknown .carbonstack-openmls-sidecar-state roots;
    non-profile sidecar device labels;
    non-profile provider storage;
    non-profile Cypher DBs;
    repo source/docs;
    release artifacts not created by the profile.

Cleanup must not become recovery, reset, re-enrollment, or key replacement.

## 9. Profile sequence

The future profile should perform:

    repo/path/toolchain checks;
    package tests or targeted tests;
    fresh temp root creation;
    local Cypher start with temp DB;
    Cypher health check;
    Alice/Bob Comms init;
    Alice/Bob dev invite creation and claim;
    Alice/Bob device registration;
    Relay Space creation;
    Alice/Bob Relay Space routing member registration;
    fresh sidecar identity creation;
    Alice sidecar conversation creation and load check;
    no-ack smoke run;
    ACK_AFTER_JOIN=1 smoke run using a separate fresh generated state set or separate fresh Relay Space/Cypher DB;
    DB summary capture;
    trust/candidate before/after capture;
    registry/public-surface assertion;
    final status output.

The first implementation may split no-ack and ACK_AFTER_JOIN into two isolated subruns.

Do not reuse the no-ack run's queued Welcome for the ack run.

## 10. Required assertions

No-ack subrun should assert:

    KeyPackage envelope exists and is queued;
    Welcome envelope exists and is queued;
    no envelope_acks rows exist;
    join output includes status joined;
    join output includes ack_requested false;
    join output includes welcome_acked false;
    checked trust/candidate files are absent or unchanged.

ACK_AFTER_JOIN subrun should assert:

    KeyPackage envelope exists and is queued;
    Welcome envelope exists and is acknowledged;
    exactly one envelope_acks row exists;
    ack row references the Welcome envelope;
    join output includes status joined;
    join output includes ack_requested true;
    join output includes welcome_acked true;
    join output includes ack_delivery_state acknowledged;
    checked trust/candidate files are absent or unchanged.

## 11. Trust/candidate nonmutation check

The future profile must not mutate:

    trust.json;
    trust-events.jsonl;
    identity-candidates.json;
    verified device state;
    candidate acceptance state;
    key replacement state;
    recovery state.

First implementation may check only runner-owned expected paths and current Comms state-dir paths.

It must not overclaim broad trust/candidate safety from absence checks.

## 12. Registry and public surface

The future runner profile may require registry coverage only when it becomes callable.

If added to registry, it must be:

    audience: developer;
    maturity: experimental;
    include_in_front_readme: false;
    explicit nonclaims preserved.

Do not promote it in the front README during first implementation.

## 13. Failure-path coverage

First implementation may be positive-path only if this is explicitly documented.

Follow-up rungs should add:

    missing KeyPackage failure;
    missing Welcome failure;
    sidecar add-member failure;
    sidecar join failure;
    no ack on Welcome write failure;
    no ack on sidecar join failure;
    wrong Relay Space ack rejection;
    wrong recipient ack rejection;
    stale generated-state refusal.

## 14. Implementation gate

v0.5.52 may implement the first runner profile only if:

    this contract is accepted;
    implementation stays narrow;
    generated state remains profile-owned;
    cleanup is explicit and narrow;
    stale state causes refusal rather than destructive repair;
    output assertions remain exact;
    nonclaims remain visible.
