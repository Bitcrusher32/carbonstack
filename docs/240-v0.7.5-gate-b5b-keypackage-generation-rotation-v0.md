# Gate B5b Repeatable KeyPackage Generation and Rotation

Status: implemented development contract for v0.7.5

## Result

Gate B5b replaces the one-shot local KeyPackage export limitation with a persistent device-local lifecycle.

Implemented surfaces:

- `keypackage-generate`;
- `keypackage-inventory`;
- `keypackage-retire`;
- corresponding Comms dev wrappers;
- permanent `keypackage-rotation-dev` validation profile.

## Identity and persistence

The OpenMLS `key_package_ref` is the cryptographic KeyPackage identity.

`request_id` is the permanent device-local idempotency identity for one generation request.

`generation_id` is a monotonic local lifecycle identifier using `kp-NNNNNN`.

Provider storage is loaded and evolved for every new generation. Prior KeyPackage bundle state remains in the same local provider storage so a later Welcome can consume any still-retained package.

## Layout

    devices/<label>/
      provider-storage.json
      public-bundle.keypackage.bin
      public-bundle-summary.json
      public-bundle-manifest.json
      keypackages/
        inventory.json
        .lifecycle-lock/
        generations/
          kp-000001-<ref-suffix>/
            keypackage.bin
            manifest.json

The fixed `public-bundle-*` files remain compatibility artifacts. They are not silently rewritten by B5b.

## Legacy adoption

A complete fixed public-bundle artifact, summary, manifest, and provider-storage set is adopted as `kp-000001` with request ID `legacy-public-bundle-import`.

An incomplete legacy set is refused. Provider storage is never guessed over, overwritten from a default provider, or discarded.

## Generation

`keypackage-generate` requires:

    --device-label <label>
    --request-id <safe-id>

An exact request retry returns the existing generation without mutation.

A fresh request loads existing provider storage, creates a new KeyPackage, persists the evolved provider, publishes an immutable generation directory, and publishes the inventory last.

Every successful fresh generation becomes current. Prior active generations remain active until explicit retirement.

## Inventory

`keypackage-inventory` is read-only. It exposes current, active, and retired generations across process restart and validates the inventory, generation manifests, artifact hashes, OpenMLS references, and lifetime metadata.

No implicit repair occurs in the read-only command.

## Retirement

`keypackage-retire` marks a non-current generation retired in inventory metadata.

Retirement:

- is idempotent;
- never deletes artifacts;
- never deletes private provider state;
- refuses the current generation;
- performs no Relay or trust revocation.

## Concurrency and recovery

Generation and retirement share one device-local lifecycle lock.

Concurrent identical requests produce one generation and one idempotent replay. Concurrent distinct requests serialize into distinct generations.

Provider storage is replaced before a generation becomes inventory-visible. Generation directories are immutable after publication. A complete generation directory missing from inventory can be reconciled by request ID. Provider-only orphan state is retained but never advertised as available.

## B5a integration

`keypackage-inspect` and `openmls-keypackage-inspect-dev` accept an optional generation manifest.

When supplied, the immutable generation manifest is the local ownership evidence and must agree on:

- device label;
- KeyPackage reference;
- artifact SHA-256;
- artifact size;
- lifetime bounds.

Inspection remains read-only and does not establish account, Relay Space, human identity, or trust verification.

## Nonclaims

B5b does not implement:

- Relay publication;
- duplicate or cross-destination Relay reuse policy;
- KeyPackage consumption or ACK;
- Welcome submission or join;
- identity or trust promotion;
- production onboarding or production E2EE.

Those remain downstream work, beginning with B5c only after the mandatory post-B5b continuity breakpoint.
