# CarbonStack v0.6.32 Public Surface / Manual Docs Refresh v0

Status: selected docs/help cleanup after v0.6.32A public-surface and manual/CLI docs recon.

Scope: public/operator discoverability cleanup before v0.7.0 release-boundary/package-root rehearsal.

This document is not a release rehearsal.

This document does not add a runner profile.

This document does not change registry semantics.

This document does not change generated command reference count.

This document does not add `full-runtime-dev`.

This document does not implement adversarial harness cases.

This document does not claim deployment readiness, production security, hostile-server safety, PQ/hybrid security, backup/restore, or audit/certification.

---

## 1. Why this checkpoint exists

v0.6.31 created the adversarial harness contract/evidence matrix.

v0.6.32A then inspected the public surface, command registry, generated command reference, runner help, manual/CLI docs, state/recovery docs, deployment warnings, and toolchain floor before v0.7.0 release-boundary/package-root rehearsal.

The recon found that the project was coherent and validated, but release rehearsal should wait until selected discoverability gaps were fixed.

The goal of v0.6.32B is to patch those selected gaps without broadening claims or changing validation semantics.

## 2. v0.6.32A findings addressed

### 2.1 `full-validate-release` help discoverability

Finding:

    `full-validate-release` existed in the runner switch and registry, but runner `--help` did not list it.

Fix:

    runner help now lists `full-validate-release` beside `full`.

Boundary:

    behavior remains exact alias to current `full`.

### 2.2 Runner README first-class profile documentation

Finding:

    runner README had a v0.6.30 note, but no first-class `full-validate-release` profile section.

Fix:

    runner README now documents `full-validate-release` as the preferred explicit release-package validation profile name.

Boundary:

    `full` remains compatibility name through v0.7.0.

### 2.3 Front README current operator surfaces

Finding:

    registry/front-README candidates had moved ahead of the front README.

Fix:

    front README now points to current operator/developer surfaces:

    - `full-validate-release`;
    - `full`;
    - `release-snapshot`;
    - `message-send-dev`;
    - `message-inbox-dev`;
    - `state-audit-dev`;
    - `COMMAND_REFERENCE.v0.md`;
    - docs/229 adversarial harness contract.

Boundary:

    this is discoverability, not production endorsement.

### 2.4 Docs README current-surface pointer

Finding:

    docs README referenced the newest numbered docs but did not clearly index the normal-message wrapper and current manual/docs refresh surface.

Fix:

    docs README now references this checkpoint and current operator-surface categories.

### 2.5 Toolchain floor clarity

Finding:

    runner declares Go `1.24`, while Comms and Cypher currently declare Go `1.26.3`.

Fix:

    runner README and this document record that the floor must be made release-facing before v0.7.0 package rehearsal.

Boundary:

    no `go.mod` file is changed in this checkpoint.

## 3. Current operator-surface categories

### 3.1 Release/package validation

    go run . --profile full-validate-release
    go run . --profile full
    go run . --profile release-snapshot
    go run . --profile verify-checksums

`full-validate-release` is the preferred explicit name.

`full` remains compatibility naming.

`release-snapshot` remains package-root/layout/checksum/core validation.

### 3.2 Normal-message dev/pre-alpha wrappers

    go run ./cmd/comms message-send-dev
    go run ./cmd/comms message-inbox-dev

These are recommended dev/pre-alpha normal-message wrappers.

They are not mature product UX.

They do not prove production E2EE, hostile-server safety, metadata privacy, or verified identity.

### 3.3 State-boundary inventory

    go run ./cmd/comms state-audit-dev
    go run ./cmd/comms state-audit-dev --format json

This is non-mutating state-boundary/proto-substrate inventory.

It is not backup/restore, recovery, secure storage, production vault, trust verification, or Cypher repair.

### 3.4 Adversarial harness contract

    docs/229-v0.6.31-adversarial-harness-contract-evidence-matrix-v0.md

This is a contract and evidence-matrix model.

It is not an implemented adversarial runner.

It does not prove hostile-server safety.
