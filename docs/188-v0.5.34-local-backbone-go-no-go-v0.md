# v0.5.34 local-backbone go/no-go reassessment

Status: local-backbone go/no-go reassessment / implementation-readiness decision
Phase: v0.5.x post-validation-profile-boundary / pre-cleanup-roadmap-checkpoint
Scope: local-backbone readiness, first narrow implementation target, Relay Space schema/API substrate, validation/CLI boundaries
Date: 2026-06-08 local session

## 1. Purpose

v0.5.34 reassesses whether CarbonStack is ready to move from planning toward first narrow implementation after:

    Relay Space mechanics planning;
    provider live-flow boundary planning;
    validation profile boundary planning.

This is a docs-only reassessment.

v0.5.34 does not implement:

    local-backbone;
    Relay Space schema;
    Relay Space API routes;
    Relay Space join flow;
    provider live-flow wiring;
    validation profile changes;
    CLI/registry entries;
    destructive reset/recovery;
    backup/restore;
    re-enrollment mutation;
    vault;
    PQ/hybrid crypto.

Decision:

    local-backbone receives a conditional GO for first narrow implementation planning.
    This is not a GO for full local-backbone.
    The first implementation target should be Cypher Relay Space schema/API substrate.
    Comms broad provider live-flow remains deferred.
    Local-backbone validation profile remains deferred.
    CLI/registry remains deferred.
    v0.5.35 should be cleanup / roadmap refresh / implementation-readiness checkpoint.
    v0.5.36+ may begin first narrow implementation only if continuity and planning-doc scout pass.

## 2. Meaning of conditional GO

Conditional GO means:

    the planning chain is now coherent enough to plan the first narrow implementation rung;
    the first implementation rung can be scoped to routing/storage substrate;
    the project can stop adding broad preconditions before any code;
    implementation can proceed later only with strict continuity and boundary checks.

Conditional GO does not mean:

    full local-backbone is ready;
    local-backbone validation exists;
    Relay Space is implemented;
    provider live-flow is implemented;
    OpenMLS join is automated;
    local trust is mature;
    CLI/registry can be exposed;
    production/security claims are allowed.

## 3. Current readiness chain

Recent controlling chain:

    v0.5.30:
      local-backbone closer but still blocked; selected Relay Space recon/planning.

    v0.5.31:
      Relay Space join/invite/member mechanics planned.

    v0.5.32:
      provider/OpenMLS live-flow boundary planned; broad provider live-flow deferred until Relay Space schema/API and validation boundaries exist.

    v0.5.33:
      validation-profile boundary planned; local-backbone validation profile deferred; generated-state cleanup and release-package/live-umbrella boundaries preserved.

v0.5.34 concludes that the next useful movement is not more broad planning before code, but a cleanup/readiness checkpoint followed by a narrow Cypher Relay Space substrate implementation if still claim-safe.

## 4. Why not full local-backbone

Full local-backbone remains blocked because:

    Relay Space schema/API does not exist;
    Relay Space implementation does not exist;
    Relay Space-scoped envelopes do not exist;
    provider live-flow is not wired;
    Comms client wrappers for Relay Space do not exist;
    local-backbone validation profile does not exist;
    mature verification ceremony does not exist;
    destructive recovery/reset/re-enrollment remains intentionally absent;
    CLI/registry exposure would still overstate maturity;
    release-package local-backbone validation is not possible.

Therefore:

    do not call the next implementation local-backbone.
    call it a first narrow Relay Space substrate implementation.

## 5. First implementation target

Preferred first implementation target:

    Cypher Relay Space schema/API substrate.

Reason:

    provider live-flow needs routable Relay Space artifacts;
    Comms client wrappers need server/API substrate;
    local-backbone validation needs something concrete to validate;
    Relay Space must remain routing/storage only;
    Cypher can implement routing substrate without becoming trust authority.

Candidate first implementation surfaces:

    relay_spaces table;
    relay_space_invites table;
    relay_space_members table;
    relay_space_id-scoped envelope support or migration path;
    create/get/list Relay Space APIs;
    invite create/claim APIs;
    routing member registration/list APIs;
    tests proving routing-only semantics;
    tests proving no trust authority is introduced.

Do not implement all of this at once if a smaller schema-only rung is safer.

## 6. What must remain deferred

Defer:

    Comms broad provider live-flow;
    provider event broad import;
    automatic candidate promotion;
    trust.json mutation from provider observation;
    Relay Space membership as trust;
    OpenMLS/provider membership as local verification;
    local-backbone validation profile;
    CLI/registry exposure;
    destructive reset/recovery/re-enrollment helpers;
    vault;
    PQ/hybrid;
    hostile-server harnesses;
    deployability claims.

## 7. Cypher boundary for first implementation

Cypher may implement routing/storage substrate.

Cypher may store:

    relay_space_id;
    invite metadata;
    routing_member records;
    routing account/device labels;
    envelope routing metadata;
    ack state;
    payload size/hash metadata;
    timestamps and operational routing fields.

Cypher must not store or claim:

    verified trust;
    local trust state;
    plaintext;
    local verification result;
    key replacement authority;
    provider safety truth;
    trust.json authority;
    identity-candidates.json authority.

## 8. Comms boundary after first implementation

Comms should not be broadly wired immediately after Cypher schema/API lands.

Later Comms work should be split into:

    Relay Space client wrapper;
    no-trust-mutation tests;
    candidate handoff only when identity material is explicit;
    provider/OpenMLS join wiring;
    ack-boundary tests;
    validation profile integration.

Relay Space server state should enter Comms as routing context, not trust truth.

## 9. Validation boundary

Do not add local-backbone validation profile in v0.5.34.

Future validation profile work should happen only after concrete substrate exists.

A future profile may prove:

    local Cypher starts;
    Relay Space schema exists;
    Relay Space can be created;
    invite can be created/claimed;
    routing member can be registered;
    Relay Space-scoped envelope can be stored/retrieved;
    no trust authority is created by routing operations.

It must not prove:

    production secure messaging;
    hostile-server safety;
    metadata privacy;
    mature verification UX;
    provider live-flow correctness;
    local verified trust;
    deployment readiness;
    external audit/certification.

    assistant should scout relevant planning docs before code;
