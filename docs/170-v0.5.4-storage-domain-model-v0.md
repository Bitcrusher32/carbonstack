# v0.5.4 storage-domain model

Status: planning model
Phase: v0.5.x state correctness and persistence planning
Scope: CarbonStackComms, CarbonStackCypher, CarbonStack runner/registry, future CarbonStackOS boundary
Date: 2026-06-07 local session

## 1. Purpose

v0.5.4 turns the v0.5.3 state-domain inventory into a storage-domain model.

v0.5.3 answered:

    what state exists today?

v0.5.4 answers:

    what storage domain does each state type belong to?
    who owns it?
    what persistence rule applies?
    what is allowed to regenerate?
    what must fail loudly?
    what should become vault-protected later?
    what should remain server-side, generated, or ephemeral?

This document is still a planning record.

It does not implement:

    vault encryption;
    PQ/hybrid ciphersuites;
    mature send/inbox UX;
    Relay Space join;
    local-backbone;
    Cypher schema changes;
    runner enforcement of storage domains.

## 2. Baseline

Input docs:

    CarbonStack has several valid state islands, not one coherent production storage architecture yet.

It names the storage domains so future work can decide where each state type belongs and which boundaries must be enforced.

## 3. Storage-domain vocabulary

### 3.1 source

Tracked source code, docs, migrations, tests, and release metadata templates.

Rules:

    committed to Git;
    human-reviewable;
    reproducible from repo;
    must not contain generated secrets, local DBs, sidecar provider state, private keys, or transient test outputs.

Examples:

    docs/*.md
    registry/commands.v0.yaml
    migrations/*.sql
    Go/Rust source files
    tests

### 3.2 generated-build

Build outputs from Go, Rust, or packaging tools.

Rules:

    not committed;
    safe to delete;
    expected during validation/build;
    must stay under known generated roots;
    should be cleaned by explicit cleanup where release/package validation requires it.

Examples:

    carbonstack-comms/internal/protocol/mls/openmls-sidecar/target

### 3.3 generated-dev-provider

Dev-only OpenMLS sidecar provider/identity/conversation state.

Rules:

    not committed;
    sensitive;
    not production vault;
    not safe to silently regenerate in meaningful identity/conversation workflows;
    may be generated by dev tests/smokes;
    must remain ignored and scoped.

Examples:

    .carbonstack-openmls-sidecar-state
    signer.json
    provider-storage.json
    sidecar identity summaries
    sidecar conversation state
    sidecar group/provider storage

### 3.4 local-app-state

Local CarbonStackComms application state.

Rules:

    belongs to Comms client runtime;
    stores local profile/account/device/server context;
    must survive ordinary restart once initialized;
    must not silently regenerate after invite/account/device binding;
    currently dev/pre-alpha JSON;
    future format needs versioning/migration.

Examples:

    .carbonstack-comms/state.json

### 3.5 local-trust-state

Local device trust records and trust event history.

Rules:

    belongs to Comms client trust layer;
    must survive restart;
    must not silently regenerate;
    must become loud if missing, replaced, or inconsistent;
    future design should protect integrity/confidentiality as appropriate;
    should eventually bind to real provider identity state.

Examples:

    .carbonstack-comms/trust.json
    .carbonstack-comms/trust-events.jsonl

### 3.6 relay-staging-state

Temporary or semi-temporary local files used to move opaque OpenMLS artifacts into/out of Cypher envelopes.

Rules:

    not committed;
    may contain ciphertext artifacts or setup artifacts;
    must have explicit lifecycle rules before mature UX;
    should not be used as final message storage;
    ack/open behavior must define when files can be deleted.

Examples:

    downloaded KeyPackage artifacts
    downloaded Welcome artifacts
    downloaded application-message artifacts
    artifact files written from Cypher envelope payloads

### 3.7 server-relay-state

CarbonStackCypher server-side relay/storage state.

Rules:

    belongs to Cypher;
    persists account/invite/device/envelope/ack data;
    is not a message-truth trust root;
    may survive restart;
    requires migration/backup/retention policy before serious operator use;
    must not be confused with local client vault.

Examples:

    Cypher SQLite DB
    accounts
    invites
    devices
    envelopes
    ack state
    schema_migrations

### 3.8 validation-package-state

Release package roots, checksums, runner scan state, validation temporary roots, and generated test state.

Rules:

    not runtime state;
    not trust state;
    used to validate package/release integrity;
    should be isolated from live source;
    generated artifacts must remain scoped and cleaned where required.

Examples:

    release/checksums.txt
    staged package roots
    fresh extraction roots
    temporary local-cypher DBs

### 3.9 future-vault-state

State that should eventually be protected by a real local vault or appliance storage boundary.

Rules:

    not implemented yet;
    must be designed after state domains are understood;
    should protect identity-bearing, trust-bearing, group-bearing, message-bearing, and recovery-bearing state;
    should not be treated as a generic encrypted folder.

Examples:

    future real identity private material
    OpenMLS provider storage
    OpenMLS group/conversation state
    trust store and event log
    local message database
    recovery/export bundles

### 3.10 must-not-silently-regenerate

Cross-cutting marker for state whose unexpected loss/replacement changes identity, trust, group continuity, or delivery correctness.

Rules:

    loss or replacement must eventually produce loud warnings, hard errors, recovery flows, or re-verification;
    no automatic silent reinitialization in mature mode;
    dev-only workflows may still regenerate only when explicitly requested.

Examples:

    Comms account ID
    Comms device ID
    trust records
    trust event history
    sidecar signer identity
    provider storage
    OpenMLS conversation/group state
    group epoch/membership state
    revocation state
    Cypher schema migration history

## 5. Domain boundary rules

### 5.1 Source must stay clean

Source must not contain:

    generated provider state;
    signer material;
    private keys;
    local SQLite DBs;
    Rust target outputs;
    smoke-test generated roots;
    downloaded relay artifacts;
    local trust stores;
    local Comms state.

### 5.2 Local app state is not trust state

`.carbonstack-comms/state.json` may identify the local account/device/server context.

It should not become the sole source of truth for:

    verified device trust;
    key-change history;
    revocation history;
    OpenMLS group/provider state;
    future private identity material.

### 5.3 Trust state is not provider state

`trust.json` and `trust-events.jsonl` are Comms trust-layer records.

OpenMLS provider state is sidecar/provider-layer state.

The current bootstrap wrappers intentionally do not mutate Comms trust state.

Future integration must explicitly define when provider identity changes become trust events.

### 5.4 Provider state is not release/package state

Sidecar signer/provider/group state is runtime/dev provider state.

It must not leak into:

    release packages;
    source snapshots;
    registry files;
    docs;
    package checksums;
    generated command references.

### 5.5 Relay staging is not message storage

Relay staging files are an artifact bridge, not a final local message database.

Future mature UX must define:

    staging root;
    filename policy;
    envelope_id to message_label mapping;
    deletion after open/ack;
    failure retention;
    replay handling;
    backup exclusion/inclusion.

### 5.6 Cypher state is not a trust root

Cypher persists routing/delivery state.

It must not decide:

    valid group membership truth;
    trusted device identity;
    key-change acceptance;
    message plaintext truth;
    client trust history.

### 5.7 Validation state is not runtime state

Runner temporary roots and package validation outputs should not influence mature runtime state design except as validation fixtures/checks.

## 6. Persistence expectations

### 6.1 Must survive ordinary restart

    Comms account/device/server state after setup;
    Comms trust store;
    Comms trust event history;
    OpenMLS identity/provider/group state;
    Cypher operator DB state;
    Cypher schema migration history.

### 6.2 May be temporary

    runner temp roots;
    local-cypher temp DBs;
    build outputs;
    smoke-test generated artifacts;
    relay staging files before mature lifecycle policy.

### 6.3 Must be explicit export/import later

    trust state;
    provider/group state;
    local message database;
    recovery bundles;
    backup bundles;
    device migration state.

### 6.4 Must fail loudly if missing/replaced

    local account/device binding;
    verified device record;
    trust event log;
    signer identity;
    provider storage;
    group/conversation state;
    schema migration records;
    revocation records.

## 7. Future validation implications

Future runner or test checks may eventually enforce:

    no generated provider state in source/package roots;
    no local DBs in source/package roots;
    no signer/provider storage in release packages;
    trust state survives restart/load;
    provider state load-check passes after restart;
    missing provider state causes explicit error, not silent recreation;
    trust event log append/load behavior is stable;
    relay staging cleanup does not ack before sidecar open;
    Cypher migration drift fails clearly.

Do not promote these into runner profiles until the storage model is stable enough to avoid false authority.

## 8. PQ / ciphersuite implications

PQ/hybrid ciphersuite work should read this storage-domain model first.

PQ/hybrid changes will likely affect:

    KeyPackage artifacts;
    Welcome artifacts;
    provider storage;
    group state;
    protocol_version;
    content_type;
    trust display;
    group reinit/rekey;
    artifact sizes;
    validation thresholds;
    release claims.

Therefore:

    ciphersuite selection must become visible state;
    migration must be explicit;
    artifact size changes must be measured;
    group/provider state compatibility must be tested;
    trust UI/docs must not claim quantum safety from one lifecycle pass.
