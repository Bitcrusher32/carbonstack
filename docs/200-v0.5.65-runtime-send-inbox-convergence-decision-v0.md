# v0.5.65 runtime send/inbox convergence decision

Status: implementation-boundary decision  
Phase: v0.5.x tail / v0.6.0 pre-release runway  
Scope: runtime send/inbox command-surface convergence, legacy command boundary, OpenMLS dev message path declaration

## 1. Purpose

v0.5.65 closes the v0.6.0 roadmap G3 send/inbox convergence decision without adding a new command wrapper.

The decision is:

    openmls-send-dev and openmls-inbox-dev are the current canonical dev/pre-alpha OpenMLS application-message runtime paths.

The older send, inbox, and ack commands remain legacy/stub-era command surfaces and must continue to warn.

This is a command-surface decision, not mature product messaging UX.

## 2. Current command surfaces

### Legacy surfaces

    send
        legacy/stub-era send path;
        uses the older mock/stub message path;
        not OpenMLS-backed;
        warning points to openmls-send-dev.

    inbox
        legacy/stub-era inbox path;
        may print stub_plaintext;
        not OpenMLS-backed;
        warning points to openmls-inbox-dev.

    ack
        legacy ack helper;
        delivery/local-processing state only;
        not a standalone secure receive proof.

### Canonical dev/pre-alpha OpenMLS message surfaces

    openmls-send-dev
        current dev/pre-alpha OpenMLS application-message send path;
        protects a message through the OpenMLS sidecar;
        submits the produced application-message artifact through Cypher;
        still not mature product UX or production security.

    openmls-inbox-dev
        current dev/pre-alpha OpenMLS application-message receive/open path;
        fetches Cypher inbox envelopes;
        skips unsupported envelopes;
        writes OpenMLS application-message artifacts;
        opens through the OpenMLS sidecar;
        optionally acks only after sidecar open succeeds;
        still not mature product UX or production security.

## 3. Why no new wrapper command yet

A new message-send-dev / message-inbox-dev wrapper would mostly be a naming alias around existing OpenMLS dev commands.

That would add another command layer before the release command-boundary table exists.

The existing command naming convention already uses openmls-*-dev for OpenMLS dev runtime commands. The registry already exposes openmls-send-dev and openmls-inbox-dev as dev-only front README candidates, while legacy send/inbox entries point to them as replacements.

Therefore v0.5.65 chooses documented separation rather than adding aliases.

## 4. v0.6.0 release posture

v0.6.0 may state:

    CarbonStack has explicit legacy send/inbox/ack warnings and canonical dev/pre-alpha OpenMLS application-message paths through openmls-send-dev and openmls-inbox-dev.

v0.6.0 must not state:

    mature product messaging UX;
    production secure messaging;
    local-backbone;
    hostile-server safety;
    metadata privacy;
    production E2EE;
    completed vault/key storage;
    Android readiness.

## 5. Future v0.6.x work

Early v0.6.x should do a real messaging process revamp/consolidation arc.

That future work can decide whether:

    send and inbox should be replaced;
    legacy send/inbox should reject by default unless --allow-stub is passed;
    OpenMLS dev commands should be promoted/renamed;
    a product-facing message CLI should exist;
    ack behavior should be folded into receive/open semantics;
    sidecar labels and conversation labels should become persistent UX state.

## 6. Validation expectation

This decision doc does not require Comms code changes.

Required validation:

    carbonstack registry/tooling tests pass;
    Comms tests remain green;
    Cypher tests remain green;
    runner doctor passes.

## 7. Nonclaims

v0.5.65 does not:

    add a new command;
    add a wrapper;
    change send behavior;
    change inbox behavior;
    change ack behavior;
    remove legacy commands;
    reject legacy commands;
    rewrite OpenMLS runtime message flow;
    change sidecar behavior;
    change trust mutation behavior;
    add release-profile inclusion;
    claim mature messaging UX;
    claim production secure messaging.
