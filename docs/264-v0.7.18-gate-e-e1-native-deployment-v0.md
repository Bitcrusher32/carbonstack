# Gate E E1 Native Deployment

Status: accepted implementation document  
Scope: v0.7.x Gate E E1  
Profile: `gate-e-native-deployment-dev`

## Summary

Gate E E1 introduces the first manual-private native deployment proof profile after Gate D closure.

The profile is intentionally manual and explicit. It does not install a service, generate systemd units, start public ingress, start a TUI, introduce containers, or promote `full-runtime-dev`.

## Why manual first

The Gate E recon found that `cmd/cypher` is a server entrypoint, not a safe terminating CLI inspection surface. Calling `go run ./cmd/cypher --help` starts the server with defaults rather than printing help and exiting.

Therefore Gate E E1 avoids implicit inspection and proves only the safer model:

- build Cypher into a deployment-owned bin root;
- start Cypher intentionally;
- use explicit loopback address;
- use explicit DB path;
- use explicit migrations path;
- use explicit dev invite;
- health-check;
- stop;
- restart against the same DB;
- inspect the deployment-root state with Gate C policy surfaces.

## Deployment-root fixture

The profile creates a generated deployment-root fixture with:

- `bin/`
- `config/`
- `state/comms/`
- `state/cypher/`
- `state/sidecar/`
- `logs/`
- `evidence/`
- `tmp/`

The fixture is generated evidence, not an installed runtime and not a production configuration.

## Accepted E1 semantics

Gate E E1 proves:

- explicit native deployment context is generated and inspectable;
- Cypher can be built into a deployment-owned binary location;
- Cypher can start under explicit environment variables;
- Cypher can write its DB into the declared deployment state root;
- Cypher can restart against the same explicit DB;
- Gate C C1/C2/C3/C4 state-policy surfaces work over the deployment roots;
- registry/reference freshness and nonclaim coverage remain intact;
- Gate D authority remains present without promoting `full-runtime-dev`.

## Blocked after E1

Further Gate E subgates require a continuity breakpoint first.

Potential later Gate E subgates include:

- runbook polish;
- a terminating Cypher inspection/config mode;
- a helper runner, only if justified;
- semi-persistent service/systemd exploration, only after explicit acceptance;
- package/runtime split planning for Gate F.

## Nonclaims

Gate E E1 does not claim:

- Gate E final closure;
- semi-persistent service readiness;
- systemd readiness;
- helper install readiness;
- public ingress;
- container readiness;
- TUI readiness;
- `full-runtime-dev`;
- production readiness;
- production E2EE;
- verified identity;
- trust promotion;
- vault security;
- backup/restore safety;
- PQ/hybrid support;
- Android;
- CarbonStackOS implementation;
- v0.8.0 release readiness.
