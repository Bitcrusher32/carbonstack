## 0. Executive summary

v0.6.2 demoted the old stub-era message commands by requiring explicit `--allow-legacy-stub` for:

    send
    inbox
    ack

v0.6.3 now defines the replacement-side contract around the existing dev/pre-alpha OpenMLS message path:

    openmls-send-dev
    openmls-inbox-dev --ack

This document is intentionally a planning contract. It does not add wrappers, rename commands, change behavior, or promote dev commands to mature UX.

Current decision:

    Keep openmls-send-dev and openmls-inbox-dev as the canonical dev/pre-alpha command names for now.
    Do not add message-send-dev or message-inbox-dev wrappers yet.
    Treat Relay Space onboarding as a prerequisite/artifact path, not ordinary message flow.
    Strengthen command-level OpenMLS tests before nicer names or integrated runtime profile expansion.
    Defer live_deployment or similarly named profile until the finalized message flow exists and has stable tests.

## 1. Why this checkpoint exists

The v0.6.x roadmap centers on OpenMLS message-flow integration and boundary hardening. The normal message workflow must become OpenMLS-based rather than mock/stub based, artifact inboxes must not be confused with message inboxes, and registry/docs must classify real behavior without promotion drift.

v0.6.1 mapped the message surfaces.

v0.6.2 made the old stub path opt-in.

v0.6.3 defines what the normal OpenMLS application-message path means before new public-ish wrappers or aliases are introduced.

This prevents a second ambiguity layer:

    old ambiguity:
        send / inbox sounded normal but were stub-era

    possible new ambiguity:
        message-send-dev / message-inbox-dev could sound more mature than they are

So v0.6.3 keeps the ugly-but-honest OpenMLS dev names while specifying the contract they already mostly satisfy.

## 3. Normal OpenMLS application-message preconditions

A normal dev/pre-alpha OpenMLS application-message exchange assumes:

    sender Comms state exists and is ready;
    recipient Comms device exists;
    Cypher server is reachable;
    OpenMLS sidecar identity exists for sender and recipient;
    an OpenMLS conversation exists or has already been joined;
    the sender knows the sidecar device label and conversation label;
    the recipient knows the sidecar device label and conversation label;
    trust policy permits the send path;
    Relay Space onboarding/artifact work has already happened if needed.

Relay Space onboarding is not part of ordinary message send/open. It is a prerequisite path.

## 4. Normal send contract

Command:

    openmls-send-dev

Required flags:

    --to-device
    --message
    --sidecar-device-label
    --conversation

Optional flags:

    --state
    --strict
    --sidecar-dir
    --message-label

Current sequence:

    1. Parse flags.
    2. Require recipient device, plaintext message, sidecar device label, and conversation label.
    3. Load ready Comms state.
    4. Resolve command state/trust paths.
    5. Evaluate send trust policy.
    6. In non-strict mode, print dev trust warning.
    7. Block if trust policy denies send.
    8. Run OpenMLS sidecar message-protect.
    9. Resolve message_artifact_path_hint from sidecar output.
    10. Submit the artifact through Cypher as an OpenMLS application-message envelope.
    11. Print structured summary:
        command
        status
        sender_device_id
        recipient_device_id
        content_type
        protocol_version
        envelope_id
        delivery_state
        server_received_at
        payload_sha256
        payload_size_bytes
        sidecar labels
        dev/pre-alpha warning

Current content/protocol shape:

    content_type: carbonstack.mls.application-message.v0
    protocol_version: carbonstack-openmls-sidecar-v0

Allowed current claim:

    openmls-send-dev is the current canonical dev/pre-alpha OpenMLS application-message send path.

Forbidden claims:

    production E2EE
    hostile-server safety
    metadata privacy
    verified identity
    mature product UX
    general-user readiness

## 5. Normal inbox/open contract

Command:

    openmls-inbox-dev

Required flags:

    --sidecar-device-label
    --conversation

Optional flags:

    --state
    --sidecar-dir
    --message-label
    --limit
    --ack

Current sequence:

    1. Parse flags.
    2. Require sidecar device label and conversation label.
    3. Require --limit >= 1.
    4. Load ready Comms state.
    5. Fetch current device inbox from Cypher.
    6. Print inbox header and dev/pre-alpha warning.
    7. For each envelope until opened count reaches limit:
        - skip unsupported content/protocol pairs;
        - generate message label if omitted;
        - write OpenMLS artifact from envelope to temp path;
        - run OpenMLS sidecar message-open;
        - if message-open fails, report failure and do not ack;
        - if message-open succeeds, print opened plaintext/metadata;
        - if --ack is passed, ack only after successful message-open;
        - report ack failure separately if ack fails.
    8. Print summary counters:
        opened_envelopes
        unsupported_envelopes
        open_failures
        ack_failures

Ack rule:

    No ack on fetch.
    No ack on unsupported envelope.
    No ack on artifact-write failure.
    No ack on message-open failure.
    Ack only after successful sidecar message-open and only when --ack is explicit.
    Later, after durable local storage/vault work exists, ack should move toward decrypt plus durable local commit.

Allowed current claim:

    openmls-inbox-dev is the current canonical dev/pre-alpha OpenMLS application-message inbox/open path.

Forbidden claims:

    mature inbox UX
    production receive proof
    hostile-server safety
    durable local storage
    vault-backed receive semantics
    metadata privacy

## 6. Relay Space / onboarding boundary

Relay Space onboarding commands are separate artifact/lifecycle primitives:

    openmls-relay-keypackage-submit-dev
    openmls-relay-keypackage-inbox-dev
    openmls-relay-welcome-submit-dev
    openmls-relay-welcome-inbox-dev
    openmls-relay-add-member-dev
    openmls-relay-join-dev

They are not normal message send/open.

Boundary rules:

    KeyPackage envelopes are onboarding artifacts.
    Welcome envelopes are onboarding artifacts.
    KeyPackage inbox and Welcome inbox are artifact inboxes.
    Artifact write success is not message-open success.
    Artifact write success is not ack eligibility by itself.
    Welcome ack is only eligible after successful conversation-join when explicit.
    Application-message ack is only eligible after successful message-open when explicit.

A future wrapper may orchestrate onboarding, but the primitive commands must remain separately callable because partial lifecycle states are operationally important.

## 7. Current test evidence

Current command-level app tests cover:

    openmls-send-dev:
        rejects missing required flags;
        does not submit when message-protect fails;
        submits an OpenMLS application-message artifact after message-protect succeeds.

    openmls-inbox-dev:
        rejects missing required flags;
        skips unsupported envelopes;
        does not ack when message-open fails;
        acks only after message-open succeeds when --ack is explicitly passed.

Current Relay/OpenMLS app tests cover:

    KeyPackage submit requirements;
    KeyPackage submit/export/envelope behavior;
    Welcome submit requirements;
    Welcome submit behavior;
    KeyPackage inbox writes without ack;
    Welcome inbox writes without ack;
    artifact write failure without ack;
    add-member success and failure edges;
    join success and failure edges;
    join ack only after success when requested.

Current protocol-level tests cover:

    sidecar wrong-device rejection;
    sidecar wrong-conversation rejection;
    duplicate/replay rejection;
    corrupt/truncated artifact rejection;
    real-Cypher OpenMLS lifecycle;
    OpenMLS relay artifact behavior;
    lower-level bridge and artifact validation.

Current runner surfaces:

    dev-runtime-openmls:
        direct-sidecar smoke proof for openmls-send-dev -> Cypher -> openmls-inbox-dev --ack.

    dev-runtime-openmls-wrappers:
        wrapper-bootstrap smoke proof for openmls-*-dev bootstrap wrappers -> openmls-send-dev -> Cypher -> openmls-inbox-dev --ack.

    relay-openmls-join-dev:
        manual/dev live-umbrella Relay Space join proof; still excluded from full/release-snapshot.

## 8. Test gaps before wrappers or promotion

Before adding message-send-dev/message-inbox-dev wrappers or a broader live_deployment profile, add or explicitly defer command-level tests for:

    send path:
        submit failure after message-protect succeeds;
        trust policy block under strict mode;
        empty message label uses sidecar/default label behavior;
        missing/empty message_artifact_path_hint;
        relative artifact path resolution;
        output contract contains content_type/protocol_version/payload metadata.

    inbox path:
        empty/no-message inbox behavior;
        artifact write failure;
        ack failure after successful open;
        multiple OpenMLS envelopes with --limit;
        generated message-label behavior when --message-label is omitted;
        unsupported envelope summary count;
        open failure summary count;
        ack failure summary count;
        output contract contains content_type/protocol_version/plaintext metadata.

    cross-path:
        direct smoke and wrapper smoke remain separate until wrapper path can replace direct path;
        Relay onboarding remains prerequisite material, not normal message inbox;
        no command auto-acks merely because an envelope was fetched or written.

Some negative behavior is already covered at protocol/sidecar level. v0.6.3 does not require duplicating every sidecar negative test at command level. It requires deciding which command-level boundaries must be explicit because they affect CLI contract or ack safety.

## 9. Registry/table policy

No registry or command-boundary table change is required by this docs-only contract.

Registry/table updates are required later if:

    new wrapper commands are introduced;
    command names change;
    maturity/audience changes;
    required or optional flags change;
    runner profiles include or exclude these commands differently;
    a live_deployment or full-runtime-dev profile is added;
    OpenMLS dev commands are promoted or demoted;
    behavior changes enough that current descriptions become false.

Do not add registry rows for planned commands before behavior exists.
