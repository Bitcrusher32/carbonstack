# v0.5.42 provider/OpenMLS join wiring plan

Status: planning-only decision document
Phase: v0.5.x Relay Space substrate/client/bridge complete enough for join planning
Scope: provider/OpenMLS join wiring plan, artifact order, candidate boundary, ack timing, future implementation ladder
Date: 2026-06-08 local session

## 1. Purpose

v0.5.42 defines how provider/OpenMLS join wiring should be approached after the v0.5.36-v0.5.41 implementation sequence.

v0.5.42 does not implement code.

It does not add:

    app/runtime wiring;
    provider live-flow;
    OpenMLS join automation;
    local-backbone validation profile;
    CLI/registry entries;
    roadmap refresh;
    trust.json mutation;
    identity-candidates.json mutation;
    verified identity import;
    destructive reset/recovery/re-enrollment;
    vault;
    PQ/hybrid cryptography.

This document exists because provider/OpenMLS join wiring is the point where routing, provider membership, candidate observation, local trust, and ack policy can accidentally collapse into unsafe claims.

## 3. Current OpenMLS sidecar/app surfaces

Current Comms dev/runtime surfaces already include:

    identity create/status;
    public bundle / KeyPackage export;
    conversation create;
    conversation load check;
    conversation add member;
    Welcome artifact creation;
    conversation join from Welcome;
    message protect;
    message open;
    unscoped OpenMLS send/inbox dev commands;
    ack only after message-open succeeds in the existing inbox command.

These surfaces prove pieces of the OpenMLS artifact lifecycle, but they do not yet create a mature Relay Space join flow or local-backbone.

## 4. Core distinction

Relay Space is routing and conversation infrastructure.

OpenMLS provider/group membership is cryptographic group membership.

Local verification is local trust ceremony/state.

These three things must remain separate.

A device being present in a Relay Space does not mean verified.

A device receiving a Relay Space invite does not mean verified.

A device submitting a KeyPackage does not mean verified.

A device joining an OpenMLS group does not mean verified.

A provider reporting successful membership does not mean verified.

A successful Welcome consume/join does not mean verified.

Local verification must remain a separate explicit ceremony/state transition.

## 5. Preferred artifact order

The future join path should use explicit Relay Space-scoped artifact movement.

Preferred conceptual order:

    1. Relay Space exists.
    2. Routing members exist for the devices participating in the join.
    3. Invitee exports an OpenMLS KeyPackage/public bundle.
    4. Invitee submits KeyPackage artifact through Relay Space-scoped envelope route.
    5. Inviter retrieves KeyPackage from Relay Space-scoped inbox.
    6. Inviter writes KeyPackage artifact locally.
    7. Inviter runs OpenMLS conversation-add-member with the KeyPackage.
    8. Sidecar creates Welcome artifact.
    9. Inviter submits Welcome artifact through Relay Space-scoped envelope route to invitee.
    10. Invitee retrieves Welcome from Relay Space-scoped inbox.
    11. Invitee writes Welcome artifact locally.
    12. Invitee runs OpenMLS conversation-join with the Welcome.
    13. Only after successful sidecar join should the Welcome envelope be acked.
    14. Application messages remain a separate later flow after membership exists.

This is still a dev/pre-alpha artifact flow, not mature UX.

## 6. Candidate observation rule

Provider/OpenMLS join wiring may expose identity-relevant material.

Identity-relevant material may include:

    Cypher device IDs and public keys;
    OpenMLS KeyPackage/public bundle material;
    provider-observed member information;
    sidecar summary material that can be mapped to a device/conversation.

If identity material is observed, it may enter candidate observation paths.

It must not directly enter:

    verified trust;
    trust.json mutation;
    key replacement;
    local verified device status;
    automatic candidate promotion;
    recovery bypass.

Core rule:

    Provider-observed identity material is candidate/unverified material until local verification says otherwise.

## 7. Provider membership vs local verification

Provider/OpenMLS membership can mean:

    the sidecar accepted a KeyPackage;
    a Welcome was produced;
    a Welcome was consumed;
    a group became reloadable;
    a member count changed;
    an epoch advanced;
    application messages can be protected/opened in that group.

Provider/OpenMLS membership must not mean:

    the human/device is locally verified;
    trust.json should be mutated;
    the known key should be replaced;
    the candidate should be accepted;
    recovery is safe;
    metadata privacy is achieved;
    hostile-server safety is achieved.

## 8. Ack timing

Ack must remain tied to successful local processing.

For KeyPackage envelopes:

    receiver may ack only after the KeyPackage artifact was decoded/written and the intended sidecar operation succeeded or the caller deliberately records safe terminal handling;
    preferred first implementation should avoid automatic KeyPackage ack unless add-member succeeded.

For Welcome envelopes:

    invitee may ack only after the Welcome artifact was decoded/written and conversation-join succeeded.

For application-message envelopes:

    recipient may ack only after message-open succeeds.

Do not ack merely because:

    the envelope was downloaded;
    the Relay Space exists;
    a routing member exists;
    a provider group exists;
    an artifact file was written without successful sidecar consume/open/join;
    a command entered a happy path before sidecar success.

## 9. Forbidden automatic mutations

Future join wiring must not automatically:

    mark a device verified;
    mutate trust.json from Relay Space membership;
    mutate trust.json from provider membership;
    mutate trust.json from KeyPackage observation alone;
    mutate identity-candidates.json as accepted/verified;
    silently replace known key material;
    bypass mapped mismatch classification;
    bypass recovery classification;
    bypass candidate review;
    create destructive reset/recovery/re-enrollment operations;
    expose CLI/registry entries that overstate maturity.

## 10. First safe implementation slice after v0.5.42

The first safe implementation after v0.5.42 should not be full join automation.

Recommended first implementation slice:

    narrow Relay Space OpenMLS join artifact transport helpers or dev command scaffolding;
    KeyPackage and Welcome movement only;
    no local trust mutation;
    no automatic candidate acceptance;
    no validation profile;
    no CLI/registry public contract unless explicitly scoped as dev/pre-alpha;
    no claim of local-backbone.

Candidate v0.5.43 implementation target:

    preflight first;
    decide whether to implement KeyPackage/Welcome relay command scaffolding or lower-level helper functions;
    keep implementation narrow;
    prove only artifact route shape and sidecar success gating.
